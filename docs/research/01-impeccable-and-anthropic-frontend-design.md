## 2. Source-by-source notes

### 2.1 pbakaus/impeccable — design skill + detector for AI coding harnesses

#### 2.1.A Architecture: one source, many harnesses

- **Single source** in `skill/` (`SKILL.src.md`, `reference/*.md`, `agents/*.md`, `scripts/`); the build emits provider copies into `.claude/`, `.cursor/`, `.agents/` (Codex), `.gemini/`, `.github/` (Copilot), `.grok/`, `.hermes/`, `.kiro/`, `.opencode/`, `.pi/`, `.qoder/`, `.rovodev/`, `.trae/`, `.trae-cn/`, `.vibe/`, `.veto/`, `.dsh/`, `.agent/` (Antigravity). The generated folders are committed so `npx skills` and git-submodule users can consume them directly ([IMP]/CLAUDE.md §Build System; [IMP]/docs/HARNESSES.md).
- **Compile-time placeholders**: `{{model}}`, `{{config_file}}`, `{{ask_instruction}}` (per harness: Claude Code is told to stop and use its AskUserQuestion tool; Codex its structured question tool, else plain chat), `{{command_prefix}}` (`/` vs Codex's `$`), `{{available_commands}}`, `{{scripts_path}}` ([IMP]/scripts/lib/utils.js `PROVIDER_PLACEHOLDERS`). A build validator checks that every ask-placeholder sits at the start of a sentence.
- **Provider-tagged blocks**: markdown wrapped in `<claude>`, `<codex>` or `<gemini>` tags survives only in the matching build (`providerTags` in [IMP]/scripts/lib/transformers/providers.js). This is how Impeccable ships **model-specific calibration**: a Claude-only block says Claude's habitual rendering turns warm, bookish or child-facing subjects into cream grounds, italic serif display and lamplight even when nothing asked for it ([IMP]/skill/reference/new-work.md §4); a Codex-only block bans GPT-typical tells (a hairline border under a wide soft shadow, over-rounded cards — radii 12–16px, pills only for small controls — sketch-style SVG pictures, decorative stripe/grid backgrounds, dismissive "X theater" copy, plus a reminder that tracking stops at −0.04em and −0.02 to −0.03em usually reads better); a Gemini-only block forbids animating images on hover ([IMP]/skill/reference/craft-floor.md).
- **Per-harness frontmatter**: e.g. the Claude Code build omits `allowed-tools` because that field blocked activation in non-interactive sessions (comment referencing issue #736 in providers.js); Codex gets the version inside `metadata` plus an `agents/openai.yaml` sidecar.
- **Sub-agents**: canonical prompts in `skill/agents/` (finish-reviewer, documenter, asset-producer, manual-edit-applier) are emitted as native agent files only where a documented on-disk format exists (Claude/Grok markdown, Codex TOML nested in the skill, Copilot `.agent.md`); everywhere else an in-thread fallback (`reference/degraded/*.md`) is generated. Codex must ask the user before spawning; Cursor's sub-agents are chosen by the agent and cannot be reliably spawned by a skill ([IMP]/docs/HARNESSES.md, spawn/permission table).
- **Hooks**: after-edit detector hooks on Claude Code / Codex / Copilot (post-tool reminder to the model), Cursor (pre-write hook that *blocks* a bad write), Grok (findings surfaced on Stop). Rules are tiered: 13 *immediate* rules run per edit — `broken-image`, `text-overflow`, `clipped-overflow-container`, `body-text-viewport-edge`, `low-contrast`, `gray-on-color`, `tiny-text`, `gradient-text`, `dark-glow` and the four `design-system-*` drift rules — and the full set runs once on Stop ([IMP]/crates/foundation/src/registry.rs `IMMEDIATE_TIER_RULES`; [IMP]/skill/reference/hooks.md). A harness without hooks receives a `MANUAL_DETECTOR_REQUIRED` directive asking for one detector run before finishing.
- **Engine**: the skill has no runtime of its own; a POSIX launcher execs a version-pinned self-contained Rust binary, downloaded on first run into `~/.impeccable/bin/` ([IMP]/README.md; [IMP]/CLAUDE.md §Engine binary). Open security caveats: no independent integrity check for that download (impeccable#813), antivirus quarantines on Windows (#740, #758, #814), and hooks executing outside the model-tool permission layer (README; #744).
- **Private components**: the concept/composition catalog used by the "roll", the A/B eval framework and the website live in private repos; `concept-seed` calls `https://impeccable.style/api/roll` (one GET carrying scope, mode, an 8-hex seed key and a re-roll counter) and, without network, degrades to a roll with no catalog challengers; a choice-ping telemetry call respects `DO_NOT_TRACK` ([IMP]/CLAUDE.md §Repo split; [IMP]/crates/context/src/seed_text.rs `DEGRADED_BODY`). CLAUDE.md describes the catalog as the commercial moat.

#### 2.1.B Context gathering: PRODUCT.md, DESIGN.md, surface briefs, config

- **Setup**: each session runs `scripts/impeccable context` once; it loads PRODUCT.md, DESIGN.md, the matching surface brief and native-platform guidance and prints directives such as `NO_PRODUCT_MD`, `INCUMBENT_WORLD_UNDOCUMENTED`, `IMAGE_GEN_AVAILABLE`, `MANUAL_DETECTOR_REQUIRED`, `CONTEXT_STALE`, `UPDATE_AVAILABLE` ([IMP]/skill/SKILL.src.md §Setup; [IMP]/crates/context/src/context_cli.rs). If the launcher is refused, the model must tell the user in a separate message before its next tool call and then read the files directly.
- **Separation of concerns (v4)**: PRODUCT.md holds durable product truth; DESIGN.md the durable visual system; `.impeccable/surfaces/*.md` per-route strategy (visitor mode, direction contract); `.impeccable/config.json` workflow settings such as `buildPath` (`comp` or `code`) ([IMP]/skill/reference/new-work.md; init.md).
- **`init` interview rules** ([IMP]/skill/reference/init.md): scan docs, copy, package/config, routes, roles, logos, legal/proof assets and platform/accessibility signals first, treating findings as hypotheses; ask at most three focused questions per round; get at least one real answer round before writing a new PRODUCT.md; start with (1) primary user, situation and job, (2) what the product enables and its distinctive mechanism, (3) durable constraints, assets and evidence. Whether a human can answer is tested mechanically (probe once); if nobody can, infer only from the explicit brief and label each inferred fact. **No aesthetic questions at init** (no feel, references, colors or type). PRODUCT.md sections: `## Platform` (bare `web|ios|android|adaptive`), `## Stack` (greenfield only; record "delegated" if the user leaves it to the agent), `## Users`, `## Product Purpose`, `## Positioning`, `## Operating Context`, `## Capabilities and Constraints`, `## Brand Commitments`, `## Evidence on Hand` (including absences that must not be fabricated), `## Product Principles` (3–5, no visual recipes), `## Accessibility & Inclusion`, plus a schema-version comment. Invented testimonials, customers, benchmarks, pricing and deployment claims are excluded by rule.
- **v3 → v4**: v3's `teach` asked for a 3-word brand personality, reference sites and anti-references and stored a project-wide `## Register` (brand/product) ([IMP-v3]/reference/teach.md). v4 removed register in favour of per-surface *mode*, moved aesthetic questions to the per-surface new-work round, and treats a leftover `## Register` as deprecated and to be ignored ([IMP]/skill/reference/doctor.md Step 3).
- **`document` → DESIGN.md** ([IMP]/skill/reference/document.md): uses the Google Labs **DESIGN.md format** (spec: https://raw.githubusercontent.com/google-labs-code/design.md/main/docs/spec.md; the format Google Stitch lints). YAML frontmatter tokens are normative — only `colors`, `typography`, `rounded`, `spacing`, `components` at top level; component sub-tokens limited to eight properties (`backgroundColor`, `textColor`, `typography`, `rounded`, `padding`, `size`, `height`, `width`); references written `{colors.primary}`. The body has up to eight sections in fixed order with exact headings: Overview, Colors, Typography, Layout, Elevation & Depth, Shapes, Components, Do's and Don'ts. What the spec cannot hold (tonal ramps, shadows, motion tokens, breakpoints, self-contained component HTML/CSS snippets with `ds-` prefixed classes and hover/focus states, narrative) goes to a sidecar `.impeccable/design.json` (schemaVersion 2). Scan order: CSS custom properties → Tailwind config → CSS-in-JS themes → token JSON → component library → global stylesheet → computed styles in the running page. Only qualitative language is asked of the user (two rounds of ≤3 questions): a named metaphor for the system ("Creative North Star"), overview voice, descriptive color names, elevation and component philosophy. Writing conventions: description first with the exact value in parentheses; memorable "Named Rules" (`**The [Name] Rule.**`, 1–3 per section) because agents follow them better than bullet lists; record only reused tokens; never invent components; never overwrite an existing DESIGN.md without asking. Seed mode (no code yet) writes only `name`/`description` frontmatter and marks unsettled values `[to be resolved during implementation]`.
- **DESIGN.md is written after the build, not before** (v4): for a new world the documenter sub-agent derives DESIGN.md from the shipped artifact, on the reasoning that rules written up front end up defended against what was actually built ([IMP]/skill/reference/new-work.md §5; [IMP]/skill/agents/impeccable-documenter.md). The documenter must not turn a craft-floor violation into a system rule (a session once shipped five invented kickers and the documenter recorded their style as house style).
- **`doctor`** separates tool-version drift, schema drift (mechanical, auto-fixable) and *truth drift* (code moved on; only reported, and a commit count must be presented as a proxy, never as proof the document is wrong) ([IMP]/skill/reference/doctor.md).

#### 2.1.C Visitor modes and the new-work (build) flow

- **Four modes, chosen per surface, not per product**: **Persuade** (landing, marketing, pricing: earn attention and action), **Operate** (app UI, dashboards, settings: scanability, consistency and native expectations outrank expression), **Read** (docs, articles: comprehension first, then reading pleasure), **Experience** (portfolios, galleries: the artifact leads and the interface recedes). A product's landing page is Persuade even if the product is a tool; a fashion house's docs are Read ([IMP]/skill/SKILL.src.md §Modes). This replaced v3's two-valued brand/product "register".
- **Core rules**: a pinned brief always wins over the skill's taste (honour requested aesthetics, fonts, palettes even when they trip a slop warning); **refinement preserves** identity, behavior, copy and everything outside scope (ask before replacing factual copy), **redesign replaces** the look but keeps product truth, content, function and native affordances; never split the difference by polishing a look that is being discarded; a missing DESIGN.md does not by itself make a project greenfield.
- **Bounded verification** (SKILL.md principle 3): build fully, inspect once in a batched round (desktop + mobile together on web; each shipped device class on native), fix everything in one batch, confirm with at most one more round, then stop; open-ended self-QA is described as costly and worse than the dedicated finish handoffs. new-work §7 sets two inspection rounds as the ceiling.
- **Step 1 — decide what is already true**: redesign / established world (inherit) / incomplete brand (extend with the user) / no visual authority (create with the user). A section, component or state inside an established surface inherits that surface.
- **Step 2 — ask 2–3 questions** through the structured question tool, by mode: Persuade (who must act, what they should come to believe, which real proof earns that belief), Operate (the task, information, important states, frequency, constraints), Read (the reader's question, source material, structure, wayfinding), Experience (what leads, how exploration unfolds, which interaction matters). Across modes: what success looks like, what must stay untouched, what would make a polished result feel wrong. Never ask for CSS values or offer canned style lanes.
- **Step 3 — amount of invention**: extending a surface needs no concept tournament; a whole new surface inside an established world derives **5–7 materially different structures** and the engine deals three to the user as equal-salience cards; creating or replacing a world goes: (1) state the product's unique mechanism in one sentence, the audience's real scene and cultural home, what this first surface must prove, and both the category's default page and its predictable opposite (both count as the rut); (2) list **seven concrete visual systems, artifacts, places or rituals** from the audience's world, ordered by resonance and spanning **at least three material families** — on Operate/Read surfaces never draw them from the tools the audience operates (a terminal aesthetic on a working screen becomes costume); (3) turn them into complete directions; (4) run `impeccable concept-seed`, **the roll**: `build_index = 3 + floor(u·(n−2))` with `u` from SHA-256 of the seed key, so **the assigned direction is always candidate #3…#n of the model's own ranked list, never its top two** — the stated reason being that the model's first choice is what every run would ship ([IMP]/crates/context/src/concept_seed.rs; seed_text.rs `PROMOTED_DIRECTION`). The roll also deals human-approved catalog "challengers", which are fused with the product's facts and judged on exactly two axes, **audience identification** and **product clarity**, with verdicts wins / competitive / declined; even a declined challenger must donate one discipline the assigned direction lacks (its rigor or ambition, not its surface styling). (5) Present one fully committed direction, at most one "pick" card showing the model's own favourite with an honest note on its familiarity, the alternates, re-roll (plain / safer / bolder registers) and a permanent quiet option to do the category standard straight — offered as the user's choice, never recommended by the agent. The agent may re-roll on its own only for factual reasons, never taste. Decisions are presented on a local decision page (`serve-question`) with the structured question tool as fallback.
- **Truth binds claims, not demonstrations**: demo content may be authored at full fidelity if labelled synthetic; prices, customers, benchmarks, endpoints and capabilities may never be invented (new-work.md, rule `skill-truth-binds-claims`).
- **Step 4 — commit the world**: choose a **color strategy** before colors — *Restrained* (neutrals + one accent; default for Operate/Read), *Committed* (one saturated color covers **30–60%** of the surface), *Full palette* (3–4 named roles), *Drenched* (the surface is the color); color commits at page scale, not as scattered accents. **Light or dark is never a default**: write one sentence of physical scene (who, where, what ambient light) and let it decide. Fonts: Operate/Read surfaces are well served by system stacks and workhorse UI faces; on Persuade/Experience surfaces the following count as training-data defaults that need a reason no other face satisfies (and a subject association is never such a reason): Fraunces, Playfair Display, Cormorant, Lora, Crimson, Newsreader, Syne, Space Grotesk, Space Mono, IBM Plex, Inter-as-display, DM Sans, DM Serif, Outfit, Plus Jakarta Sans, Instrument Sans. **Calibration**: generated interfaces cluster in three looks — (a) warm cream ground, high-contrast serif display, terracotta/signal-red accent; (b) near-black with one neon accent and glowing edges; (c) broadsheet-editorial hairlines, italic display serif, tiny tracked mono labels. Each is legitimate if the brief asks for it; landing in one when the brief leaves the aesthetic open means the self-check failed. The test: if the look could be predicted from the category alone, or from the category plus a simple avoid-the-obvious inversion, rework it.
- **Step 5 — record the direction contract** (~150 words) under `## Direction contract` in the surface brief: THESIS (the one idea and the category-default arrangement it refuses), OWN-WORLD (palette and component language recognizable with the content removed), STORY, FIRST VIEWPORT (exact composition, where the primary action sits), FORM (+ seed key) and a fixed FINISH line stating that an unreviewed, undocumented build is unfinished. The contract must **never be copied into shipped code** (comments, hidden DOM, data attributes, RSC payloads, JSON-LD …) — a rule added after impeccable#666 showed contracts leaking into production HTML where they were findable by web search.
- **Step 6 — build with full commitment**: rebuild every atom (nav, buttons, inputs, links) in the chosen form's vocabulary — a stock component inside a committed form is a lapse; treat the first viewport as a thesis and apply a **memory test** (what would someone who left after one viewport describe an hour later? if only a mood, the concept has not committed); prove rather than claim (show the product working); author real assets instead of substituting chrome (gradients, glass, generic icon tiles, many-vertex clip-paths); pace density, scale and quiet like a studio, with more space above headings than below; use real, verified imagery when the brief implies it; orchestrate motion once rather than scattering it.
- **Comp-led path** (image generation available, `buildPath: comp`): three high-fidelity comps → user approval → the approved comp becomes a *measured spec*: `comp-spec` grid and named regions (`plate`/`image`/`texture` are raster; `text`/`control`/`chrome` are code; a code region larger than 25% of the comp is refused), `font-match` (a fingerprint index of ~3,100 Google Fonts faces; reported 42% top-1 and 72% top-5 family recall at ~30px cap height), raster "plates" regenerated at ≥1.5× region size with the generation prompt embedded as provenance, a human plan-and-asset review, then a **hero gate**: `comp-diff` (SSIM over blurred grayscale with a small translation search, histogram + Lab palette match, high-frequency detail energy, section-band alignment, per region) must reach **≥72%** with no hard veto (missing region, contradicted plate or text block, SVG illustration, clipped plate, invented ink); after three failed attempts the agent shows the first viewport to the user instead of looping; then sections → motion → responsive (captures at 1440 and 390 wide; the first viewport must hold at 1280–1600, not just at the comp's width) ([IMP]/skill/reference/new-work.md §6; visualize.md; component-review.md; region-map.md; [IMP]/docs/COMP-FIDELITY.md). The skill itself warns this path needs a frontier-tier model; smaller models stall at the hero gate.
- **Code-led path**: no comp; ambition lives in the contract's FIRST VIEWPORT block plus a named signature interaction and motion grammar, and is audited in behavior at the finish.
- **Step 7 — inspect and finish**: one batched screenshot round (adding the user's real viewport width when known), critique against the request and contract, fix, one confirming round — two rounds maximum. **Capture validity** comes first: settle or disable entrance animation (content hidden by animation timing looks missing and gets "fixed" into a regression), take full-page shots from the top, open each file once and confirm it shows what its name claims. Hookless web harnesses run `impeccable detect --json` once. Then a **fresh finish-reviewer sub-agent with no inherited conversation** is spawned (the stated rationale: a reviewer that sees the build transcript inherits the builder's framing and optimism) and given the request, answers, artifact path, screenshots, contract, hook findings, quality-bar card, comp, build state, diff reports and the craft-floor path. The parent acts on exactly four dispositions: `recapture` (evidence invalid — a review of invalid evidence counts for nothing), `rebuild` (wholesale), `fix` (one batch, recapture the same files, then a **verdict pass** scoring each fix *resolved / partial / unresolved*, where the builder's own description of what it fixed does not count as evidence), `ship`. Unattended runs stop after two rounds; attended runs give the remaining table to the user. Screenshots or named mismatches supplied by the user always trigger a new full review by a fresh reviewer. The final report states the verdict at its true scope (scoring three fixes as resolved is not a claim that no issues remain). The documenter then writes DESIGN.md and the sidecar.
- **Finish-reviewer checks, in order** ([IMP]/skill/agents/impeccable-finish-reviewer.md): 0 *Evidence* — every required viewport present and valid, otherwise return only `recapture`; 1 *Persistence* — PRODUCT.md, build state, recorded approvals; 2 *Fidelity* — read the measured diff first, then build an element matrix (match / acceptable adaptation / missing / contradicted / added without approval) from **the reviewer's own inventory of the comp, written before reading the builder's contract** (anti-anchoring), with three mandatory rows: TYPE (lettering character, width, weight, contrast), MATERIAL (flat CSS or clean vector where the comp shows painted/textured/photographic material is contradicted; faked physicality such as CSS bevels is treated as the most reliable sign of machine-made design), GROUND (the page field's value and temperature, sampled from pixels; drift toward warm cream on light grounds or blue-black slate on dark is the known bias); an adaptation counts only if it cites the user answer, brief, accessibility need or product truth that required it; 3 *Ceiling* — devices of the chosen world the build left unused; 4 *Contract*, promise by promise, plus the memory test; 5 *Truth* — synthetic data labelled, no invented claims, every raster shipped and actually visible (an asset at near-zero opacity is compliance theatre); 6 *Floor* — the craft floor's refuse list checked against the screenshots. Output: the disposition line and exactly five sections (`persistence`, `fidelity`, `ceiling`, `material_fixes` ≤8 ordered, `keep`), no praise. Budget 30 turns; stop reading by about turn 10.

#### 2.1.D The craft floor (loaded right before any UI edit) and Operate-mode rules

**Verify** — checks on the built result, run together in the batched rounds ([IMP]/skill/reference/craft-floor.md):
- Contrast: body and placeholder text ≥ **4.5:1**, large text ≥ **3:1**; secondary text on a colored surface is tinted from that hue or the foreground, never gray.
- Depth: shadows have an offset and a soft blur; a zero-offset colored halo is decoration, not depth.
- Spacing: tight groups, generous separation, **more space above a heading than below it** — read computed values, don't guess.
- Type: body measure **65–75ch**, display at most **6rem**, letter-spacing no tighter than **−0.04em**, balanced headings, obvious scale and weight steps; render the real copy at every breakpoint and fix overflow.
- Motion: **one authored moment** rather than scattered effects or the same entrance on every section; exponential ease-out starting from an already-visible default; blur, backdrop-filter, clip-path, mask and shadow are legitimate materials when they stay smooth.
- States: hover, disabled, loading, error, empty — plus real content, working controls, responsive composition, keyboard focus.
- **Browser surfaces**: theme what the page author didn't draw — text selection, caret, scrollbars, focus rings, link underline offset, numerals in tabular data. The skill calls this the cheapest signal that a page was built deliberately, and the one models skip most.
- Copy: the product's own language; controls name their action; errors name the problem and the recovery.
- Coverage: every requirement in the brief is present and findable within seconds.

**Refuse** — category defaults that the brief's own words may justify, except where marked absolute: identical same-size icon+heading+text cards as the page structure (nested cards are always wrong); the hero-metric template (big number, small label, supporting stats, accent); **a kicker/eyebrow label above a heading — absolute, no brief justifies it**; section numbers (01/02/03) unless the sequence itself is information; a modal where neither interruption nor protected focus is needed; gradient text (use weight or size for emphasis); glass/blur as decoration; a colored `border-left`/`border-right` over 1px on cards, list items, callouts or alerts; hard offset shadows (`4px 4px 0`) outside a genuinely neobrutalist world; sparklines, progress rings or soft-shadowed rounded rectangles standing in for content; monospace as a costume for "technical"; a system display face (Impact, Arial Black, the platform sans) as the display voice of a custom-world page; Unicode glyphs or emoji instead of an icon system (one library, one stroke weight); geometric masks imitating organic contours; light/dark chosen by category instead of use scene. The floor fixes mechanics only and never chooses the direction; when unsure between refined and committed, it says to commit.

**Operate/Read depth** ([IMP]/skill/reference/operate.md; v3 `product.md`): the *product slop test* asks whether a category-fluent user would trust the interface immediately or hesitate at subtly-off components — in product UI the failure is purposeless strangeness, and familiarity is a feature. Rules: one family is often enough; **fixed rem type scale, not fluid** clamp() headings; scale ratio **1.125–1.2**; prose 65–75ch while tables may run 120ch+; Restrained color is the floor; standardize a state vocabulary (hover, focus, active, disabled, selected, loading, error, warning, success, info); accent only for primary actions, selection and state; a second neutral layer for sidebars/toolbars; every interactive component ships **default, hover, focus, active, disabled, loading, error**; skeletons instead of mid-content spinners; empty states that teach the interface; overlays must escape `overflow` containers (`<dialog>`, popover API, `position: fixed`, portal); transitions **150–250ms**; motion only for state; no page-load choreography. Bans: display fonts in labels/buttons/data, inconsistent component vocabulary across screens, reinvented standard affordances, saturated color on inactive states, reaching for a modal first.

#### 2.1.E The 24 commands — what each tells the agent to do

`craft` (deprecated alias of new-work) · `shape` (discovery interview, up to two rounds of 2–3 questions, then a 7-part brief: job & audience; outcome & proof; selected direction; scope & boundaries; states & realistic min/typical/max content ranges; interaction & layout intent; constraints & open decisions — never code) · `init` · `document` · `extract` (only patterns used **3+ times with the same intent**; duplication is preferred to premature abstraction; don't create a design system without asking where it should live) · `critique` · `audit` (§2.1.F) · `polish` · `bolder` · `quieter` · `distill` · `harden` · `onboard` · `animate` · `colorize` · `typeset` · `layout` · `delight` · `overdrive` · `clarify` · `adapt` · `optimize` · `live` · `generate`. Key rules:

- **polish** ([IMP]/skill/reference/polish.md): refinement only, never a disguised redesign; classify each drift as missing token / one-off implementation / conceptual mismatch / local defect and fix at the narrowest correct level; read the latest critique snapshot as a backlog (it closes automatically when the target file's content fingerprint changes); **triage order**: (1) broken or blocked tasks, data loss, misleading state, inaccessible paths → (2) missing loading/empty/error/success/disabled/permission states → (3) flow, hierarchy, responsive and design-system drift → (4) visual and motion inconsistencies → (5) code and asset cleanup; walk the path with mouse, keyboard and touch; check zoom, contrast, focus, screen-reader names, console errors, layout shift, interaction latency; end with a review of the source diff; a clean detector scan is not a substitute for looking.
- **bolder**: scope is sovereign — touch only the named target, add no colors, fonts, radii or primitives without asking; a flat section usually skips moves the rest of the system already makes, so raise it to its neighbours' level in the system's own vocabulary; making everything louder flattens the section; **skeleton test** — strip the copy and check the structure still says what the section is.
- **quieter**: Persuade/Experience keep their point of view with more air; Operate/Read reduce noise; reduce saturation to **70–85%**; step weights down (900→600, 700→500); motion distances 10–20px rather than 40px; ease-out-quart; never equalize everything, never strip all color.
- **distill**: one primary goal; 1–2 colors + neutrals; one family, **3–4 sizes, 2–3 weights**; drop cards used only for layout; halve the copy, then halve again; never remove needed functionality or accessibility; record what was removed and which user feedback to watch.
- **harden**: test extremes (100+ character names, empty, emoji, RTL, CJK, 1,000+ items, offline/slow, HTTP 400/401/403/404/429/500 each with its own handling); budget **+30–40%** text expansion for translation; logical CSS properties; `Intl` formatting and real plural rules; `min-width: 0` on flex/grid children; interrupted-gesture handling (`pointercancel`, `lostpointercapture`, window blur); prevent double submits; 16px minimum on inputs because iOS Safari zooms focused inputs below 16px; verification includes rapid repeated submits; always state what produced gesture evidence (emulation, synthesized touch, which engine, real device).
- **typeset** and **layout** both run **two isolated assessments** — a design assessment whose every answer must cite a file, selector or computed value, then `impeccable detect --scope type|layout` — and forbid letting detector output anchor the design assessment. Typeset: 16px body floor; prose 45–75ch (craft floor says 65–75ch); compensate light-on-dark text on leading, tracking and one weight step; tabular/numeric OpenType features where useful; metric-compatible fallbacks; respect zoom and Dynamic Type; use paragraph spacing or first-line indent, not both. Layout: **squint test** (with detail blurred, can you still find the primary element, the secondary, the groups?); proximity before containers; a 4-unit spacing base; `gap` for sibling rhythm; container-aware components; DOM and focus order must match visual order; every verification item needs rendered or source evidence, not a bare yes.
- **colorize**: build roles, not swatches (canvas, elevated surfaces, primary/secondary text, action/focus/selection, borders, success/warning/error/info, data scales); OKLCH for new web palettes; choose hue from product meaning, never category association; AA minimums: body **4.5:1**, large **3:1**, **controls, icons and focus indicators 3:1**; simulate color-vision deficiencies; never color alone; compose dark mode rather than inverting; lower chroma near white and black; prefer explicit colors over chains of alpha.
- **animate**: find the job (acknowledge an action, make a state or spatial change legible, keep continuity, direct attention, embody the world); durations **100–150ms feedback, 150–300ms routine state change, 300–500ms layout/overlay/view transition, 500–800ms one authored focal entrance**; exits faster than entrances; `cubic-bezier(0.16, 1, 0.3, 1)` for confident arrivals; no reflexive bounce/elastic; cap total stagger; content visible in the default state so a failed script cannot hide the page; no layout-property animation; `will-change` only during animation; **every web animation gets a `prefers-reduced-motion` alternative** that removes spatial movement but keeps meaningful feedback (this requirement disappeared from all build-time guidance in v4.0.0–v4.0.4 and had to be restored, impeccable#514).
- **delight**: one delight thesis; intensity proportional to frequency and consequence; never fake progress or delay completion for a flourish; no jokes around loss, money, privacy or blocked work; no sound without consent.
- **clarify**: verb + object labels; destructive actions name object and consequence; prefer undo to confirmation when recovery is safe; persistent labels (placeholders are only examples); errors say what failed, why (when useful) and how to recover; empty states distinguish first use, no results, filtered, no permission and failure; complete translatable strings, never concatenated fragments; alt text carries the image's information, `alt=""` for decoration; keep a terminology glossary.
- **adapt** (web): adaptation means rethinking, not scaling; 44×44px touch targets; content-driven breakpoints (it suggests three usually suffice: 640, 768, 1024px); `pointer`/`hover` media queries; `env(safe-area-inset-*)`; `srcset`/`picture`; never hide core functionality on mobile; DevTools emulation is not touch truth — exercise custom sliders and drag surfaces with synthesized touch and report which engine produced the evidence (Chromium is not Safari). **adapt.native** adds an iOS↔Android idiom translation table.
- **onboard**: get users to the first moment of real value fast, not a product tour; always skippable; tours 3–7 steps; five empty-state types (first use, user cleared, no results, no permissions, error). It is the only command that asks for validation **with real users** (time to completion, comprehension, next action taken, skip rate, completion rate, time to value).
- **overdrive**: propose 2–3 directions with trade-offs and get the user's choice before writing code; progressive enhancement mandatory; target **60fps and simplify below 50**; wow / removal / device / context tests. Its instruction to iterate over multiple rounds conflicts with the bounded-pass rule (impeccable#853, #902).
- **optimize**: measure first; Core Web Vitals **LCP < 2.5s, INP < 200ms, CLS < 0.1** (INP replaced FID in March 2024); never lazy-load above-the-fold content.
- **live / generate**: in-browser variants. The agent first writes an **identity lock** — one sentence recording the real surface/accent values, loaded fonts, layout topology, surface treatment and voice. *Default* mode (about 90% of sessions) varies expression within that identity; *departure* only on an explicit request. Three variants must each commit to a **different primary axis** among hierarchy, layout topology, typographic system, color strategy, density and structural decomposition; a squint test rejects variants that rhyme; each variant may expose 0–4 coarse parameters (CSS variables) the user can tune without regenerating ([IMP]/skill/reference/live.md §4–§7).
- **native** (ios.md / android.md, distilled from ehmo/platform-design-skills, MIT): iOS — lay out inside safe areas; tab bar for 2–5 sections (never actions); never disable edge-swipe back; **44×44pt** targets; Dynamic Type text styles, **11pt floor, body 17pt**; semantic system colors; a single tint; system materials; SF Symbols; capture from the Simulator (`xcrun simctl io booted screenshot`), include dark appearance and a large Dynamic Type size, and say whether evidence came from simulator or hardware. Android — Material 3; navigation bar with 3–5 destinations on compact width, rail or drawer on expanded; predictive Back; edge-to-edge with insets; **48×48dp targets with ≥8dp spacing**; `sp` units; Material color roles with Dynamic Color and a static fallback; tonal elevation; one FAB; snackbars for transient feedback; capture with `adb exec-out screencap`, test `cmd uimode night yes` and `font_scale 1.3`.

#### 2.1.F Evaluation protocols: critique, audit, scoring

**critique** ([IMP]/skill/reference/critique.md, 841 lines):
- **Two independent assessments run as two isolated, parallel sub-agents** whenever a sub-agent tool exists. Running them in one context is a *degraded* run, and the report's first line must then be a banner of the form `⚠️ DEGRADED: single-context (<reason>)`; a proper run starts with `Method: dual-agent (A: <id> · B: <id>)`. **Assessment A** — a design-director review: design specificity, hierarchy, IA, emotional fit, discoverability, composition, type, color, accessibility, states, copy, edge cases, cognitive load, emotional journey (peak-end rule, reassurance at high-stakes moments) and Nielsen scoring — **must be finished before any detector output enters the synthesis context**, because even deterministic output anchors judgment. **Assessment B** runs `impeccable detect --json` and, for viewable targets, injects the detector overlay into a fresh browser tab (3–5 representative pages for multi-view targets); skipping the detector fails the critique. Each assessment opens its own tab; any helper server is stopped before reporting. Codex must ask permission before spawning.
- **Synthesis**: interleave, don't concatenate; note where LLM review and detector agree, what only the detector found, and which detector hits are false positives. Report order: provenance line → Design Health Score table → **Design Specificity Verdict** (does this look authored for this product or interchangeable within its category?) → overall impression → 2–3 strengths → 3–5 **Priority Issues**, each `[P0–P3] What / Why it matters / Fix / Suggested command` → persona red flags → minor observations → provocative questions → trend line → targeted questions, placed last because text after a structured question is hidden until the user answers.
- **Nielsen scoring**: each of the 10 heuristics gets **0–4** with a rubric per heuristic (e.g. H1 runs from no feedback at all to every action confirmed and progress always visible); total /40. Heuristics 7 and 10, or any that genuinely cannot apply, may be `n/a` on Persuade/Experience surfaces, with a one-line reason and a renormalized total (e.g. 24/32 — never "/40" over a partial set). Bands **36–40 Excellent, 28–35 Good, 20–27 Acceptable, 12–19 Poor, 0–11 Critical** (by percentage: ≥90 / 70 / 50 / 30%). Calibration note: 4 means genuinely excellent, and most real interfaces land between 20 and 32.
- **Severity P0–P3**: P0 Blocking (prevents task completion), P1 Major (significant difficulty; audit adds any **WCAG AA violation**), P2 Minor (a workaround exists), P3 Polish (no real user impact). Tie-breaker for borderline cases: "Would a user contact support about this?" — if yes, at least P1.
- **Cognitive-load checklist** (8 items: single focus; chunking ≤4 items per group; grouping; visual hierarchy; one decision at a time; ≤4 visible options per decision point; no need to carry information across screens; progressive disclosure): 0–1 failures = low load, 2–3 = moderate, 4+ = high. Working memory taken as ≤4 items (citing Cowan, 2001; 5–7 is the edge, 8+ overloaded). Practical caps: one primary and 1–2 secondary actions, ≤5 top-level navigation items. Eight named violations (wall of options, memory bridge, hidden navigation, jargon barrier, visual noise floor, inconsistent pattern, multi-task demand, context switch) and the intrinsic / extraneous / germane load distinction.
- **Personas**: Alex (impatient power user), Jordan (confused first-timer), Sam (screen-reader and keyboard-only, zoom to 200%), Riley (deliberate stress tester: empty, 1,000 items, emoji/RTL input, refresh mid-flow, multiple tabs), Casey (one-handed, interrupted, slow 3G, 44×44pt targets); a selection table by interface type (e.g. dashboard → Alex + Sam; checkout → Casey, Riley, Jordan); 1–2 project-specific personas only when PRODUCT.md holds real audience data — never invented. The report must say what specifically broke for each persona.
- **Persistence and trend**: the report body and metadata (`total_score`, `max_score`, `na_heuristics`, `p0_count`, `p1_count`, a content fingerprint for local files) are saved in `.impeccable/critique/` and a five-run trend line is printed; `polish` consumes the snapshot as its backlog and closes it. `.impeccable/critique/ignore.md` suppresses known findings.
- **Close**: 2–4 questions that each reference specific findings and offer 2–3 concrete options (priority area, intended tone, scope, off-limits areas); questions may be skipped only when there were **fewer than three Priority Issues**, and then an explicit `Questions skipped: <reason>` line is required. After answers: an ordered command plan ending in `polish`, and an invitation to re-run critique to see the score move.
- **Tone**: name the exact element, explain the user impact, give concrete fixes, drop hedging openers, prioritize hard, don't soften criticism.

**audit** ([IMP]/skill/reference/audit.md): technical, code-level; it **documents and does not fix**. Five dimensions scored 0–4 — *Accessibility* (contrast below 4.5:1 or 7:1 for AAA; a `prefers-reduced-motion` alternative that keeps state changes — a blanket 0.01ms kill that removes useful feedback is itself a finding; ARIA roles/labels/states; keyboard, focus visibility, traps; semantic HTML; alt text; form labels; scale from 0 = fails WCAG A to 4 = AA fully met, approaching AAA), *Performance*, *Theming* (hard-coded colors, broken dark mode, wrong tokens), *Responsive* (fixed widths, targets under 44×44px, gestures that fail under touch — a resized viewport proves layout, not the gesture — horizontal scroll, text scaling), *Implementation Integrity* (run the detector, verify each hit in context, system drift, decorative or interchangeable structure). Total /20, bands **18–20 Excellent, 14–17 Good, 10–13 Acceptable, 6–9 Poor, 0–5 Critical**. Each issue records `[P?] name`, location (component, file, line), category, impact, WCAG/standard, recommendation, suggested command; the report adds systemic patterns and positive findings, and forbids reporting unverified false positives. **audit.native** substitutes VoiceOver/TalkBack, Dynamic Type/sp, 44pt/48dp, *Platform Conformance* and *Adaptivity*.

Design note: CLAUDE.md records a deliberate choice to keep accessibility out of build-time guidance and in `audit`, because reminders at design time make models over-cautious and produce safe, under-designed output ([IMP]/CLAUDE.md §Modes). The craft floor still verifies contrast, focus and states, and reduced motion was put back into `animate.md` after #514.

#### 2.1.G The deterministic detector (61 rules)

All rule ids, names and descriptions: [IMP]/crates/live/assets/antipatterns.json (the registry [IMP]/crates/foundation/src/registry.rs adds category, scope and severity). **"slop" category (AI tells, 32):** `side-tab`, `border-accent-on-rounded`, `overused-font`, `flat-type-hierarchy`, `gradient-text`, `ai-color-palette`, `cream-palette`, `nested-cards`, `monotonous-spacing`, `bounce-easing`, `pulsing-dot`, `blinking-cursor`, `shape-assembled-illustration`, `dark-glow`, `radial-halo`, `radial-spotlight-glow`, `marquee`, `icon-tile-stack`, `italic-serif-display`, `hero-eyebrow-chip`, `kicker-above-heading`, `numbered-section-labels`, `em-dash-overuse`, `marketing-buzzword`, `aphoristic-cadence`, `oversized-h1`, `extreme-negative-tracking`, `gpt-thin-border-wide-shadow`, `repeating-stripes-gradient`, `codex-grid-background`, `theater-slop-phrase`, `image-hover-transform`. **"quality" category (29):** `organic-clip-path`, `buried-raster`, `broken-image`, `script-error`, `content-hidden-at-rest`, `edge-flush-cards`, `text-occlusion`, `first-viewport-column-overflow`, `gray-on-color`, `low-contrast`, `layout-transition`, `line-length`, `cramped-padding`, `body-text-viewport-edge`, `tight-leading`, `skipped-heading`, `heading-rhythm`, `justified-text`, `tiny-text`, `undersized-ui-text`, `all-caps-body`, `wide-tracking`, `text-overflow`, `repeated-container-text`, `clipped-overflow-container`, `design-system-font`, `design-system-color`, `design-system-radius`, `design-system-font-size`. Severities: `script-error` and `content-hidden-at-rest` are `error`; 12 rules are `advisory` (`blinking-cursor`, `shape-assembled-illustration`, `numbered-section-labels`, `em-dash-overuse`, `design-system-color|radius|font-size`, `gpt-thin-border-wide-shadow`, `repeating-stripes-gradient`, `codex-grid-background`, `theater-slop-phrase`, `image-hover-transform`); the rest default to `warning`.

Thresholds read from source (portable as testable checks):
- `side-tab`: a non-neutral left/right border **≥2px** that is ≥2× every other side (or the others ≤1px) **with border-radius >0**, or **≥3px** without radius; a top/bottom accent ≥2px on a rounded box is `border-accent-on-rounded`; links, inputs, table cells, list items and buttons are exempt ([IMP]/crates/core/src/checks/rules.rs `check_borders`). Known miss: a dedicated stripe child `<div class="w-1 …">` (impeccable#394).
- `ai-color-palette`: heading-sized text (h1–h3 or ≥20px) with chroma ≥50 and **hue 260–310°**; purple→blue/cyan/pink Tailwind gradients; literal purple hexes `#7c3aed #8b5cf6 #a855f7 #9333ea #7e22ce #6d28d9 #6366f1 #764ba2 #667eea` in color/gradient declarations ([IMP]/crates/core/src/checks/html_patterns.rs).
- `cream-palette`: page background with min(R,G,B) ≥ **209**, R ≥ G ≥ B and R−B between **6 and 48** ([IMP]/crates/core/src/checks/measures.rs `is_cream_color`).
- `overused-font`: inter, roboto, open sans, lato, montserrat, arial, helvetica (the older monoculture) plus fraunces, instrument sans/serif, geist (sans/mono), mona sans, plus jakarta sans, space grotesk, recoleta — a code comment calls this second group the wave set by the Anthropic skill, Vercel and GitHub defaults; brand faces are allowed on their own domains (Roboto/Google, Geist/Vercel, Mona Sans/GitHub) ([IMP]/crates/foundation/src/constants.rs).
- `flat-type-hierarchy`: with ≥3 text roles among h1–h6/p/li/td/th/dd/blockquote/figcaption, every step between adjacent sizes < **1.25×**.
- `bounce-easing`: animation names containing bounce/elastic/wobble/jiggle/spring, Tailwind `animate-bounce`, or a `cubic-bezier` whose y1 or y2 lies outside **[−0.1, 1.1]** (overshoot). `layout-transition`: transitions on width/height/padding/margin or min/max sizes.
- `dark-glow`: a box/text shadow with chroma ≥30, blur >4px and **zero x/y offset**, or any colored blurred shadow on a background with relative luminance < **0.1**.
- `icon-tile-stack`: a 32–128px, near-square (aspect 0.7–1.4) tile with visible background or border, not a circle, containing an icon, sitting directly above a heading. `hero-eyebrow-chip`: an h1 ≥**48px** (outside app contexts) preceded by a 2–60 character label ≤**14px** that is uppercase with ≥1.6px tracking, or bold (≥700) in an accent color, or dash-prefixed. `italic-serif-display`: italic known serif on h1 (or h2 ≥48px). `oversized-h1`: h1 ≥**72px** with ≥**40 characters** taking ≥28% of viewport height or ≥25% of its area.
- `line-length`: **at least two rendered lines** exceeding the limit (default **80 characters**, configurable) by 5+; fix with `max-width: 65ch–75ch`. `tight-leading`: line-height < **1.3×** on non-heading text over 50 characters (recommend 1.5–1.7). `tiny-text`: body text < **12px**. `undersized-ui-text`: functional text (links, buttons, nav, labels, table cells, meta) < **11px** (non-interactive legal small print 10px); being on the DESIGN.md ramp does not exempt it. `wide-tracking`: > **0.05em** on non-uppercase body text. `extreme-negative-tracking`: ≤ **−0.05em** (the craft floor's limit is −0.04em). `all-caps-body`: uppercase over 30+ characters of non-heading text. `justified-text` without `hyphens: auto`. `body-text-viewport-edge`: body text wider than half the viewport within **16px** of its edge.
- `cramped-padding`: inside a box with a visible background or ≥2 borders, the rendered text's vertical inset is < max(**4px**, 0.3×font-size) or horizontal inset < max(**8px**, 0.5×font-size) ([IMP]/crates/core/src/browser/quality.rs).
- `monotonous-spacing`: ≥10 spacing declarations in which one value (rounded to 4px) accounts for **>60%** and there are ≤3 distinct values. `nested-cards`: a card-like element (shadow/border/radius/background, ≥50×30px, ≥10 characters of text) inside a card-like ancestor. `heading-rhythm`: two or more headings whose space above is not larger than the space below.
- `organic-clip-path`: `polygon()` with ≥10 off-grid vertices or `path()` with ≥3 curve segments. `buried-raster`: an image under a gradient wash whose stops are all ≥0.9 alpha, or an image at opacity < 0.15. `em-dash-overuse`: ≥8 em dashes at roughly one per 500 characters. `gpt-thin-border-wide-shadow`: a ≤1.5px visible border combined with a wide diffuse shadow.
- Contrast uses WCAG's large-text definition: ≥18pt (24px) or ≥14pt (18.67px) bold → 3:1, else 4.5:1.

Operation: engines = regex/text over source files, static HTML, browser (CDP; rendered DOM + computed layout), and visual contrast; exit codes 0 clean / 2 findings / 1 a target could not be scanned; ignores in `.impeccable/config.json` (`detector.ignoreRules|ignoreFiles|ignoreValues`) or inline `impeccable-disable[-line|-next-line] <rule>: reason`. **Triage policy**: fix real problems; the agent may add only *narrow value-level* ignores, with named evidence written as `<who decided: evidence>`; file- or rule-wide ignores need the user ([IMP]/skill/reference/hooks.md). The README states plainly that a clean run is evidence, not proof of visual or accessibility quality.

Documented detector gaps (open issues): `.astro/.jsx/.svelte/.vue` files silently get fewer rules than byte-identical `.html`, so zero findings can mean lost coverage (impeccable#884); only `.html/.htm` reach the DOM engine in `detect`, so contrast/a11y rules never run on Blade/Vue/Svelte there (#795); gradient+alpha backgrounds composited over black misreport 17.6:1 text as 1.2:1 (#881); closed `<details>` counted as occluders (#882); tracking misread through cross-file `var()` (#883); padding false positives from unreadable custom properties (#867); placeholder contrast was not evaluated until #790. Web only — no detector for native apps.

#### 2.1.H The historical per-domain references (v3.0.4) and what v4 changed

v4 deleted `typography.md`, `color-and-contrast.md`, `spatial-design.md`, `motion-design.md`, `interaction-design.md`, `responsive-design.md`, `ux-writing.md`, `cognitive-load.md`, `personas.md` and `heuristics-scoring.md`, and CLAUDE.md forbids bringing per-domain reference files back; their substance moved into the command references and the craft floor so it loads only when relevant ([IMP]/CLAUDE.md). The v3.0.4 versions remain the most-copied Impeccable content; their key rules:
- **v3 shared design laws** ([IMP-v3]/SKILL.md): OKLCH; lower chroma near 0 and 100 lightness; never `#000`/`#fff` and tint every neutral toward the brand hue (chroma **0.005–0.01**); the color-strategy axis (Restrained = tinted neutrals + one accent at **≤10%**); theme from a physical-scene sentence (its example: an SRE checking incident severity on a large monitor at 2am in a dim room forces dark, whereas the bare category does not); body 65–75ch; ≥1.25 ratio between type steps; vary spacing; cards are the lazy answer; no layout-property animation; ease-out quart/quint/expo, no bounce or elastic; the absolute bans (side stripes, gradient text, default glassmorphism, hero-metric template, identical card grids, modal-first); copy with no restated headings and **no em dashes**; an "AI slop test" plus a **category-reflex check** that rejects palettes guessable from the domain (its examples: observability → dark blue, healthcare → white + teal, finance → navy + gold, crypto → neon on black).
- **typography.md**: vertical rhythm on the line-height unit; a 5-size scale (0.75 / 0.875 / 1 / 1.25–1.5 / 2–4rem) with one committed ratio (1.25, 1.333 or 1.5); light text on dark gets +0.05–0.1 line-height, +0.01–0.02em tracking and optionally one weight step; paragraph spacing or indent, never both; never pair two similar-but-different families; fallback metric overrides (`size-adjust`, `ascent-override`, …; Fontaine); `font-display: swap` vs `optional` (~100ms budget); preload only the critical weight; variable fonts for 3+ weights; fluid `clamp()` only for display type on marketing/content pages and fixed rem for app UI (it notes Material, Polaris, Primer and Carbon don't use fluid type in product UI **[unverified]**); clamp max ≤ ~2.5× min; OpenType features (`tabular-nums`, `diagonal-fractions`, `all-small-caps`, no ligatures in code); `text-wrap: balance` for headings and `pretty` for prose; all-caps labels +0.05–0.12em; semantic token names; never disable zoom; rem/em rather than px. It also asserted that body text under 16px fails WCAG on mobile — **incorrect**: WCAG 2.x sets no minimum font size (v4's own `undersized-ui-text` description says so).
- **color-and-contrast.md**: OKLCH over HSL for perceptual uniformity; avoid reflexive hue-250 blue and hue-60 orange; tint neutrals 0.005–0.015 toward the *specific* brand hue; palette structure primary (3–5 shades), neutral (9–11), semantic (4 × 2–3), surface (2–3 levels); 60-30-10 as visual weight, not pixels; WCAG table incl. AAA 7:1 and 4.5:1; placeholders still need 4.5:1; dangerous pairs (gray on color, red/green, yellow on white, thin text on images); dark mode builds depth with lighter surfaces (a 3-step scale such as 15/20/25% lightness), slightly lighter body weight (~350), desaturated accents and no pure black (12–18% lightness); two token layers (primitive → semantic; dark mode remaps only semantic); heavy alpha treated as a smell.
- **spatial-design.md**: 4pt base (4, 8, 12, 16, 24, 32, 48, 64, 96); `repeat(auto-fit, minmax(280px, 1fr))`; squint test; hierarchy through 2–3 dimensions at once (size ratio ≥3:1 counts as strong); container queries for components; optical alignment (≈−0.05em text offset, play icons shifted right); 44px targets via pseudo-element expansion; a semantic z-index scale; subtle shadows.
- **motion-design.md**: 100/300/500 rule (100–150 feedback, 200–300 state, 300–500 layout, 500–800 entrance); exits ~75% of entrance duration; easing tokens ease-out-quart `(0.25,1,0.5,1)`, quint `(0.22,1,0.36,1)`, expo `(0.16,1,0.3,1)`; stagger via `calc(var(--i)*50ms)` with a cap on total delay; reduced motion is mandatory (it cites ~35% of adults over 40 with vestibular disorders — the usual source, Agrawal et al. 2009, measured vestibular *dysfunction*, so the framing is **[unverified]**); perceived performance (an ~80ms "feels instant" threshold **[unverified]**; optimistic UI for low-stakes actions only; skeletons).
- **interaction-design.md**: eight states (default, hover, focus, active, disabled, loading, error, success); never `outline: none` without a `:focus-visible` replacement; focus ring 2–3px, offset, **≥3:1** against adjacent colors; visible labels, validate on blur, errors under the field linked with `aria-describedby`; native `<dialog>`, `inert`, Popover API, CSS anchor positioning with fallbacks, portals; z-index scale dropdown 100 → sticky 200 → backdrop 300 → modal 400 → toast 500 → tooltip 600; **undo rather than confirm** except for truly irreversible, high-cost or batch actions; roving tabindex; skip links; every gesture needs a visible alternative.
- **ux-writing.md**: no "OK/Submit/Yes/No" — verb + object ("Save changes", "Delete message", "Keep editing"); error formula what happened / why / how to fix, with templates; never blame the user; empty state = acknowledge, explain value, give an action; constant voice, adaptive tone; no humor in errors; standalone link text; translation expansion (German +30%, French +20%, Finnish +30–40%; it claims Chinese uses ~30% fewer characters at similar width **[unverified]**); keep numbers out of sentences; one term per concept (Delete, Settings, Sign in, Create).
- **brand.md** (v3 brand register): font procedure — write three physical-object voice words, list your three reflex fonts and reject any on the reflex list, browse a real foundry catalog with the words in mind, then cross-check that the pick didn't drift back to the reflex; name a concrete real-world reference before choosing a color strategy (unnamed ambition drifts to beige); ship imagery whenever the brief implies it (restaurants, hotels, travel, fashion…), searching for the brand's physical object rather than the category; vary across projects; editorial-magazine styling is one lane, not the default.

#### 2.1.I Evidence of effectiveness (what Impeccable itself measured)

- **A private A/B eval framework** runs the same brief with and without the skill; no results are public ([IMP]/CLAUDE.md §Evals Framework). The public docs and the Neo Mirai case study report **no quantitative outcomes** (checked 2026-10-01).
- **Comp-fidelity sweeps** ([IMP]/docs/COMP-FIDELITY.md, August 2026; n = 2–3 per cell; the documented sweeps alone cost on the order of $300 in API spend): when the phased machine (spec → plates → hero gate) actually ran, it beat the one-pass build on every niche and both models on `comp-diff` against the approved comp — e.g. GPT-5.6-sol: album 53–56% → 66–77%, moto forum 46–47% → 62–64%, analytics dashboard 61–66% → 71–72% — at **2–4× the turns and cost** (Opus branch samples $9–15 each; runs of 150–160 turns). A human review with 230 pins (section header says 32 builds; its verdict table lists 4 pass, 1 pass-except-one-bug, 10 unsure, 27 fail) put the human pass line at about **68–73% comp-diff**; recurring pin types (wrong font size/weight, hallucinated kickers/dividers/buttons, SVG instead of the painted asset, clipped shapes, tall nav strips) were then turned into numeric hero readings. The document's root diagnosis — the earlier build depended on "the model judging its own reproduction from memory of an image" — is the single most relevant lesson for UI-Evaluator: replace model self-assessment of visual output with measurement wherever possible. It also observes that code-led builds only appeared better because they had no target to fail against, and that weaker models declared work done over failing gates (a compliance problem, not a capability problem).
- **Skill-behavior tests** check tool-call traces rather than prose, across at least two model families because cross-family disagreement surfaces the most skill-text defects; ~$0.50–1.50 per sweep ([IMP]/CLAUDE.md §Skill-behavior tests).
- **Third-party measurement (impeccable#744)**, pinned suites of 120 attempts per permission mode (480 attempts across the reported runs): activation precision 100% (N=28, 95% CI 88–100%) with zero false positives over 70 negatives; but a request phrased like `document` triggered the skill **0/10** times while the base model wrote its own DESIGN.md in 10/10, never opening `document.md`; in v4.2.1 **0 of 35 reference files** were opened across 28 activations and `craft-floor.md` was read before a UI edit in only **6/29 (21%)** of runs, rising to **16/30 (53%)** in v4.2.2 after a launcher fix; under `acceptEdits`, 55/55 launcher calls were refused. Prose that relies on the model choosing to open a reference file is often simply not read.

#### 2.1.J Known limitations (issues, docs, my reading)

1. **Weight and cost**: ~390 KB of reference prose in 38 files (≈65k words including SKILL.md and agents) at v4.4.0 (35 files / 353 KB at v4.2.1 per #744); comp-led builds take 100–160 turns and roughly $9–25 per run in the authors' own evals; described by its author as needing frontier models.
2. **References frequently unread** (#744); the always-loaded description is ~120 words (#375); quality depends on the launcher being permitted to run.
3. **Prompt-register issues on literal-following models**: a booster preamble telling the model its earlier work was timid, nine `**CRITICAL**`/`**IMPORTANT**` banners, and overdrive's iterate-many-rounds rule contradict the bounded-pass principle (#853, #902).
4. **Internal inconsistencies**: measure 45–75ch (typeset) vs 65–75ch (craft floor, operate); tracking limit −0.04em (floor) vs −0.05em (detector); v3's always-tint-neutrals rule vs v4 colorize's acceptance of neutral gray (the project's own DESIGN.md uses zero-chroma text tokens); the craft floor's instruction to theme scrollbars vs operate.md's ban on reinventing affordances such as custom scrollbars; the README's short anti-pattern list still says to always tint.
5. **Accessibility deliberately pushed to the end**; reduced motion vanished from build guidance for five releases (#514); the project's own site was reported for contrast failures (#387). Coverage is partial (contrast, headings, ARIA hints, target size) with no mapping to WCAG 2.2 success criteria (e.g. 2.4.11 Focus Not Obscured, 2.5.8 Target Size (Minimum) 24×24 CSS px, 3.3.7 Redundant Entry, 3.3.8 Accessible Authentication) and no screen-reader test protocol.
6. **No empirical user-research loop**: personas are synthetic archetypes; nothing ingests real user feedback, analytics, support tickets or usability-test notes; no task-based testing, think-aloud, cognitive walkthrough or A/B methodology. Its "Nielsen 0–4 per heuristic" is a convenience score, not Nielsen's per-*problem* severity rating (0–4 from frequency, impact and persistence), and it comes from one LLM rather than 3–5 independent evaluators followed by aggregation — the dual sub-agent split separates design review from detector evidence, not two independent heuristic evaluators.
7. **CJK and non-Latin typography essentially absent**: `harden.md` only says to test with CJK; v3 made a questionable claim about Chinese character counts; nothing on CJK font stacks, line-height for ideographs, `word-break`/`line-break`, `text-autospace`, punctuation trimming, vertical writing or Han–Latin mixing; the font fingerprint index is Latin-only; the live overlay submits mid-IME-composition (#856).
8. **Closed components**: the catalog, roll service, evals and site are private; offline the roll has no challengers.
9. **Detector coverage gaps and false positives** (§2.1.G); web only.
10. **Supply chain**: unverified binary download (#813); hooks run outside the model's permission layer (#744; README).

#### 2.1.K Strengths, weaknesses, what UI-Evaluator should adopt

**Strengths.** (1) The most complete public catalogue of *named, testable* AI-UI tells, with source-level thresholds and per-model calibration blocks. (2) A real anti-convergence *mechanism* (seeded dice over the model's own ranked list, human-curated challengers, an always-available exit to convention) rather than exhortation. (3) Clean context architecture: product truth vs visual system vs per-surface strategy, and interview rules that forbid inventing facts. (4) Evaluation hygiene that matches HCI practice: independent assessments, anti-anchoring order, mandatory disclosure of degraded runs, a severity scale with a tie-breaker, evidence-validity checks, verdict passes per fix, and user evidence that reopens review. (5) Measurement where models are weak (comp-diff, font fingerprints, numeric hero readings), calibrated against human review. (6) A one-source, many-harness build with provider-specific blocks. (7) Candour about limits (clean scans are not proof).

**Weaknesses for our purpose.** Thin usability rigor (no real-user evidence, synthetic personas, no cognitive walkthrough, single-evaluator heuristic scores); accessibility de-emphasized at build time; no CJK; heavy prompt and cost footprint; private dependencies; several internal contradictions; some unsourced or wrong claims (16px "WCAG" rule, 80ms, 35% vestibular).

**Adopt:** see §4 (IMP-001 … IMP-062; most rows trace to Impeccable).

The PR bodies give almost no rationale (v3: frame the task as a design lead, list default looks to avoid, ask for deliberate palette/type/layout choices).

**v1 (Nov 2025) — the famous version.** Before coding, settle Purpose, Tone (pick an *extreme* from a menu: brutally minimal, maximalist chaos, retro-futuristic, organic, luxury, playful/toy-like, editorial, brutalist, art deco, soft/pastel, industrial…), Constraints and Differentiation (the one unforgettable thing); intentionality matters more than intensity. Aesthetics: characterful fonts — avoid Arial/Inter, pair a distinctive display face with a refined body face; commit to a cohesive palette via CSS variables, dominant colors with sharp accents beat timid evenly-spread palettes; motion via CSS (Motion library in React), favour one orchestrated page load with staggered `animation-delay` reveals, plus surprising scroll and hover effects; unexpected composition (asymmetry, overlap, diagonal flow, grid-breaking); atmospheric backgrounds (gradient meshes, noise textures, geometric patterns, layered transparencies, dramatic shadows, decorative borders, custom cursors, grain). Never: overused fonts (Inter, Roboto, Arial, system fonts), purple gradients on white, predictable layouts, cookie-cutter design; vary light/dark, fonts and aesthetics between generations and never converge (it names Space Grotesk); match implementation complexity to the vision. No accessibility, usability or evaluation content at all.

**v2 (Jun 2026).** Reframed as the design lead of a small studio whose client rejected templated proposals; one justified aesthetic risk. *Ground it in the subject*: if the brief doesn't say what the product is, name one concrete subject, its audience and the page's single job, and state the choice; distinctive choices come from the subject's own world (materials, instruments, artifacts, vernacular); use memory of the person's preferences and earlier designs as a hint. *Principles*: the hero is a thesis — open with the most characteristic thing in the subject's world (headline, image, animation, live demo, interaction); the big-number + small-label + stats + gradient hero is the template answer; pair display and body faces deliberately with a clear scale; structure is information — numbering/eyebrows/dividers/labels must encode something true (01/02/03 only for real sequences); motion deliberately, an orchestrated moment beats scattered effects, and extra animation itself reads as AI-generated; match complexity to vision; copy can feel as templated as layout. *Calibration*: three generated looks — warm cream background (near `#F4F1EA`) + high-contrast serif display + terracotta accent; near-black + single acid-green or vermilion accent; broadsheet layout with hairline rules, zero radius, dense columns — legitimate for some briefs but defaults rather than choices; the brief's own words always win. *Process*: two passes — (1) a compact token plan: palette as 4–6 named hex values, typefaces for 2+ roles (a characterful display face used with restraint, a complementary body face, an optional utility face for captions/data), a layout concept with one-sentence descriptions and **ASCII wireframes** to compare options, and one *signature* element; (2) review the plan against the brief — if any part is what you'd produce for any similar page (test by imagining a similar prompt), revise it and say what changed and why; only then code, deriving every color and type decision from the plan. Watch CSS specificity collisions (e.g. `.section` vs `.cta` padding). Do most planning in thinking; show the user ideas only when confident. *Restraint and self-critique*: spend boldness in one place; not taking a risk is a risk; quality floor without announcing it (responsive to mobile, visible keyboard focus, reduced motion respected); critique your own work with screenshots where possible; before finishing, take away one accessory (a check the skill attributes to Chanel); keep notes of what was tried for future passes. *Writing*: words exist to make the interface easier to understand and use; write from the user's side of the screen (users manage notifications, not webhook config); active voice; controls say exactly what happens ("Save changes", not "Submit"); an action keeps its name through the flow ("Publish" → toast "Published"); errors explain what went wrong and how to fix it, never apologize, never vague; empty screens invite action; conversational, plain verbs, sentence case, no filler; each element does exactly one job.

**v3 (Sep 2026, current) — changes from v2.** Typography: one family or two (if two, clearly distinct); choose faces deliberately, not your default families; set the scale following the default guidance of Bringhurst's *The Elements of Typographic Style*; use type treatment as an active design element; **line length under 80 characters** by default, serif body may run slightly longer and gets slightly more leading than sans. Three default typographic treatments named as the commonest tells: accenting a single word in a headline (italic/bold/color), all-caps labels, unnecessary typographic labels above content. Motion: non-user-triggered motion only sparingly to draw attention; fade-and-slide-up entrances on each section and hover transitions on every card are named as generic AI defaults; motion that answers a user action is welcome when it shows what changed. Calibration expanded to **five clusters**: (1) cream `#F4F1EA`-ish + high-contrast serif + terracotta/clay accent "often near `#D97757`" — explicitly identified as Anthropic's own Claude-interface accent and therefore a tell on a user's brief; (2) near-black + one acid-green/vermilion accent; (3) broadsheet hairlines, zero radius, newspaper columns; (4) the **SaaS-card kit** — identical rounded cards, one radius everywhere, the same soft grey shadow `rgba(0,0,0,.1)`, decorative gradient washes; (5) **template chrome** — tracked ALL-CAPS eyebrow above every heading, meta strings joined with middle dots, labels like "WORD — fragment" with a spaced em dash, tinted near-black (`#0B0B0B`, `#111`) used as black, monospace for small data labels, a `→` appended to link/button text. The token plan changes "signature" to "principles" and adds alignment guidance (left / center / justified) to the layout concept. The quality floor adds visual accessibility and harmonious palettes. The advice to keep notes of what was tried remains.

**Strengths.** Short (~9 KB, ~1,400 words), always-loadable; strong on *why* (convergence on defaults), subject grounding, plan-then-review against the brief, restraint, writing; explicitly names its own lab's house style as a tell; tracks newer model defaults over time.

**Weaknesses / gaps.** No evaluation protocol, scoring, severity, or report format; self-critique happens inside the generating thread (Anthropic's own engineering post shows self-grading is biased — §2.3); no detector or measurable thresholds beyond <80 characters; accessibility is a one-line floor; no product/app (Operate) guidance — everything is framed as distinctive visual identity, which can conflict with familiarity in tools; no user research or feedback loop; no i18n/CJK; v1's still-widely-copied advice (atmospheric gradient meshes, grain, noise, custom cursors, scroll/hover surprises, a distinctive display face paired with a refined body face) is now contradicted by v3 and by Impeccable.

**Adopt.** Subject grounding; the token-plan + ASCII-wireframe + same-for-any-similar-prompt review step; restraint (one signature element; remove one accessory); structure as information; the five-cluster calibration list (merged with Impeccable's); the writing rules; the rule that the brief's own words override every default.

### 2.3 Anthropic engineering & product blog posts

**(a) "Improving frontend design through Skills"** — claude.com blog, **2025-11-12**, by Anthropic's Applied AI team (Prithvi Rajasekaran, Justin Wei, Alexander Bricken; with Molly Vorwerck, Ryan Whitehead). https://claude.com/blog/improving-frontend-design-through-skills (page text downloaded and read in full).
- **Diagnosis — distributional convergence**: sampling follows the statistical center of training data; "Safe design choices–those that work universally and offend no one–dominate web training data." Without direction the model lands on Inter, purple gradients on white and minimal animation, which makes AI interfaces immediately recognizable and dismissible.
- **Claude is highly steerable** (telling it to avoid Inter/Roboto or to use atmospheric backgrounds helps immediately), but putting all design guidance in the system prompt taxes every unrelated request; **Skills** solve this by loading specialized context on demand via file reads (progressive disclosure), keeping context lean because too many tokens degrade performance.
- **Method**: think like a frontend engineer — map aesthetic improvements to implementable code; target typography, motion, backgrounds and themes; prompt at the "right altitude" (per Anthropic's context-engineering post, https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents, 2025-09-29: between brittle hard-coded logic such as exact hex codes and vague guidance that assumes shared context).
- **Typography prompt** (`<use_interesting_fonts>`): never Inter, Roboto, Open Sans, Lato or default system fonts; example "impactful" choices — code aesthetic: JetBrains Mono, Fira Code, Space Grotesk; editorial: Playfair Display, Crimson Pro; technical: IBM Plex family, Source Sans 3; distinctive: Bricolage Grotesque, Newsreader; pairing for high contrast (display + mono, serif + geometric sans, a variable font across weights); **extremes: weights 100/200 vs 800/900, size jumps of 3× or more rather than 1.5×**; one distinctive font used decisively, loaded from Google Fonts. They observed that the font mandate improved other aspects of the design too.
- **Theme prompt** (`<always_use_rpg_theme>`): lock a named aesthetic (palette, ornate borders, parchment textures, medieval serif).
- **General ~400-token prompt** (`<frontend_aesthetics>`): (1) tell the model it tends toward on-distribution output; (2) focus areas — typography; color & theme (CSS variables, dominant color + sharp accents, inspiration from IDE themes and cultural aesthetics); motion (CSS-only for HTML, Motion for React, one orchestrated staggered page load); backgrounds (layered CSS gradients, geometric patterns, contextual effects instead of solid colors); (3) explicit avoid-list; (4) a closing reminder against converging on a *new* local maximum (Space Grotesk named).
- **Results**: three qualitative before/after pairs (SaaS landing, blog, admin dashboard) — **no metrics, no sample sizes, no user study**. A second skill, `web-artifacts-builder`, scaffolds React + Tailwind + shadcn/ui and bundles to one HTML file with Parcel; shown with qualitative examples (whiteboard, task manager).
- **Generalization**: identify convergent defaults → provide concrete alternatives → write guidance at the right altitude → package it as a reusable Skill.

**(b) "Harness design for long-running application development"** — Anthropic Engineering, **2026-03-24**, Prithvi Rajasekaran. https://www.anthropic.com/engineering/harness-design-long-running-apps (read in full).
- **Self-evaluation is unreliable**: asked to grade their own work, agents praise it confidently even when it is obviously mediocre — worst on subjective tasks like design; the post says agents "reliably skew positive when grading their own work". Separating generator and evaluator is the lever; the evaluator is still lenient toward LLM output, but tuning a standalone evaluator to be skeptical is far more tractable than making a generator self-critical.
- **Making taste gradable** — four criteria given to both generator and evaluator: **Design quality** (coherent whole; colors, type, layout, imagery combine into a distinct mood and identity), **Originality** (evidence of custom decisions vs template layouts, library defaults, AI patterns such as purple gradients over white cards; unmodified stock components fail), **Craft** (type hierarchy, spacing consistency, color harmony, contrast ratios — a competence check), **Functionality** (users understand the interface, find primary actions, complete tasks without guessing). Design quality and originality were weighted higher because the model already did fine on craft and functionality.
- **Calibration**: few-shot examples with detailed score breakdowns aligned the evaluator to the author's taste and reduced score drift across iterations.
- **Loop**: generator → evaluator with Playwright MCP navigating the live page (not a static screenshot) → written critique → generator decides to refine or pivot; 5–15 iterations, runs up to 4 hours; scores improved then plateaued; progress was not monotonic (a middle iteration was sometimes preferred); complexity grew across rounds; even iteration 1 beat an unprompted baseline. **Criterion wording steers output**: a criterion phrase praising museum-grade work pushed designs toward one particular look. Example: a Dutch art-museum site that, at iteration 10, abandoned a polished dark landing page for a CSS-perspective 3D gallery with doorway navigation.
- **Full-stack extension** (planner → generator → evaluator): the planner expands a 1–4 sentence prompt into a product spec (and was given the frontend-design skill to define a visual language); generator and evaluator negotiate a **sprint contract** (what "done" means and how it will be verified) before code; the evaluator clicks through the running app with Playwright, files bugs with file/line-level diagnoses, and each criterion (product depth, functionality, visual design, code quality) has a **hard threshold**; Sprint 3 alone had 27 criteria. Out of the box Claude was a poor QA agent — it found real issues then argued itself into approving, and tested superficially; the fix was reading evaluator logs, finding divergences from human judgment and updating its prompt over several rounds. Cost: solo run 20 min / $9 vs full harness 6 h / $200; a simplified V2 harness built a DAW in 3 h 50 min / $124.70. **Every harness component encodes an assumption about what the model cannot do**; remove components one at a time when models improve; the evaluator is worth it only where the task sits beyond what the model does reliably solo.

**(c) "Demystifying evals for AI agents"** — Anthropic Engineering, **2026-01-09**. https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents (grep-read for grader guidance). Relevant rules: a good task is one where two domain experts would independently reach the same pass/fail verdict; vague rubrics produce inconsistent judgments; LLM-as-judge graders must be calibrated against human experts; give the judge an explicit "Unknown" way out; grade each dimension with an **isolated** LLM judge rather than one judge for everything; report pass@k vs pass^k depending on whether one success or consistency matters; combine automated evals, production monitoring, A/B tests, user feedback, transcript review and periodic systematic human studies (used to calibrate graders).

**(d) Third-party evaluation of v1 (context only, not Anthropic)** — Justin Wetch, "Teaching Claude to Design Better", 2026-01-05, https://www.justinwetch.com/blog/improvingclaudefrontend/ (via WebFetch summary). Points out that v1's instruction never to converge across generations is impossible to follow because each conversation starts without memory; a rewrite (positive "instead" alternatives, concrete type/color guidance) won 21 of 28 decisive pairwise comparisons over 50 prompts across Haiku/Sonnet/Opus (p≈0.0125) — but the judge was Claude Opus 4.5, not humans **[unverified; LLM-judged]**. Anthropic's v2/v3 replaced the impossible instruction with advice to keep notes of past attempts.

Notably, the cookbook's own Jupyter display helper uses `#667eea` (a purple Impeccable's detector lists as an AI-palette hex) — trivia, but a reminder of how ubiquitous these defaults are.

**(b) Claude Platform Docs — "Prompting best practices"**, https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices (fetched 2026-10-01). The *Frontend design* section says Claude Opus 4.5/4.6 build strong frontends but default to generic patterns without guidance, points to the blog, mentions **Claude Design** (a canvas product for interactive design work), and reprints the ~400-token `<frontend_aesthetics>` snippet. Migration advice: explicitly ask for more relevant features and interactions and request animations explicitly. General advice relevant to skill writing: newer models are more responsive to system prompts, so all-caps CRITICAL/MUST phrasing should be dialled back to plain instructions; giving Claude a **crop/zoom tool** gives consistent uplift on image evaluation tasks.

**(c) Model-specific prompting pages** (fetched 2026-10-01) — the most concrete Anthropic evidence on *current* defaults:
- **Claude Opus 4.8** (https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-4-8, §Design and frontend defaults): a persistent house style — warm cream/off-white backgrounds (~`#F4F1EA`), serif display type (Georgia, Fraunces, Playfair), italic word accents, terracotta/amber accent; good for editorial/hospitality/portfolio, wrong for dashboards, dev tools, fintech, healthcare, enterprise; appears in slides and web UIs. Generic instructions (banning one color, or asking for a clean minimal look) move the model to *another fixed palette* rather than producing variety. Two reliable approaches: **(1) specify a concrete alternative** (a worked spec with palette hexes, 4px radius everywhere, type character, section structure, 160ms ease-out hovers), or **(2) propose options before building** — e.g. 4 distinct directions, each as background hex / accent hex / typeface plus a one-line rationale, user picks one, implement only that (recommended over relying on temperature). Opus 4.8 needs less anti-slop prompting; a one-paragraph `<frontend_aesthetics>` snippet suffices (now also naming purple gradients on *dark* backgrounds).
- **Claude Sonnet 5** (…/prompting-claude-sonnet-5): same pattern and the same two remedies; `temperature`/`top_k` are rejected by the API, so proposing options is *the* recommended route to variety.
- **Claude Opus 5.5** (…/prompting-claude-opus-5-5, §Frontend design defaults): without direction it falls back on a few default styles, and a general instruction to avoid a generic AI look "mostly swaps one default for another"; it responds well to **naming specific patterns to avoid** — the example excludes cream/off-white backgrounds, italic accent words in headlines, numbered 01/02/03 section labels, monospace labels and pill-shaped buttons — and the docs advise working iteratively: check which styles the first result used instead and extend the list.
- **Claude Fable 5** (…/prompting-claude-fable-5): no frontend section, but a relevant verification rule — on long runs, instruct the model to audit each progress claim against a tool result from the session and to report only what it can point to evidence for (Anthropic reports this nearly eliminated fabricated status reports in its testing).

**Strengths of the Anthropic guidance overall.** Clear causal story; small, cheap prompts; honest, model-versioned descriptions of each model's house style; two practical variety mechanisms (concrete spec; propose-then-pick); a published generator/evaluator method with gradable criteria and the self-evaluation-bias finding.
**Weaknesses.** Before/after anecdotes rather than measurements (except the harness post's qualitative logs and costs); early advice (specific "good" fonts, atmospheric gradients/noise, motion everywhere) became the next monoculture and is still reprinted in the docs snippet; no accessibility or usability methodology beyond a one-line floor and the "Functionality" criterion; no user-feedback ingestion.

### 3.2 Consensus (both sources, independently)

1. **Generic output is a default, not a lack of ability**; naming defaults and grounding in the subject's own world reliably moves output ([IMP]/new-work.md; Anthropic blog; skill v2/v3).
2. **The brief always wins**: pinned aesthetics override any slop warning ([IMP]/skill/SKILL.src.md §How to design; skill v2/v3).
3. **Shared list of generated looks**: cream ground + high-contrast serif + terracotta; near-black + single neon/acid accent; broadsheet editorial with hairlines; plus SaaS card kit and template chrome (Anthropic v3) which map onto Impeccable's detector rules (`nested-cards`, `icon-tile-stack`, `gpt-thin-border-wide-shadow`, `kicker-above-heading`, `hero-eyebrow-chip`, `em-dash-overuse`). Anthropic's model docs confirm Opus 4.8's house style is exactly cluster (a) and Opus 5.5 adds italic accent words, 01/02/03 labels, mono labels and pill buttons.
4. **Structure must carry information**: numbered markers only for sequences; eyebrows/kickers/labels above headings are tells (Impeccable makes the kicker an absolute ban; Anthropic names needless typographic labels above content and all-caps labels).
5. **The hero/first viewport is a thesis**; the big-number hero-metric template is the default to avoid.
6. **Restraint and focus**: one signature move / one authored motion moment; per-section fade-ups and hover effects on every card read as generated.
7. **Plan before code** (token plan / direction contract) and **check the plan against the generic answer** before building.
8. **UX writing**: verb+object controls, consistent action names, errors that say what went wrong and how to fix it, empty states that lead to action, plain sentence-case language.
9. **A quality floor** of responsive layout, visible focus and reduced motion.
10. **Self-assessment of visual output is unreliable**: Anthropic's harness post (self-grading skews positive) and Impeccable's comp-fidelity work (models judging reproductions from memory) reach the same conclusion and both answer it with a separate evaluator and/or measurement.

### 3.4 Gaps neither source covers (to fill from other research streams)

- **Real-user evidence**: no ingestion of user feedback, analytics, session recordings, support tickets or usability-test notes; no task-based usability test plans, think-aloud protocols, SUS/UMUX/SEQ, success/time-on-task metrics, A/B test design, or the objectives → tasks → data → analysis chain (CMU lecture). Personas are synthetic.
- **Heuristic-evaluation rigor**: no multiple independent evaluators with consensus/debrief, no "one listing per violation" rule, no ≥2-pass procedure, no per-problem severity from frequency × impact × persistence, no ease-of-fix field; Impeccable's Nielsen score is per heuristic, not per problem.
- **Cognitive walkthrough**: absent (no task + action-sequence + four-question protocol).
- **Accessibility depth**: no WCAG 2.2 success-criterion mapping (e.g. 1.4.10 Reflow at 320 CSS px, 1.4.12 Text Spacing overrides, 2.4.11 Focus Not Obscured, 2.5.7 Dragging Movements, 2.5.8 Target Size 24×24 CSS px, 3.3.7 Redundant Entry, 3.3.8 Accessible Authentication — https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/), no screen-reader walkthrough procedure, no automated axe-core integration in either.
- **CJK/i18n typography**: no CJK font stacks, ideograph line-height, `line-break`/`word-break`, punctuation compression/`text-spacing-trim`, `text-autospace`, mixed Han–Latin rhythm, vertical text, IME-safe input handling (Impeccable's own overlay fails it, #856). WCAG notes large-text thresholds have CJK equivalents (https://www.w3.org/TR/WCAG22/, definition of "large scale"), so contrast checks need CJK-aware sizing.
- **Data visualization**, **forms at scale**, **dark patterns/ethics**, **performance budgets for generated pages**: only touched (colorize data scales; optimize CWV).
- **Operate-mode distinctiveness evidence**: neither shows that "distinctive" designs keep task performance on tools; Anthropic's harness "Functionality" criterion is the only guard.

## 5. Open questions / things to verify later

1. **Licenses**: checked on 2026-10-01 — `google-labs-code/design.md` is Apache-2.0 (28k★; the spec builds on the W3C Design Tokens format and also allows an `omitted` list of sections), `ehmo/typecraft-guide-skill` and `ehmo/platform-design-skills` are MIT (the latter also packages WCAG 2.2 rules — worth reading by the accessibility stream). Still open: Anthropic blog/docs prose carries no explicit open license (treat as cite-only).
2. **Unverified numbers inside Impeccable**: Cowan (2001) as the basis for "≤4 options per decision point" (the paper concerns working-memory capacity, not menu sizes); the ~80ms "instant" threshold; the claim that roughly 35% of adults over 40 have vestibular disorders (likely Agrawal et al., 2009, which measured vestibular dysfunction); the claim that Material, Polaris, Primer and Carbon never use fluid type in product UI; v3's "Chinese −30% characters". Verify against primary sources before adopting any of them as rules.
3. **Does build-time accessibility guidance make models timid?** Impeccable asserts it (CLAUDE.md) but publishes no data, and its removal of reduced-motion guidance caused regressions (#514). We should A/B a short a11y floor in our own evals and measure both distinctiveness and WCAG failures.
4. **Is the "roll" better for users?** Forcing rank 3…n of the model's own list is a clever anti-mode-collapse device, but there is no public evidence that it improves user-rated quality or task success versus showing the top candidates; Impeccable itself allows the familiar option. Needs our own human-rated comparison.
5. **Generalization of comp-diff thresholds**: the 72% hero gate and the 68–73% human pass line come from three niches with n=2–3 and one primary reviewer; calibrate on our own set before using as a gate.
6. **Two-isolated-assessment critique**: no published evidence that it raises agreement with expert evaluators compared with a single pass; measure inter-rater agreement (LLM vs LLM, LLM vs human) when we implement it, and compare with the lecture's 3–5 independent evaluators + consensus procedure.
7. **Severity mapping**: our proposed P0–P3 ↔ Nielsen 4/3/2/1 mapping must be checked against the CMU lecture's definition (severity from frequency, impact, persistence) and NN/g's published scale.
8. **Detector false-positive/negative rates** are unknown (open bugs #881–#884, #795, #867, #394). If we port rules, build our own fixture corpus with should-flag/should-pass pairs and report coverage per file type.
9. **Local-maximum shift**: both sources saw bans push models to the *next* default (Space Grotesk after Inter; a different fixed palette after banning cream). We need a recurring measurement of what current models default to, per model version, to keep reflex lists current (Opus 5.5 and later).
10. **CJK typography** is a complete gap in both sources: needs its own research (e.g. W3C *Requirements for Chinese Text Layout* clreq, https://www.w3.org/TR/clreq/; Japanese jlreq; CSS `text-autospace`, `text-spacing-trim`, `line-break`, `word-break`; CJK font stacks; ideograph line-height and measure in characters; WCAG large-text CJK equivalence; IME-safe Enter handling as in impeccable#856). Assign to the typography/i18n research stream.
11. **Empirical loop**: neither source ingests real user feedback, analytics or usability-test results; the framework's "feedback → prioritized fix → verification" loop must come from the HCI/empirical research streams (think-aloud, task success/time, SUS, A/B design).
12. **Cost budgets**: Impeccable's comp-led builds cost $9–25 per run and Anthropic's harness runs $124–200; decide what verification depth UI-Evaluator can afford per command and expose it as an explicit budget.
13. **Impeccable moves fast** (4.0 → 4.4 in ten weeks; detector counts and rules change) — re-check rule ids/thresholds before porting, and pin to a commit in our NOTICE.
