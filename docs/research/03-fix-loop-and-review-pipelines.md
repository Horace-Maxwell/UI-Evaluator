## 1. Scope and method

### 1.1 Scope

This note covers the *mechanics* of closed UI improvement loops — how existing agent skills audit a UI, turn findings into fixes, and re-verify — not the design doctrine itself (typography, colour, anti-"AI slop" rules), which other notes cover. For each source the questions were:

1. phases and their order;
2. evaluator roles and their independence;
3. evidence capture (screenshots, DOM / accessibility tree, selectors, file:line);
4. severity / priority scales and scoring formulas;
5. finding and report schemas;
6. how fixes are scoped (one at a time vs batched);
7. commit and revert policy;
8. regression detection;
9. stopping criteria;
10. how false positives and "fixing what isn't broken" are avoided;
11. failure modes reported in issues and READMEs.

The note also maps these mechanics onto the CMU lecture *Evaluation: Analytical vs Empirical*. That lecture covers heuristic evaluation (≥2 passes, 3–5 independent evaluators, consensus, severity 0–4 from frequency/impact/persistence, and ease-of-fix), cognitive walkthrough, and empirical methods. NN/g primary pages were checked for its numbers.

#### 2.1.1 `/design-review` — "Design Audit → Fix → Verify" (the reference loop)

**Phase order (design-review/SKILL.md.tmpl):**

| # | Phase | Key mechanics |
|---|---|---|
| Setup | Parse target URL / scope / depth (`--quick` = homepage+2, standard = 5–8 pages, `--deep` = 10–15). No URL on a feature branch → **diff-aware mode** (map `git diff <base>...HEAD` to routes, audit only affected pages). | Reads `DESIGN.md` first; deviations from the project's own system are **higher severity**. If DESIGN.md has YAML front-matter tokens, *a value present in the token map is never a finding* and a finding that departs from a token must name the token. |
| Setup | **Clean working tree required** (`git status --porcelain`); if dirty, ask commit / stash / abort — because each fix must be its own atomic commit. | |
| Setup | Browser probe (Aside real browser → fallback headless `$B`), test-framework bootstrap, optional mockup generator (`$D`), optional deterministic **detector** (impeccable engine, 61 rules) | Each run gets a `REPORT_DIR` and `RUN_ID`; DOM dumps are written per run and deleted after Phase 9 unless `--keep-dom`. |
| 0 | **Mechanical scan** (only if detector installed): DOM mode for a URL (dump rendered DOM per page, scan once after last page) or source mode for diff-aware (scan changed files vs base branch). | Each rule = **one** `FINDING-NNN [rule-id]` with a location list, never one finding per hit. *A detector hit is evidence, not a verdict*: it must be confirmed in the rendered page, dropped if DESIGN.md tokens bless it, and advisory rows never pad the report. |
| 1 | **First impression** (full-page desktop screenshot; a structured gut reaction: what the site communicates, what stands out, the first three things the eye lands on — checked against what the designer intended — and a one-word verdict; plus a page-area test: any area whose purpose cannot be named within about 2 s is poorly defined). | Narrated in first person; the skill treats any observation that cannot name a specific element as a platitude. |
| 2 | **Design-system extraction from the rendered page** (computed `fontFamily`, colors, heading sizes/weights, touch targets <44 px, navigation timing; capped at 500 elements). | Flags: >3 font families, >12 non-gray colors, skipped heading levels, off-scale spacing. Offers to save as DESIGN.md. |
| 3 | **Page-by-page audit**: console-error hook injected *before* navigation, interactive accessibility snapshot, annotated screenshot, responsive captures at 375×812 / 768×1024 / 1440×900, DOM dump. Trunk test on every page (6 questions; PASS 6/6, PARTIAL 4–5, FAIL ≤3 → FAIL is HIGH impact). | ~80-item checklist in 10 categories (hierarchy 8, typography 15, color 10, spacing 12, interaction states 12, responsive 8, motion 7, content 8+, AI slop, performance 6). |
| 4 | **Interaction-flow review**: 2–3 key flows, one script per flow, accessibility-tree *diff* before/after each action, console errors, screenshots. **Goodwill meter** starts at 70/100 with explicit deltas (−15 hidden info / interstitial, −10 format punishment / unnecessary info / sloppy look, −5 per ambiguous choice; +10 obvious top tasks / graceful error recovery, +5 upfront costs / step-saving / apologies). <30 critical, 30–60 needs work, >60 healthy — the skill itself calls these numbers heuristic and says the useful output is the list of specific drains and fills. | |
| 5 | Cross-page consistency (nav, footer, component reuse, tone, spacing rhythm). | |
| 6 | **Compile report + baseline**: dual headline grades **Design Score (A–F)** and **AI-Slop Score (A–F)**; `design-baseline.json` (schema v2) written atomically (temp file then `mv`) plus a per-run copy. | Every category starts at **A**; each High finding drops one letter, each Medium half a letter, Polish = no grade effect. Weights: hierarchy 15, typography 15, spacing 15, color 10, interaction states 10, responsive 10, content 10, AI slop 5, motion 5, performance 5 (%). |
| — | **Outside voices** (independent second opinions): Codex CLI (read-only sandbox, 300 s cap) + a fresh Claude subagent, run in parallel and awaited before synthesis. | Findings merged with `[codex]` / `[subagent]` / `[cross-model]` tags; a 7-item YES/NO **litmus scorecard** is filled from both. If Codex fails, the run is tagged `[single-model]` and *missing coverage is never reported as clean*. Changelog: "Cross-model agreement = high confidence; disagreement = investigate." |
| 7 | **Triage** into High / Medium / Polish; anything not fixable from source (third-party widget, copy that needs the team) is **deferred** regardless of impact. | |
| 8 | **Fix loop**, per finding in impact order: 8a locate source (only files directly related; prefer CSS over structure) → 8a.5 optional *target mockup* of the fixed state → 8b **minimal fix**, no refactors → 8c **one commit per fix** `style(design): FINDING-NNN — …` → 8d **re-test** (re-navigate, snapshot, console errors, full-page *after* screenshot read next to the *before*; `CONSOLE_ERRORS` must be `[]` or no worse than baseline — a new error is a regression) → 8e **classify** verified / best-effort / reverted (`git revert HEAD`, finding → deferred) → 8e.5 regression **test only for JS-behaviour fixes** (CSS-only fixes are re-caught by re-running the audit) → 8f **self-regulation**. | See risk formula below. |
| 9 | **Final audit**: re-run on all affected pages; if target mockups exist, `$D verify` (vision diff, pass if matchScore ≥ 70 and no high-severity difference); recompute both grades and the detector count (`Detector: N → M`); **warn prominently if final scores are worse than baseline**. | |
| 10 | Report: per-finding fix status, commit SHA, files changed, before/after screenshots; summary deltas; a one-line PR summary with issue/fix counts and both score deltas. | |
| 11 | TODOS.md: add deferred findings; annotate fixed ones. Learnings log (typed, confidence 1–10, with file paths for staleness detection). | |

**Self-regulation (`DESIGN-FIX RISK`), checked every 5 fixes or after any revert** (design-review/SKILL.md.tmpl §8f): start 0 %; +15 % per revert; +0 % per CSS-only file; +5 % per JSX/TSX/component file; +1 % per fix after the 10th; +20 % for touching unrelated files. **Risk > 20 % → stop and ask the user. Hard cap 30 fixes.** `/qa` uses the same idea (`WTF-LIKELIHOOD`): +15 % per revert, +5 % per fix touching >3 files, +1 % per fix after 15, +10 % if all remaining issues are Low, +20 % for unrelated files; stop at >20 %; **hard cap 50 fixes**; test-only commits don't count.

**Evidence rules:** every finding needs ≥1 screenshot (annotated preferred); findings must state the concrete change and the reason for it, never a vague impression; document each finding as it is found (no batching); prefer 5–10 well-evidenced findings over many vague ones; always include a *Quick Wins* section (3–5 highest-impact fixes under 30 min); every screenshot must be displayed to the user (the browse skill says an unseen screenshot does not count as evidence). **During the audit phases the primary auditor must not read source code** — it evaluates the rendered site (Important Rule 4); source is opened only in the fix loop. (The *outside voices*, by contrast, are explicitly asked to review frontend source and cite file:line — so one run deliberately mixes a black-box auditor with white-box second opinions.) Keeping the auditor black-box separates observation from implementation knowledge and stops it from rationalising what the code intends.

**Critique language** (design-review §Design Critique Format): four sentence stems — I notice… (observation), I wonder… (question), What if… (suggestion), I think… because… (reasoned opinion); every point is tied to user goals and paired with a specific improvement.

**Regression mode** (`--regression` or an existing baseline): compare per-category grade deltas, new and resolved findings. Detector deltas are only computed when detector mode *and* the hashed target set match; otherwise the report states that no delta can be computed and why (different modes or a changed target set); an engine-version change is printed as a caveat. Because live pages jitter, raw counts are only advisory and the signal is which rule ids appeared or disappeared.

**Design-mode classifier before judging** (§Design Hard Rules, derived from impeccable): name the surface's mode — PERSUADE (landing), OPERATE (app UI), READ (docs), EXPERIENCE (portfolio), HYBRID (classify per section) — and apply that mode's rules. This is a false-positive guard: e.g. dense app UI is not penalised by landing-page rules.

#### 2.1.2 Finding triage vocabulary shared across gstack design skills (`lib/design-catalog.ts`, `review/design-checklist.md`)

Each catalog entry carries: `detect` method (engine / grep / render / llm), `confidence` (HIGH = reliably greppable; MEDIUM = heuristic or aggregation, some noise expected; LOW = needs visual intent, so it is presented only as a possible issue to verify visually), `tier` (**auto-fix / ask / possible**), `impact` (high / medium / polish), and a `handoff` command. The **AUTO-FIX** bucket is deliberately tiny and mechanical: `outline: none` without replacement, `!important` in new CSS, `transition: all`/layout-property transitions, justified body text, body text <16 px, all-caps paragraphs. **Everything involving design judgment (all AI-slop findings, typography structure, spacing choices, missing states, DESIGN.md violations) is ASK.** LOW-confidence items are never auto-fixed. Output groups: AUTO-FIXED / NEEDS INPUT / POSSIBLE. **Suppressions** (do not flag): patterns documented as intentional in DESIGN.md, vendor/third-party CSS, resets/normalize, test fixtures, generated/minified CSS.

The generic `/review` **pre-emit verification gate** (generated `review/SKILL.md` §Confidence Calibration) is the strongest anti-false-positive rule found: quote the exact `file:line` text motivating a finding; *if you cannot quote it, the finding is unverified and its confidence is forced to 4–5*. Display: 9–10 and 7–8 shown normally; 5–6 shown with a verify-this caveat; 3–4 appendix only; 1–2 only if catastrophic and labelled speculative. Fix-First heuristic (`review/checklist.md`): auto-fix only what a senior engineer would apply without discussion; anything reasonable people could disagree on, anything >20 lines, anything changing user-visible behaviour, and design decisions → ASK. If a user confirms a <7 finding was real, log it as a calibration learning.

#### 2.1.3 Bounded slop gate — the anti-thrash pattern (`scripts/resolvers/design.ts`, `{{DESIGN_DETECTOR:gate}}`, used by `/design-html`)

Scan once → **one** surgical fix pass over non-advisory rules → scan once more → **stop**. Whatever remains is presented as *accepted-with-reason*, where the only legitimate reasons are: the approved mockup contains the pattern; DESIGN.md tokens bless the value; DESIGN.md's Decisions Log or Do's/Don'ts records it as intentional; or an inline `<!-- impeccable-disable <rule>: <reason> -->` the user agreed to. The template is explicit that this is a single pass, not a loop. This is the cleanest mechanism found for preventing agents from oscillating on taste-level rules.

#### 2.1.4 `/qa` — Test → Fix → Verify (bug-centric sibling)

- **Fix tiers** (qa/SKILL.md.tmpl): Quick = fix critical+high; Standard (default) = +medium; Exhaustive = +low/cosmetic. Issues below the tier or not fixable from source → deferred.
- **Severity** (qa/sections/qa-patterns.md, issue-taxonomy.md): Critical = data loss, security/privacy exposure, core app unusable for all; High = core task blocked, no workaround; Medium = impaired but workaround exists; Low = cosmetic/copy/friction without lost task completion.
- **Health score 0–100**: weighted categories Console 15 %, Links 10 %, Visual 10 %, Functional 20 %, UX 15 %, Performance 10 %, Content 5 %, Accessibility 15 %. Console: 0 errors→100, 1–3→70, 4–10→40, 11+→10. Links: −15 per broken link. Other categories start at 100 and deduct Critical −25, High −15, Medium −8, Low −3, floor 0. **Deduplicate the same root cause across pages; one primary category per finding (no double deductions). Untested categories are excluded and partial scores labelled provisional; only compare runs with identical coverage.** Final = Σ(score×weight)/Σ(tested weights).
- **Probe discipline** (qa/sections/exploratory.md): write a *charter* per behaviour (contract, risk, entrypoint, isolation, exit condition); one probe at a time, never batched; **before each probe, publish a checkpoint file** (`exploration-NNN.json`: last command, exact observed output, hypothesis, next command); time budgets (Quick 30 s, Full/Regression 900 s; /review smoke 5 min or 12 probes). Every reported issue must be **confirmed by an exact replay from the same initial state, then minimised**, before repair. After any code change, every affected check is re-run (anything not proven unaffected counts as affected) and a status needs fresh evidence. Missing prerequisites, timeouts and refusals never pass.
- **Fix loop**: 8a reproduce + causal hypothesis; **8a.5 write the failing regression test first** (red before repair; prove the defect—not a bad fixture—caused the failure; attribute with ISSUE id, date, report path; never replace an existing test file; never encode buggy output as expected, weaken a test, or delete a valid failing test); a **test value bar** requires a value card `protects / fails_when / why_new / seam=none` and rejects tests that duplicate existing coverage or need a test-only production seam; 8b minimal fix; 8c re-run the regression, the original failing probe **and an adjacent happy path**; 8d commit only verified fixes with their regression (`fix(qa): ISSUE-NNN — …`), leave unresolved work uncommitted; 8e classify; 8f self-regulation; Phase 9 final QA with score delta and loud warning on regression.
- **Report template** (qa/templates/qa-report-template.md): header (date, URL, branch, commit, PR, tier, scope, duration, pages, screenshots, framework), health table, *Top 3 Things to Fix*, console-health table, severity counts, per-issue blocks (severity, category, URL, description expected-vs-actual, numbered repro steps with step screenshots), fixes table (status, commit, files), before/after evidence, regression-test table + deferred tests (precondition/action/expected/why deferred), ship-readiness (score before→after), regression table (fixed since / new since baseline).

#### 2.1.5 `/plan-design-review` — pre-implementation review loop

- Rates **7 passes** (information architecture, interaction-state coverage, user journey & emotional arc, AI-slop risk, design-system alignment, responsive & a11y, unresolved decisions) **0–10**, explains *what would make it a 10*, then resolves gaps (plan-design-review/sections/review-sections.md).
- **One issue = one question; never batch** (including multiple tabs in one call); 2–3 options each with effort-now vs risk-if-deferred, mapped to a named design principle; labelled `3A/3B`. A gap with an obvious fix still needs approval; writing a report, mapping a token or drawing a mockup approves nothing. Decisions are carried across passes (don't re-ask an already-decided fix; re-open only on new evidence).
- **Overall design score = the lowest of the six scored passes** (weakest-link), reported before and after fixes; "design-complete" only if every pass ≥8. **Re-run loop:** on re-invocation, passes ≥8 get a quick pass, <8 get full treatment. Unresolved hard-rejection caps the AI-slop pass below 8.
- Mandatory interaction-state table per feature (LOADING / EMPTY / ERROR / SUCCESS / PARTIAL — each cell describes what the user sees, not backend behaviour), a journey storyboard (step / user does / user feels / plan specifies?), and a table pairing each open decision with the consequence of deferring it.
- Outputs: NOT-in-scope list, What-already-exists, TODOs (what/why/pros/cons/context/depends-on), implementation tasks (P1 blocks ship / P2 same branch / P3 follow-up; each tied to a finding; no invented tasks), plus a JSONL artefact even when there are zero tasks, so "ran with no findings" stays distinguishable from "did not run".
- **Freshness of review evidence** (Review Readiness Dashboard): a diff review counts as CURRENT only if its start and end *working-tree content fingerprints* equal the current fingerprint; plan reviews expire after 7 days; missing/stale/unknown coverage is never shown as clear.
- Known model failure: a model overlay instructing the model to batch its questions silently broke per-finding pacing until it was re-ordered (CHANGELOG, Opus 4.7 cadence regression). Lesson: per-finding gating must be stated with higher precedence than generic efficiency advice.

#### 2.1.6 `/design-consultation`, `/design-shotgun`, `/design-html` — how DESIGN.md and user taste enter the loop

- `/design-consultation` writes **DESIGN.md in the open google-labs-code/design.md format** (YAML front matter: `colors`, `typography`, `rounded`, `spacing`, `components` with `{token.path}` references; prose sections Overview, Colors, Typography, Layout, Elevation & Depth, Shapes, Components, Do's and Don'ts, Motion, **Decisions Log** table date/decision/rationale) only after an explicit final approval (Q-final), and appends a CLAUDE.md rule: read DESIGN.md before any visual decision; do not deviate without explicit approval; in QA mode flag code that doesn't match it. `bin/gstack-design-md.ts check|tokens` validates the format and emits the flat token map used for calibration.
- `/design-shotgun`: generate N variants → served comparison board → structured feedback JSON `{preferred, ratings{A..}, comments{}, overall, regenerated}`; regenerate, remix (e.g. layout from one variant and colours from another) or more-like-this loop until Submit; **confirm the understood feedback back to the user before saving**; approved/rejected variants update a persistent **taste profile** (with decay and conflict flagging) that biases later generations. Max two rounds of context-gathering questions.
- `/design-html` refinement loop: verification screenshots at 375/768/1440 after each change, surgical edits only (never regenerate the whole file — preserves user's manual edits), **max 10 iterations then ask**; exit on explicit "done".
- Vision gates (design/src/check.ts, diff.ts): `check` = one-line PASS/FAIL on text readability, layout completeness, visual coherence; `verify` = before/after diff JSON with per-area severity and a 0–100 matchScore, pass iff ≥70 and no high-severity difference. **Weakness: both fail *open*** (API error → `pass: true` with a note) — a gate that silently passes on infrastructure failure.

#### 2.1.7 `/ios-design-review` and `/ios-fix`

- iOS review scores 10 dimensions 0–10 per screen (typography, spacing rhythm on a 4/8 pt grid, color hierarchy incl. WCAG 4.5:1/3:1, touch targets ≥44×44 pt, loading/empty/error states, accessibility incl. VoiceOver, Dynamic Type to XXL, Reduce Motion, animation discipline ≤2 simultaneous / 200–300 ms, iOS idiom alignment, information density, AI-slop); read-only capability token; asks the user about any score <7. Its failure-mode table covers finding fewer screens than the ground-truth list (ask whether the missing ones sit behind untriggered state) — a **coverage check against an expected inventory**.
- `/ios-fix` **hard rule: no Swift edit before a state snapshot that reproduces the bug has been captured**; the pre-bug snapshot + screenshot become a regression fixture; verify by restoring the snapshot after rebuild and comparing screenshots; **max 3 fix iterations, then escalate** with the best hypothesis; if several root causes are plausible, ask the user which to fix; build failure → revert edits first.

#### 2.1.8 Tooling the loop relies on (`browse`)

Accessibility-tree snapshot with stable `@e` refs (`-i` interactive only), `-D` unified diff against the previous snapshot (first call stores the baseline), `-a` annotated screenshot with ref labels, `-C` cursor-interactive refs for clickable divs, `responsive` (375/768/1280 shots), `console --errors`, `is visible|enabled|focused…` state assertions, `watch` passive observation. Conventions that make evidence auditable: every script prints labelled lines (`URL=`, `CONSOLE_ERRORS=`, `DIFF_START/END`, `NAV=`), ends with a success sentinel (missing sentinel = failure), and page content is wrapped as **untrusted** (never instructions). Auth walls are detected by URL patterns (`/login`, `/signin`, `/auth`, `/sso`) so the auditor doesn't critique a login page by mistake.

#### 2.1.9 Reported failure modes (issues/changelog)

- **#2776** — the outside (cross-model) reviewer is killed by a hard timeout and *silently replaced by a same-family subagent*; the report still looks like it had an independent voice. → Independence must be recorded per run, and loss of independence must be visible.
- **#1644** — a spec-review subagent was instructed *not* to read the codebase, so it could only check internal consistency; a doc self-rated 9/10 had 3 of 7 premises false (caught only by a reviewer that read files). → Reviewers must verify claims against ground truth; self-evaluation scores are unreliable.
- **#1529** — iteration rounds overwrote generated artifacts (two paid generations, one file). → Never reuse output paths; count artifacts vs. calls.
- CHANGELOG notes on eval flakiness and pacing regressions show that per-finding gating and format contracts need automated tests of the *rendered* behaviour, not the model's claims.

**Strengths:** most complete loop (baseline → triage → atomic fix → re-test → classify → revert → final re-audit → delta); explicit numeric stopping rules; deterministic detector + LLM judgment + cross-model voice; DESIGN.md calibration; regression mode that refuses to compute deltas across non-comparable runs; evidence and freshness discipline.
**Weaknesses/gaps:** severity is a 3-level impact scale, not Nielsen 0–4 with frequency/impact/persistence; no heuristic-id per finding; grades are LLM-judged letter grades (no inter-rater check beyond the second voice); goodwill meter is admittedly arbitrary; vision gates fail open; the design checklist mixes empirically grounded rules (WCAG) with taste rules without labelling the evidence level; no real-user data ingestion beyond the taste profile.
**Adopt:** clean-tree precondition; one-finding-one-commit with id in message; before/after screenshot pair + console-error parity as the minimum re-test; verified/best-effort/reverted/deferred status set; revert-on-regression; risk heuristic + hard cap; regression baseline JSON with id-level appear/disappear deltas and no delta when coverage differs; detector-hit-is-evidence-not-verdict; pre-emit quote gate; AUTO-FIX/ASK/POSSIBLE tiers; bounded one-pass slop gate with enumerated accepted-with-reason; DESIGN.md token calibration; no-source-reading during audit; per-run independence recording.

### 2.2 Owl-Listener/designpowers — 10-agent inclusive design team with a reconciled review → fix → persona re-test loop

- **What it is:** A markdown-only skill/agent pack (Claude Code plugin + Gemini CLI extension; portable to any tool that reads markdown) modelled on obra/superpowers. Two lanes: **Build** (full pipeline) and **Review** (audit an existing screenshot/URL/code). Two modes: **Direct** (user approves every handoff) and **Auto** (runs through, with mandatory pause conditions).
- **URL:** https://github.com/Owl-Listener/designpowers (read at commit `cb00757da9d554591fa78d27aa1854d60a05c4f7`, 2026-06-23; ~247★). Issue #35 asks why updates stopped, which suggests the project may be stalled — [unverified whether maintenance resumed].
- **License:** MIT — text and structure adaptable with attribution.
- **Files read (full):** `README.md`; `skills/using-designpowers/SKILL.md` (router: lanes, red flags, routing, modes, auto safeguards, screenshot checkpoint, reconciliation protocol, team presentation, anti-patterns); agents `heuristic-evaluator.md`, `design-critic.md`, `accessibility-reviewer.md`, `design-builder.md`; skills `design-review`, `heuristic-evaluation`, `verification-before-shipping`, `synthetic-user-testing`, `usability-testing`, `designpowers-critique`, `design-debt-tracker`, `design-state`, `taste-feedback`, `design-debate` (steps 1–6); `design-express` (verification lines), `design-memory` (observational-only rules); `examples/traced-run/{README.md, design-state.md, artifact/accessibility-evidence.txt}`; `scripts/shoot.js`; `paper/taste-as-primitive.md` (evaluation disclaimer); issues list. (Agents `design-lead`, `design-strategist`, `design-scout`, `inspiration-scout`, `motion-designer`, `content-writer` and the remaining domain skills were skimmed for loop relevance only — they are build-side.)

#### 2.2.1 Orchestration order

Build lane: Discover → Research → Personas → Strategy → Taste → Inspire → (Debate if uncertain) → Plan → Design (lead, motion, content) → **Build** → (2–4 **taste checkpoints** during build) → **Screenshot checkpoint** → **parallel review** (design-critic ∥ accessibility-reviewer ∥ heuristic-evaluator) → **reconciliation** → **fix round** (design-builder) → **re-review only the critical fixes** → **synthetic user testing** (persona walkthroughs) → (fix + re-test failing tasks only) → **verification-before-shipping** → team presentation → retrospective (skills/using-designpowers/SKILL.md §Reconciliation Protocol, §Screenshot Checkpoint).

Review lane (skills/design-review/SKILL.md): get the *actual* artefact (screenshot / live URL / code / DESIGN.md + build) → capture a **lightweight inferred brief** (key task; audience incl. ability spectrum — the whole spectrum assumed when unknown; quality bar + what prompted the review), recorded in `design-state.md` and **explicitly labelled as inferred** → run the three reviewers in parallel → reconcile → **one consolidated report** with a **Coverage line** stating what was verified vs only inferred (e.g. a static screenshot cannot verify keyboard/focus/screen-reader behaviour) → user chooses: fix (dispatch builder), track (debt register), go deeper (strategy), or validate with people. "The review proposes; it does not auto-fix without direction."

#### 2.2.2 Evaluator roles and independence

- **design-critic**: plan/brief/principle alignment, consistency, persona coverage, gaps, **craft vs the taste profile** (table: element / taste expectation / current state / gap). Severity Critical / Major / Minor / Note. Recommendation **proceed / revise / rethink / polish**.
- **accessibility-reviewer**: WCAG 2.1 AA (AAA where feasible) + COGA; measures instead of guessing (runs automated checks, computes contrast, counts touch-target pixels); every issue names **who is affected** and an exact fix (e.g. a specific hex change to reach 4.5:1). Severity Critical (blocks access) / Major / Minor. The builder treats its accessibility verdicts as final.
- **heuristic-evaluator**: Nielsen's 10 with check questions per heuristic; **cognitive walkthrough with the four classic questions per step** (will the user try to achieve the right effect / notice the action is available / associate action with effect / see progress) — any no or uncertain answer is a finding; error-path, learnability (first-time) and efficiency (repeat) assessment; per-heuristic verdict ✓/⚠/✗; findings tagged `[H#]`; recommendation proceed/revise/rethink. **No duplication across reviewers** — a contrast problem is reframed as its usability consequence rather than re-reported as a ratio.
- Independence: the three reviewers run **in parallel** against the same build and brief, and each must evaluate the built artefact rather than the spec. However, all three are prompts for the same model family (`model: sonnet` in the agent front matter) and the traced example admits its agent voices were *not* separately dispatched subagents (examples/traced-run/README.md, scope disclaimer). So independence is role-based, not model- or evaluator-based.
- **False-positive guard — URL discovery protocol** (agents/heuristic-evaluator.md): never infer a sub-page URL from a nav label (guessed URLs yield bogus 404 findings); use only real `href`s, then sitemap.xml, then robots.txt `Sitemap:`; if all fail, state that sub-pages could not be verified and evaluate the homepage only.
- Positive findings are mandatory (a *What works well* section) in every reviewer report.

#### 2.2.3 Reconciliation protocol (the most transferable piece)

1. Classify every finding from all reviewers as **Aligned** (several reviewers, same underlying issue), **Complementary** (different, non-conflicting — fix all), or **Conflicting** (they disagree on what to do).
2. Resolve conflicts by ordered rules: (1) **accessibility over aesthetics**, (2) **usability over style**, (3) **brief over opinion**, (4) **personas break ties** — prefer the option serving more personas, especially those with the greatest access needs, (5) **escalate to the user** if still unresolved.
3. Build **one prioritised fix list** (critical first), recording which reviewer sourced each item and whether it was reconciled; dispatch the builder; log reconciliation decisions in `design-state.md`.
4. **Re-run reviewers only on the critical fixes**, not a full re-review (cost control — but see weaknesses).
5. Disagreements are never hidden: the end-of-run team presentation must surface every unresolved tension (agent A vs agent B, one-sentence views each).

#### 2.2.4 Stop / pause conditions (Auto-mode safeguards)

Even in Auto, the pipeline must pause for the user if: the accessibility reviewer finds a **critical** issue; the critic says **rethink**; the heuristic evaluator finds a critical **H3** (no undo on destructive action) or **H1** (user completely lost) violation; **synthetic testing shows a persona cannot complete the primary task**; reconciliation is **unresolvable**; or any agent needs **user-only knowledge** (e.g. brand colours). The pause message must say why. Any user correction or talking to an agent by name flips back to Direct mode. Skipping an agent must be announced with its consequence (never silent).

#### 2.2.5 Persona simulation (synthetic user testing) — after the fix round

Scenario format `SCENARIO / TASK / PERSONA (ability context) / SUCCESS`; per step `USING (input method) / SEES (at their zoom/contrast/device) / THINKS / RESULT ✓ ⚠ ✗ ?` with `FINDING` and `WHO IS AFFECTED`; rules: stay in character (evaluate what a screen reader would announce, not the sighted view), use the persona's device and zoom, include emotional state, test error paths, record friction not just failure. Output a **barrier matrix** (task × persona), universal barriers (≥2 personas → design problem), persona-specific barriers, friction hotspots, emotional patterns, and **pre-fix vs post-fix comparison**. Severity: Critical = cannot complete; Major = completes with significant difficulty; Minor = rougher than it should be. Failures → builder → **re-test only the failed tasks**. The skill itself states the limits: synthetic testing catches predictable barriers but misses the genuine surprises only real people produce; it does not replace real usability testing (skills/synthetic-user-testing/SKILL.md, comparison table).

#### 2.2.6 Real usability testing (skills/usability-testing/SKILL.md)

3–5 task scenarios with a realistic trigger, clear success condition, and no hints about how to do it; recruit 5–8 incl. ≥1 screen-reader user, ≥1 person over 60, ≥1 non-native speaker, ≥1 low-tech-confidence person; method table (moderated think-aloud ≥5; unmoderated remote 8–12; guerrilla 3–5; AT-user audit 2–3); script welcome → background → tasks → debrief; the moderator never helps during a task (silence is treated as data); outcome classes **completed easily / with difficulty / failed / completed wrong (thought they succeeded)**; severity Critical = blocks ≥2 participants; every finding becomes `[Severity] [What happened] → [Design action] → [Owner agent]`; deliver task success-rate table + ranked findings + iterate/ship/rethink.

#### 2.2.7 Verification and debt (closing the loop honestly)

- **verification-before-shipping** (its core rule): no completion claim without evidence. Checklists: plan tasks complete and none deferred without user approval; brief (problem, personas, success criteria, scope creep); accessibility *run, not guessed* — automated scan (axe-core/Lighthouse), keyboard pass, screen-reader basics (headings, labels), 200 % zoom, `prefers-reduced-motion`; for design-only artefacts contrast measured with a tool and targets measured; content (no placeholders, written errors, alt text, specific labels); persona cross-reference; debt status. Verdict Ready / Issues to resolve first.
- **design-debt-tracker**: every deferred Minor/Note finding becomes a register row `ID (never reused) / date / source / severity / what / who is affected / suggested fix / status / notes`. Status **Open / Resolved / Accepted / Escalated**. **Escalate Minor→Major** when open ≥3 iterations, when several items hit the same persona/screen, on context change, when a user/stakeholder raises it independently, or when two Minors compound. Accepting accessibility debt requires explicit user acknowledgement; resolved rows are never deleted. Critical items may never be recorded as debt.
- **design-state.md** is the shared, append-only record (brief, personas, principles, taste profile, decisions log — reversals are new superseding entries, open questions, artefact index, debt register, handoff chain incl. user overrides).
- **Evidence artefact pattern** (examples/traced-run): a plain-text evidence file with computed contrast for every text/UI pair against the 4.5/3.0 thresholds plus structural checks, each PASS/FAIL, and a rendered PNG (`scripts/shoot.js`, Playwright, DPR 2).

#### 2.2.8 User feedback ingestion

- **Taste checkpoints** during build: 2–4 maximum (colour+type applied, layout scaffold, first interaction, real content); questions must be specific and answerable (name the font/size/weight, the padding/radius, the hex) — never a generic is-this-good question; response handling table (looks right / specific adjustment / wrong direction = stop and discuss / mixed / skip further checks); flag cascades before applying; adapt checkpoint frequency to user behaviour; off by default in Auto.
- **Design debate** for genuinely uncertain direction: framed question with constraints and stakes; 2–3 advocate agents argue *for* assigned directions (who it serves best/least, trade-offs, evidence; no straw men), one rebuttal round each, accessibility check of every direction as a constraint, user decides. Not for trivial decisions or when accessibility dictates the answer.
- **Design memory** is deliberately *observational only* — never fed back to steer a new project (prevents cross-client contamination). Minor internal tension: `taste-feedback` still says to record checkpoint responses as signals in design-memory and to adapt checkpoint frequency over time.

**Strengths:** explicit multi-lens review (craft / accessibility / usability) with a conflict-resolution order; inferred-brief + coverage disclosure for review-only runs; persona barrier matrix with pre/post comparison; debt register with escalation; honest evidence artefacts and an honest disclaimer that taste benefits are not empirically validated (`paper/taste-as-primitive.md`, Evaluation paragraph).
**Weaknesses/gaps:** severity is a 3–4-level label with no frequency/impact/persistence decomposition and no Nielsen 0–4 mapping; no numeric score or baseline/regression diff; no atomic-commit or revert policy for fixes; re-reviewing only the critical fixes can miss regressions introduced by Major/Minor fixes; reviewers are same-model role-plays, not independent evaluators; no deterministic detectors beyond contrast computation; synthetic personas are LLM simulations (risk of confident fabrication); fix scoping is batched (one fix list to the builder) rather than one-at-a-time.
**Adopt:** three-lens parallel review + Aligned/Complementary/Conflicting classification + ordered conflict rules; inferred-brief marked as inferred; coverage line (verified vs inferred); mandatory what-works-well section; URL-discovery anti-false-positive rule; auto-mode pause conditions; persona barrier matrix with pre/post-fix comparison and an explicit caveat that simulated users are not real users; debt register with escalation triggers and explicit acceptance; outcome class *completed wrong*; computed-evidence file for a11y claims.

### 2.3 pbakaus/impeccable — loop mechanics only (critique → act → polish → re-score; snapshots; finish-review verdict loop; hook triage)

*(Scope note: impeccable's design content — anti-pattern catalogue, craft floor, typography/colour doctrine — is covered by another research note. Only the review/fix/verify mechanics are recorded here.)*

- **URL:** https://github.com/pbakaus/impeccable (read at commit `4adabaf2c2bd3148f162d35aaa6acd7025343649`, 2026-10-01; ~73.6k★). Canonical sources live in `skill/` (host-specific copies under `.claude/`, `.agents/`, `plugin/`, `cursor-plugin/` are generated).
- **License:** Apache-2.0 (`LICENSE`); `NOTICE.md` credits ehmo/platform-design-skills (MIT) for the iOS/Android references. Adapting text requires keeping the license, a NOTICE and a statement of changes (Apache-2.0 §4); adopting the *mechanics* in our own words with attribution is unproblematic.
- **Files read:** `skill/reference/critique.md` (orchestration, invariants, report, persistence, ask-the-user, heuristic scoring guide, P0–P3, persona selection), `skill/reference/polish.md` (full), `skill/reference/audit.md` (full), `skill/agents/impeccable-finish-reviewer.md` (full), `skill/reference/new-work.md` lines 140–156 (finish-review orchestration), `skill/reference/hooks.md` lines 1–80 (hook tiers + finding triage), `crates/context/src/critique_storage.rs` (fingerprint/close/latest logic), `NOTICE.md`.

#### 2.3.1 Critique = two isolated assessments, then synthesis (skill/reference/critique.md)

- **Assessment A** (LLM design review: specificity, hierarchy/IA, cognitive load incl. >4 visible options at a decision point, emotional journey, **Nielsen's 10 scored 0–4**) and **Assessment B** (deterministic detector `impeccable detect --json` + in-browser overlay injection) **must run as two isolated parallel sub-agents** that never see each other's output. Running them in one context is permitted only when no sub-agent tool exists, and then the report's first line must be a **`DEGRADED: single-context (<reason>)` banner**; the header otherwise states `Method: dual-agent (A: id · B: id)`. Rationale stated in the file: deterministic output *still anchors judgment*, so A must finish before detector findings enter the synthesis context.
- Synthesis must *weave*, not concatenate: say where LLM and detector agree, what the detector caught that the LLM missed, and which detector hits are false positives.
- **Scoring:** each heuristic 0–4 (0 none … 4 genuinely excellent; the guide expects most real interfaces to land between 20 and 32 of 40); heuristics that cannot apply on the surface's mode (e.g. H7/H10 on landing pages) are `n/a` with a one-line reason and the total is **renormalised** (e.g. 24/32), banded by percentage: ≥90 % Excellent, ≥70 % Good, ≥50 % Acceptable, ≥30 % Poor, else Critical (raw bands for /40: 36–40, 28–35, 20–27, 12–19, 0–11). **Never print /40 over a partial set.**
- **Issue priority P0–P3**: P0 Blocking (prevents task completion), P1 Major (significant difficulty/confusion; in audit also any WCAG AA violation), P2 Minor (annoyance, workaround exists), P3 Polish (no real user impact). Tie-breaker: if a user would plausibly contact support about it, it is at least P1. Report 3–5 priority issues, each *What / Why it matters / Fix / Suggested command*; plus 2–3 strengths, persona red flags (2–3 auto-selected archetypes by interface type, plus 1–2 project-specific personas derived from the product context), minor observations, provocative questions.
- **Ignore list:** `.impeccable/critique/ignore.md` is the *only* prior-run input critique consumes; matching findings are dropped silently. (Deliberately avoids anchoring on old reports.)
- **Close of the run is mandatory:** deliver the full report in chat *before* persisting; then ask 2–4 targeted questions each tied to specific findings with 2–3 concrete options (priority direction, whether a tonal mismatch is intended, scope — top three, everything, or critical only — and off-limits areas). Skipping questions is allowed only if there are fewer than 3 priority issues, and must print `Questions skipped: <reason>`. Then an ordered action plan mapping each priority issue to a fix command, honouring the user's scope and off-limits answers, ending with `polish`; the user chooses whether to run them one at a time, all together, or in any order.

#### 2.3.2 Snapshots, fingerprints and trend (critique-storage)

- After delivery the report body is persisted to `.impeccable/critique/<slug>-<stamp>.md` with front matter `target, total_score, max_score, na_heuristics, p0_count, p1_count` and, for a local file target, **`target_fingerprint: sha256:<hash of the file bytes>`** (crates/context/src/critique_storage.rs `fingerprint_target`).
- `critique-storage trend <target> 5` returns the last five runs; the user sees one line, e.g. `24 → 28 → 32 → 29 → 32 (out of 40)`; if runs have different maxima, each is printed with its own denominator and flagged as *not like-for-like*; a first run says there is no trend yet.
- **Staleness = content change.** When `polish` asks for the latest snapshot, the stored fingerprint is compared with the current file hash; any byte change (or deletion) **closes the snapshot** (`closed: true` written into its front matter) and the command exits 2, so stale findings are not re-applied to changed code. URL targets have no fingerprint and stay current until closed explicitly. Closed snapshots keep their trend history.

#### 2.3.3 Polish = the fix pass that consumes and closes the critique (skill/reference/polish.md)

- Polish refines and never smuggles in a redesign: preserve the incumbent visual world, content, behaviour and everything out of scope; if the concept is wrong, say so and recommend redesign instead of smuggling one in.
- **Classify each drift before fixing**: *missing token* (system needs a reusable value), *one-off implementation* (a shared component should replace it), *conceptual mismatch* (flow/IA/hierarchy differs from comparable areas), *local defect*. Fix at the **narrowest correct level**; ask when a binding system principle cannot be inferred.
- Evidence first: use the feature at representative sizes; determine functional completeness, quality bar, known deliberate gaps, real states/content lengths/roles/input methods. A current (fingerprint-matching) critique snapshot is used *as one input* (its P0/P1 issues), but polish always performs its own independent pass.
- **Fix order**: (1) broken/blocked tasks, data loss, misleading state, inaccessible paths → (2) missing loading/empty/error/success/disabled/permission states → (3) flow, hierarchy, responsive, design-system drift → (4) visual and motion inconsistencies → (5) code/asset cleanup — and bring the whole path up to the same quality bar rather than perfecting one corner.
- Verify: walk the whole path again with mouse/keyboard/touch; check mobile/intermediate/wide; all states; zoom, contrast, focus, semantics, SR names; console errors, layout shift, latency; agreement with DESIGN.md and neighbours. Detector output counts as defect evidence but never as proof of quality, and a clean scan never replaces visual judgment; **never add another detector pass** beyond the one context asks for. Finish with a source-diff review to remove churn/orphans. **Close the snapshot only when every priority issue it supplied is cleared**, and only that snapshot (a newer critique stays live).
- `audit` is the report-only sibling (it documents issues for other commands and fixes nothing): 5 dimensions × 0–4 = /20 (bands 18–20, 14–17, 10–13, 6–9, 0–5), per-issue `P? / location (component, file, line) / category / impact / WCAG ref / recommendation / command`, systemic patterns, positive findings; unverified false positives must never be reported; for touch/gesture claims state *what produced the evidence* (emulated viewport, synthesized touch, engine, physical device) and what stayed untested.

#### 2.3.4 Finish review = fresh reviewer, fixed vocabulary, bounded verdict loop (skill/agents/impeccable-finish-reviewer.md; skill/reference/new-work.md)

- The reviewer is a **separate agent spawned with no forked conversation history** — the stated reason is that a reviewer inheriting the builder's transcript inherits its framing, optimism and abstractions. It edits nothing, has no browser (reviews only captured evidence), and has a hard read budget (stop reading ~turn 10 and write). Where no sub-agent exists, a degraded in-thread pass is allowed but must be disclosed.
- **Check 0 — evidence validity first:** required captures (desktop + mobile, plus the user's reported viewport if known) must exist and be valid (no black/blank regions, content matches filename, document top visible for full-page, sane dimensions). Any failure → `disposition: recapture` and *no review*, because a verdict built on broken evidence would turn the breakage into an approval. The builder must **settle or disable entrance animations before capture** because an element hidden by animation timing looks missing and then gets "fixed" into a regression.
- **Anchoring guard:** inventory the approved comp's salient elements *in your own words before* reading the builder's contract or summary.
- Checks in order: persistence (required artefacts/approvals exist), **fidelity** (per-element matrix: match / acceptable adaptation / missing / contradicted / added without approval; an adaptation counts only if it cites the user answer, brief, accessibility need or product truth that forced it — uncited deviation = defect; region scores from an image-diff report are taken as rows unless the paired crop shows the score is wrong), ceiling (quality-bar card), contract promises, truth (no invented claims, labelled demo data), floor (banned patterns).
- **Disposition is derived, never felt**, from exactly four words: `recapture` (evidence failed), `rebuild` (wholesale fidelity failure — patching a rejected page is refused), `fix` (material_fixes non-empty), `ship` (no missing/contradicted rows). The parent must report it verbatim and may not soften it. Output: five sections — persistence, fidelity matrix, ceiling, **material_fixes (ordered, ≤8, fidelity before craft)**, and a **`keep` line naming what must not be diluted while fixing** (an explicit anti-regression instruction).
- **Verdict pass** after a fix batch: the builder recaptures the *same* viewports over the *same* files; the same reviewer is in **scoring mode, not re-hunting**: each material fix → resolved / partial / unresolved *as visibly shown in the new screenshots* ("the parent's narration of what was fixed is not evidence"; a mechanically moved element that still lacks the named quality is partial at best), then at most **three regressions introduced by the fix batch**, then a recomputed disposition. Partial/unresolved can never recompute to ship, and a ship verdict covers only the scored fixes, not the whole surface.
- **Budget:** two inspection rounds is the ceiling inside the build thread (fixes are batched between rounds rather than screenshot-per-tweak); an unattended run ends after two verdict rounds; in an attended session the user decides whether to fund another round; **stop the moment a round resolves nothing**; the reviewer's list is the only work list (no re-opened hunt); no second detector pass. **User evidence reopens review**: a user's own screenshot or named mismatch outranks every capture and triggers a fresh full review — the file names inline patching plus self-certification as the way a rejected page ends up shipping twice.

#### 2.3.5 Hook-time detector and finding triage (skill/reference/hooks.md)

- Two tiers: a **per-edit hook** surfaces only *immediate*, mechanical, unambiguous findings (broken images, overflow/clipping, contrast/legibility, gradient text, glow shadows, design-system drift); taste-level rules (copy cadence, palette/typography taste, layout rhythm) are **deferred to a single deep pass at session Stop**, deduplicated against what was already reported; a clean session stops silently. (Cursor variant: a pre-write gate denies a write only when the real detector finds an issue.)
- **Triage of every detector finding:** *real problem* → fix, and never add an ignore to skip a fix; *confident false positive or sanctioned exception* → persist the **narrowest** ignore (value-level, or one rule scoped to one file) with the evidence in `--reason "<who decided: evidence>"` and disclose it — claim user confirmation only if the user actually gave it; *unsure* → leave it standing and ask the user once in one line. File-wide and rule-wide ignores require asking the user first. Inline `impeccable-disable[-line|-next-line] <rule>: <reason>` markers are reserved for files that leave the repo.

**Strengths:** strongest independence and anti-anchoring design of any source (isolated A/B sub-agents, degraded banner, fresh reviewer without transcript, inventory-before-contract); content-fingerprinted snapshots so stale findings auto-expire; Nielsen 0–4 per heuristic with honest n/a renormalisation; fixed disposition vocabulary; verdict pass that scores only listed fixes plus ≤3 regressions; evidence-validity gate; disciplined false-positive triage with reasons.
**Weaknesses/gaps:** P0–P3 has no explicit frequency/persistence dimension; heuristic 0–4 scores are single-judge LLM ratings (no inter-rater agreement); fixes are *batched* between rounds (bisecting a regression is harder than with gstack's one-commit-per-fix); no git commit/revert policy; trend scores are not like-for-like across model or prompt versions (only the max_score difference is flagged).
**Adopt:** isolated deterministic vs judgment assessments + degraded banner; report provenance header; heuristic 0–4 with n/a renormalisation and % bands; P0–P3 with the contact-support tie-breaker; fingerprint-bound findings that expire on change; trend line with like-for-like warning; polish's drift classification + fix order; fresh-context finish reviewer with evidence gate, `keep` line, four-word disposition, verdict pass (resolved/partial/unresolved + ≤3 regressions), two-round budget and stop-when-a-round-resolves-nothing; narrowest-ignore triage with a who-decided-plus-evidence reason.

#### 2.3.6 Reported failure modes (impeccable GitHub issues, read 2026-10-01)

- **#660 (closed)** — before snapshots could be closed, `polish` treated a weeks-old critique (21/40, seven priority issues, all since fixed on main) as a live backlog; a later session spent a full sub-agent pass (~200k tokens) proving each finding stale. → Origin of the fingerprint/close mechanism; findings must expire when the evaluated content changes.
- **#881 (open)** — the contrast rule composited a gradient fading to `transparent` over *black* instead of the real page ground, reporting 17.6:1 text as 1.2:1; 44 false positives on one 7-page site, all ranked as the most severe contrast failures. **Adopt:** the two-tier inner/outer loop (always-on 7-step quick visual check after any UI edit + deep review at milestones); phase order with live-environment-first; Blocker/High/Medium/Nit as the *merge-gating* view of severity; positive acknowledgement first; problem-and-impact phrasing in the finding body *paired with* a separate recommendation field.

### 2.5 BuildTheWeb1/impaccable-agent (`impeccable-flow` skill) — audit → 5 sequential fix subagents → parallel code-review ‖ browser-QA gates → ≤3 targeted repair rounds

- **What it is:** A single-author Claude Code skill (repo name "impaccable-agent", skill name `impeccable-flow`) that orchestrates impeccable's commands end-to-end with **zero prompts**. Very new and unadopted (0★, created 2026-07-28, last push 2026-08-03) — treat as a design pattern, not a proven tool.
- **URL:** https://github.com/BuildTheWeb1/impaccable-agent (commit `fc32c8adbb75df3677d5ee795a2c8ae00b8f9c2f`).
- **License:** **none** (no LICENSE file; GitHub reports `license: null`) → default copyright, all rights reserved. We may describe and re-implement its *ideas* in our own words with credit, but must not copy its text or scripts.
- **Files read (full):** `README.md`, `skill/SKILL.md`, `skill/references/pipeline.md`, `skill/references/qa.md`, `skill/references/subagents.md`, `skill/references/preflight.md`; `skill/scripts/detect.mjs` (comparison logic, lines ~40–200).

**Pipeline (skill/references/pipeline.md stage map).** 1 Preflight (shell; hard stop) → 2a detector baseline (shell) ∥ 2b audit subagent (read-only, P0–P3 + health scores) ∥ 2d before-screenshots; 2c impeccable `critique` run **at top level** (so it can spawn its own two isolated sub-agents; if it comes back with a DEGRADED banner the banner must be preserved and surfaced) → 3 **five fix subagents strictly sequential: layout → typeset → colorize → polish → animate** (ordering rationale: spacing is the substrate; type only once boxes stop moving; colour after final sizes because WCAG thresholds depend on size/weight; polish as a seam-catching sweep; animation last because any earlier stage can move the animated elements) → 4 **code-review gate ∥ 5 browser-QA gate** (both blocking, run in parallel) → loop → 6 report script → `REPORT.md`.

**Key mechanics.**
- **Preflight refuses rather than degrades** (skill/references/preflight.md): hard stops `NOT_A_GIT_REPO`, `DIRTY_TREE` (because the run never commits, `git diff` against the recorded **baseline SHA** must be a complete record of the run), skill missing, detector CLI unavailable (without it the regression check and before/after delta would be meaningless), no dev server (the only self-recoverable stop). Tool versions are recorded so that differing results in a later run can be explained.
- **Fix subagents are forbidden from self-QA** (they edit and stop; a dedicated review/QA stage follows), must stay inside the target, never commit/stash/reset, never ask questions, and must write a notes file listing files changed + why, **assumptions made in place of asking**, and **what was deliberately left alone**. Each returns ≤10 lines; the orchestrator holds only paths and summaries (context economy).
- **Gate independence:** "A reviewer that watched the fixes being made rationalises them" (skill/references/subagents.md) — review and QA are separate read-only subagents.
- **Code-review gate (round n)**: reviews only `git diff <baselineSha>`; order: (1) correctness (broken component, dropped prop/handler, orphaned CSS variable, dangling class), (2) **deterministic regression gate** — re-run the detector with `--compare` to the baseline; *every newly introduced anti-pattern is blocking*, (3) design-system fidelity (hard-coded values where tokens exist), (4) scope (files outside target that no stage justified). Line 1 is exactly `Verdict: PASS|FAIL`.
- **Finding identity for regression comparison = rule id + file + snippet, deliberately not line number** (detect.mjs `keyOf`), so edits that shift lines don't masquerade as new regressions. Advisory findings never gate.
- **Detector trust:** the author measured the *same page* returning 1, 0 and 41 findings from three ways of invoking the same detector, each failing **silently** with exit 0; hence a dedicated, smoke-tested toolchain (verified by scanning a known-bad page, not by file presence) and a `trustworthy` flag — **a zero from a scan that could not look is reported as a gate that did not run, never as clean**.
- **Browser-QA gate** (skill/references/qa.md), never edits source: (1) **breakage gate first** — FAIL and stop if HTTP ≥400, empty shell (no body text and <10 elements), uncaught exception or framework error overlay; quote the console error verbatim for the repair round; (2) before/after screenshots at 1280×800 and 390×844 with *specific* deltas (e.g. a hero headline shrinking from 64 px to 40 px, rather than a vague claim of extra polish), blocking = disappeared content, clipped/overflowing text, horizontal scroll at 390 px, overlap, collapsed contrast; (3) interaction states for every interactive element — hover, **focus driven by the keyboard (Tab), not `.focus()`, because `:focus-visible` only matches keyboard focus** and the author reports a missing focus ring as the most common regression introduced by colour or polish passes; active, disabled; (4) **animation trace via `document.getAnimations()`** after triggering the interactions the animate stage claims — blocking if a claimed focal animation never fires or a routine interaction exceeds 1000 ms; plus reduced-motion check. **False-positive traps called out:** a backgrounded tab freezes `document.timeline`; headless capture doesn't advance the animation clock; `getTiming().easing` reports the animation-level easing (`linear`) even when keyframes carry the real curve. A check that could not be run is never reported as PASS, and an uncompared screenshot never counts as a comparison.
- **Loop:** if either gate has blocking findings and n < 3, dispatch **one targeted repair subagent** against exactly those findings — *not* a re-run of the five refine commands, which would thrash the diff (each stage has no memory of the previous round and may undo the others). The repair agent must preserve the recorded design intent; if a finding cannot be fixed without discarding it, **leave it and say so** — an explicit unfixed entry is preferred over a silent revert. Exit when both gates are clean or after round 3; remaining findings go into the report verbatim under a *Left unfixed* heading; if round 3 ended with open findings, *lead* with that.
- **Git policy:** never commits, never stashes; tells the user `git checkout -- .` discards everything. Artifacts go to `.impeccable-flow/runs/<timestamp>/` (00-preflight.json, 01-audit.md, 02-critique.md, 02-detect-baseline.json, 03-fix-<cmd>.md, 04-review-r<n>.md, 05-qa-r<n>.md, shots/before|after-r<n>/, REPORT.md) and are added to `.git/info/exclude`.

**Strengths:** the most rigorous *verification* gates found (breakage gate, keyboard-driven focus, runtime animation trace, trustworthy-detector flag, line-number-independent finding identity, introduced-anti-pattern = blocking); clear separation of fixer and checkers; targeted repair rounds with an explicit left-unfixed exit; disciplined artefact layout.
**Weaknesses/gaps:** fixes are batched by *dimension* (five large passes) rather than per finding, so attribution of a regression to a specific change requires the notes files; no commits → no per-fix revert; zero prompts means taste decisions are made without the user; no human-in-the-loop severity check; no license; unproven in the wild; depends on impeccable for all design judgment.
**Adopt:** refuse-rather-than-degrade preflight (git repo, clean tree, baseline SHA, working detector, running app); fix agents forbidden from self-certifying; read-only gates in parallel; breakage gate first; keyboard-driven focus checks; `getAnimations()` trace with the three capture traps; finding identity = rule + file + snippet; `trustworthy` flag on every automated check; targeted repair (only the blocking list) with ≤3 rounds and a verbatim *Left unfixed* section; fix notes recording assumptions and deliberately-untouched items.

### 2.6 prembobby39-gif/uimax-mcp — `review_ui` → fix everything → `verify_fixes` report card

- **What it is:** An MCP server (37 tools) that gathers deterministic evidence (Puppeteer screenshot, axe-core, Lighthouse, Web-Vitals via Performance API, an 18-check SEO audit, an AST/regex code scanner with ~25 rules) and returns it with an expert-review prompt; Claude Code then writes the review and, per the README, applies every fix automatically, and `verify_fixes` re-runs everything and prints a before/after report card. Small project (10★, created 2026-03-25, last push 2026-03-29).
- **URL:** https://github.com/prembobby39-gif/uimax-mcp (commit `66a3819bf93b67043c35d410b1b009e5055a9646`, v0.9.0).
- **License:** MIT.
- **Files read:** `README.md` (tools, pipeline, report card), `CHANGELOG.md` (0.8–0.9), `src/tools/verify-fixes.ts` (full), `src/prompts/review.ts` (full: review, responsive, semantic-compare, quick-design prompts), `src/utils/grading.ts` (thresholds, code-quality penalty), `src/tools/review-history.ts` (finding identity, verdict, trend direction), `src/utils/pixel-diff.ts`, `.github/actions/uimax-review/action.yml` (budget gates), `.uimaxrc.example.json`.

**Mechanics.**
- **Loop:** `review_ui` (evidence + methodology prompt) → model writes findings in the format `[SEVERITY] Category: Title / Impact / Current / Recommendation / Implementation` with CRITICAL (blocks users / WCAG A) · HIGH (significant UX degradation / WCAG AA) · MEDIUM · LOW → model fixes everything, critical issues first (batch, no per-fix verification) → `verify_fixes` (re-run full audit) → verdict **improved / regressed / mixed / unchanged** + per-section grade transitions (e.g. `D → B+ (+22)`) + issue summary. Every review auto-saves to `.uimax-reviews.json`; `save_baseline`/`compare_to_baseline`, `review_diff`, `get_review_stats` give history.
- **Report card:** five sections (Accessibility, Performance, Best Practices, SEO, Code Quality) mapped from 0–100 to a 13-tier letter scale (A+ ≥97 … D- ≥60, F <60) (src/utils/grading.ts). Code-quality score = 100 − 5 × (10·critical + 5·high + 2·medium + 1·low) / max(1, 0.5·files) (normalised by file count).
- **CI gate:** a GitHub Action with budget inputs (min performance/accessibility/SEO score, max axe violations, optional fail-on-regression vs baseline) that posts/updates a PR comment.
- **`semantic_compare`:** before/after screenshots + pixelmatch diff (threshold 0.1) + the stated intent → model answers "does this edit look like what was requested?" with *intent verification* (map every change to the request; flag unrelated changes and unaddressed parts), *regression detection* (areas outside the request must not change; check layout shift, alignment, stacking, missing states) and 1–5 ratings for intent match, regression risk, overall quality.

**Critical observations (verified in source).**
1. **`verify_fixes` compares counts, not identities**: `resolved = max(0, before − after)`, `newlyIntroduced = max(0, after − before)` (src/tools/verify-fixes.ts `computeIssuesSummary`). Five fixes plus five new defects therefore report zero resolved and zero new — net counting hides regressions. Only `review_diff` matches findings by key, and that key includes the **line number** (`rule:severity:file:line`, review-history.ts `findingKey`), so any edit that shifts lines reports spurious new and resolved issues. Contrast impaccable-agent's rule+file+snippet identity (§2.5).
2. **No noise tolerance:** any score delta flips the direction to improved or regressed (`classifyTrendDirection`; `delta > 0`), although Lighthouse performance scores vary between identical runs (Lighthouse's own variability doc, §2.8.4: the median of 5 runs is only about twice as stable as a single run) — the verdict can be pure noise.
3. Letter grades on top of Lighthouse/axe numbers add precision theatre (13 tiers) without adding information; design quality itself is not graded at all (only a11y/perf/SEO/code).
4. Automatic application of every fix with no per-fix verification, no commit/revert policy, no stop rule.
5. The review prompt casts the model as an expert from well-known product companies — unverifiable authority; its creative-improvements section invites adding features during a fix pass.

**Strengths:** strong deterministic evidence bundle (axe, Lighthouse, CWV, SEO, AST) feeding the LLM; persisted review history; CI budget gates; the semantic-compare prompt's intent verification plus its requirement that untouched areas stay visually identical; the finding template (Impact / Current / Recommendation / Implementation).
**Weaknesses:** see the critical observations; no independence (same context reviews, fixes and judges); no design-quality rubric; no false-positive handling beyond rule on/off config.
**Adopt:** deterministic-evidence bundle per review; persisted history + `review_diff`; CI budget gates as an *outer* loop; semantic-compare's intent-mapping + unrelated-change flagging; finding template. **Do not adopt:** count-based resolution, line-number identity, tolerance-free verdicts, batch fix-everything.

### 2.8 Other notable loop sources found by search (agent repos + vendor docs)

#### 2.8.1 obra/superpowers (MIT, ~294k★; HEAD `8ca22dba9a94`) — generic but the most mature *fix-loop* contract

Read: `skills/receiving-code-review/SKILL.md`, `skills/verification-before-completion/SKILL.md`, `skills/subagent-driven-development/SKILL.md` §§ "The Task Loop", "4. The fix loop", "5. Complete the task", "Final Review". (Designpowers explicitly follows this plugin's architecture.)
- **Receiving review = verify before implementing** (the guard against fixing what is not broken): read all → restate → verify against codebase reality → evaluate for *this* codebase → respond with technical acknowledgement or reasoned push-back → implement **one item at a time, testing each**. If any item is unclear, implement *nothing* until clarified (items may be related). For external reviewers check: correct for this codebase? breaks existing functionality? reason for current implementation? context the reviewer lacks? Push back when the suggestion breaks things, lacks context, violates YAGNI, or conflicts with the owner's prior decisions; if it can't be verified, say so and ask. Order: blocking → simple → complex; verify no regressions after each. No performative agreement.
- **Verification before completion** — no claim of completion without verification evidence produced fresh in the same turn: identify the command that proves the claim, run it fresh and in full, read the output, only then claim. Regression tests must pass a **red–green–revert check** (write → pass → revert the fix → must fail → restore → pass). An agent's claim of completion is checked against the VCS diff, never accepted from its report.
- **Fix loop (subagent-driven development):** fresh implementer per task; each task gets a review (spec compliance **and** quality, both verdicts required; implementer self-review never substitutes). Only spec failures, Critical/Important findings, or confirmed ⚠ gaps enter the loop; **Minor findings never enter the loop** — they are ledgered for the final review's triage (an unread roll-up would amount to silently discarding them). A round = one fix dispatch + one **scoped re-review** of only the fix diff (verdict per finding ADDRESSED / NOT ADDRESSED + new breakage *in the fix diff only*; out-of-scope observations are deferred, never extend the loop). **Max 5 rounds/task**: rounds 1–3 resume the original implementer; rounds 4–5 hand over to a fresh implementer on a more capable model (three failed resumes are taken as a sign that the implementer cannot see its own problem). **Breaker at the cap:** the controller adjudicates each open finding — reviewer wrong → park with ruling; real but not load-bearing → park; real and load-bearing → smallest unblocking change, ruled and ledgered. "Adjudicate only at the cap"; every adjudication is a ledger entry; silent discard forbidden. The controller never fixes code itself (its fixes would skip review). Final whole-branch review → **one** fix dispatch with the complete list (per-finding fixers cost more than all tasks combined in a real session), exactly one scoped re-review, residuals adjudicated — no second wave.

#### 2.8.2 Yeachan-Heo/oh-my-claudecode (MIT, ~39.5k★; HEAD `dc7ba1da4669`) — `visual-verdict` and the Ralph loop's *feedback baseline*

Read: `skills/visual-verdict/SKILL.md`, `commands/visual-verdict.md`, `skills/ralph/SKILL.md` (verification sections).
- `visual-verdict`: compares a generated screenshot with ≥1 reference image and returns **strict JSON** `{score 0–100, verdict pass|revise|fail, category_match, differences[], suggestions[], reasoning}`; **pass threshold 90**; below it, keep editing and re-run the verdict before any other visual review; the VLM verdict is authoritative and **pixel diff is only a secondary debug aid** to localise hotspots. Weakness: no iteration cap and nothing stops the same context from grading its own work.
- Ralph's **feedback baseline** (general, but the cleanest rule found against fixing what is not broken): before any work, record normalised signatures of *pre-existing* failures; afterwards, a failure already in the baseline is environment noise — warn, never block, **never repair it inside this run** — unless it points at a file the current story touches (then it is treated as new). Acceptance criteria can be amended only through an evidence-preserving ledger, never silently weakened. Reviewer tier scales with change size (<5 files/<100 lines standard; >20 files or security/architecture → strongest model).

#### 2.8.3 Anthropic — Claude Code "Best practices" (official docs, https://code.claude.com/docs/en/best-practices, read 2026-10-01)
- *Give Claude a way to verify its work* (section title): for UI, paste the design, have Claude **screenshot the result, compare with the original, list differences and fix them**; a check is anything returning a readable pass/fail (tests, build exit code, linter, fixture diff, browser screenshot vs design).
- Four gate strengths: in the same prompt; a session `/goal` (a separate evaluator re-checks every turn); a **Stop hook** (deterministic script blocks the turn from ending until it passes); a **second-opinion verification subagent** "so the agent doing the work isn't the one grading it".
- Claude should present evidence (test output, commands and results, screenshots) instead of asserting success. Writer/Reviewer sessions: a fresh context reviews better because it is not biased toward code it has just written.
- **Over-fixing warning:** a reviewer asked to find gaps will usually find some even in sound work; chasing every finding leads to over-engineering — tell the reviewer to flag only gaps affecting correctness or the stated requirements, and treat the rest as optional.
- After two failed corrections on the same issue, start a fresh session with a better prompt (context polluted by failed approaches). Checkpoints are not a replacement for git.
- (Older community copies of this guide claimed results improve markedly after 2–3 screenshot iterations; the current page gives no number — treat the 2–3 figure as [historical, unverified in current docs].)

#### 2.8.4 Visual-regression vendor practice (deterministic re-verification)
- **Playwright `toHaveScreenshot`** (https://playwright.dev/docs/test-snapshots; API https://playwright.dev/docs/api/class-pageassertions): waits until **two consecutive screenshots are identical** before comparing; `animations: "disabled"` by default (finite animations fast-forwarded, infinite ones reset); `mask` dynamic regions; `stylePath` to hide volatile elements; `threshold` (YIQ colour distance, default 0.2), `maxDiffPixels`, `maxDiffPixelRatio`; baselines are per browser+platform because rendering varies with OS, version, settings, hardware, power source and headless mode; update baselines only deliberately (`--update-snapshots`).
- **Chromatic baselines** (https://www.chromatic.com/docs/branching-and-baselines/): a baseline is the *last accepted* state; new snapshots become baselines only when a reviewer accepts them; denied/unreviewed snapshots are ignored and the previous baseline is carried forward; baselines are tracked per branch.
- **Lighthouse variability** (https://github.com/GoogleChrome/lighthouse/blob/main/docs/variability.md): seven variability sources (page nondeterminism, local network, tier-1 network, server, client hardware, resource contention, browser nondeterminism); **median of 5 runs is about twice as stable as 1 run**; run serially on dedicated hardware.

#### 2.8.5 Smaller/unvetted examples (pattern evidence only)
- `alexmchughdev/lookout` (MIT, 8★) and its write-up (https://dev.to/alexmchughdev/how-i-built-an-open-source-visual-qa-tool-after-every-ai-agent-i-tried-failed-3nf7): autonomous agents lost the objective after 5–6 steps and hallucinated on-screen elements; the response was **deterministic scripted actions + a vision model asked one specific yes/no question per screenshot** (specific wording outperformed generic). No accuracy numbers published.
- `ibnuhnf/kage-bunshin-ui-ux` (no license, created 2026-10-01, 0★): clone loop (render, compare, correct atomically, repeat) with numeric convergence **SSIM ≥ 0.95, MAE ≤ 5.0 (8-bit)** — only meaningful for *reproduce-a-reference* tasks, not for open design critique.
- `lackeyjb/playwright-skill` (MIT, ~3.2k★): generic skill that writes and runs Playwright scripts and returns screenshots and console output — tooling, no loop policy.

### 2.9 Research evidence that constrains loop design (primary papers / NN/g)

- **Multiple independent evaluators, aggregated after** — Nielsen, *The Theory Behind Heuristic Evaluations* (https://www.nngroup.com/articles/how-to-conduct-a-heuristic-evaluation/theory-heuristic-evaluations/): averaged over six projects, single evaluators found only 35 % of the usability problems; different evaluators find different problems; use about five, at least three; each evaluator inspects alone and evaluators may communicate only after all evaluations are complete ("to ensure independent and unbiased evaluations"); go through the interface at least twice (flow first, then specific elements). The current how-to (https://www.nngroup.com/articles/how-to-conduct-a-heuristic-evaluation/) adds: record one observation per line with its heuristic, 1–2 h sessions, then synthesise and debrief (where do we agree/disagree, which issues are most detrimental). The 5-evaluator coverage figure (~75–85 %) is read off a chart — [exact value unverified].
- **Severity needs ≥3 independent raters** — Nielsen, *Severity Ratings for Usability Problems* (https://www.nngroup.com/articles/how-to-rate-the-severity-of-usability-problems/): severity combines frequency, impact, persistence (+ market impact); scale 0 not a problem, 1 cosmetic, 2 minor, 3 major, 4 catastrophe; collect ratings independently *after* the evaluation; single-evaluator severity is "too unreliable to be trusted"; the mean of three evaluators is satisfactory for many practical purposes.
- **LLM heuristic evaluation is useful but imprecise, and degrades over iterations** — Duan, Warner, Li, Hartmann, *Generating Automatic Feedback on UI Mockups with LLMs*, CHI 2024 (https://dl.acm.org/doi/10.1145/3613904.3642782; PDF https://people.eecs.berkeley.edu/~bjoern/papers/duan-heuristic-chi2024.pdf): GPT-4 precision 0.603 vs 0.829 for an average human evaluator, recall 0.380 vs 0.336, F1 0.466 vs 0.478 (Table 2); on initial UIs 52 % of suggestions accurate / 28 % partially / 20 % not; **after designers edited the UIs, later rounds fell to 39 % / 26 % / 35 %**, helpful-or-very-helpful 47 % → 33 % (§5.3) — i.e. once the obvious problems were fixed, a larger share of the LLM's later suggestions was judged inaccurate or unhelpful (more false positives per round); "Aesthetic and Minimalist Design" was the worst-performing guideline for accuracy; expert inter-rater reliability on the suggestions was low (0.155 accuracy, 0.085 helpfulness); of all violations 9 % were found by GPT-4 only, 29 % by both, 62 % by humans only.
- **Grounding and examples improve LLM critique** — UICrit (Duan et al., UIST 2024, https://arxiv.org/abs/2407.08850): 3,059 critiques on 983 mobile UIs from seven designers; few-shot and visual prompting gave a 55 % gain in LLM UI-feedback performance. Iterative visual prompting with bounding-box refinement (https://arxiv.org/abs/2412.16829) closed the gap to human performance by 50 % on one metric.
- **Synthetic HE can out-recall individual humans but misses cross-screen and convention issues** — *Synthetic Heuristic Evaluation* (https://arxiv.org/abs/2507.02306): 73 % / 77 % of issues found on two apps vs 57 % / 63 % for experienced humans; weak on recognising some UI components/conventions and on violations spanning multiple screens; strong on layout issues.
- **MLLM judges only partially track human perception** — *MLLM as a UI Judge* (https://arxiv.org/abs/2510.08783): GPT-4o, Claude and Llama on 30 interfaces approximate human preferences on some factors and diverge on others.
- **Atomic changes** — Google engineering practices, *Small CLs* (https://google.github.io/eng-practices/review/developer/small-cls.html): one self-contained change; smaller changes are reviewed faster and more thoroughly, introduce fewer bugs and are easier to roll back; keep refactors separate from fixes.

## 3. Cross-source synthesis

### 3.1 Consensus — the loop that every mature source converges on

Read across gstack, impeccable, designpowers, impaccable-agent, superpowers and the vendor docs, the same skeleton recurs. Where sources differ it is in *granularity* and *budget*, not in the order of steps.

Shared principles stated almost verbatim by several sources:
- **Evidence before claims** (designpowers verification-before-shipping; superpowers verification-before-completion; Anthropic best practices; gstack Important Rule 2; agent-browser dogfood guidance).
- **The doer must not be the grader** (Anthropic second-opinion subagent; impaccable-agent independent gates; impeccable reviewer spawned without the builder's transcript; superpowers implementer self-review never replaces task review).
- **A gate that could not run is not a pass** (impaccable-agent `trustworthy:false`; gstack outside-voice and qa rules; impeccable degraded-banner rule; designpowers coverage line).
- **Bounded loops** (every mature source has a numeric ceiling; the only unbounded loop found — oh-my-claudecode's visual-verdict, which keeps editing until the score reaches 90 — is also the only one that lets the same context grade itself).

### 3.2 Conflicts and proposed resolutions

1. **One fix at a time vs batched fixes.** gstack commits and re-tests each finding individually; superpowers' receiving-review also implements and tests one item at a time. But impeccable batches fixes between at most two inspection rounds instead of screenshotting every tweak, impaccable-agent runs five whole-dimension passes then one targeted repair batch, and superpowers' final review dispatches *one* fixer for the whole list because per-finding fixers were too expensive. **Resolution:** separate *attribution* from *judgment*. Each finding gets its own minimal change and its own commit (cheap; preserves revert/bisect), followed by the cheap deterministic re-tests (console, a11y-tree diff, detector compare, targeted screenshot of the affected region/viewport). The expensive judgment re-review (fresh reviewer, full viewport set) is batched once per round and scoped to the listed findings. Where findings interact (spacing → type → colour → motion), order the batch by that dependency chain (impaccable-agent's rationale) so later fixes are not invalidated.
2. **Commit per fix vs never commit.** gstack commits each fix; impaccable-agent never commits and uses `git diff` against the baseline SHA as the record. **Resolution:** default to atomic commits on a dedicated branch/worktree (Google's Small CLs guidance: easier review and rollback); if the user forbids commits, keep per-finding patch files or checkpoints and the baseline SHA so any single fix can still be reverted. Either way the clean-tree precondition holds.
3. **Problems vs prescriptions.** OneRedOak tells the reviewer to describe problem and impact, not the technical fix; gstack, uimax and designpowers demand exact values. **Resolution:** a finding has separate fields — *problem + impact + evidence* (neutral, observable) and *recommendation* (specific, but advisory). The black-box evaluator fills the first; the recommendation may come from the evaluator or the fixer; the fixer is free to choose a different implementation that resolves the observed problem.
4. **Does the evaluator read source?** gstack's auditor and agent-browser's dogfood tester must not; OneRedOak's reviewer reads the diff and PR intent first; impeccable's Assessment A reads source *and* looks at the page; gstack's outside voices review source with file:line. **Resolution:** two distinct roles — a black-box UX evaluator that sees only the rendered app (protects against anchoring on the implementer's intent), and a white-box code evaluator that reports file:line (tokens, states, a11y markup). Fixers read source. Reviewers of fixes get the diff *and* the rendered evidence but never the fixer's narration as evidence.
5. **Severity scales.** gstack design: high/medium/polish; gstack qa & agent-browser: critical/high/medium/low; impeccable: P0–P3 per issue + Nielsen 0–4 per heuristic; designpowers: critical/major/minor/note; OneRedOak: blocker/high/medium/nit; NN/g & the CMU lecture: 0–4 per problem from frequency, impact, persistence. **Resolution:** record the lecture/NN/g *problem severity 0–4* with its three factor ratings as the primary field (rated independently by ≥2–3 evaluators and averaged, since single-rater severity is unreliable), derive priority P0–P3 from it (4→P0, 3→P1, 2→P2, 1→P3, 0→drop), and derive merge gating (P0/P1 block). Keep *per-heuristic* 0–4 scores only as a report-level health summary (impeccable), and keep *confidence* and *fix tier* as separate fields — they answer different questions.
6. **Stopping rules.** Caps found: gstack 30 design fixes / 50 qa fixes with a >20 % risk stop; impaccable-agent 3 review rounds; impeccable 2 rounds plus an immediate stop when a round resolves nothing; ios-fix 3 attempts; superpowers 5 rounds per task with escalation from round 4; design-html 10 user-driven iterations; visual-verdict none. The Duan et al. CHI 2024 data (the share of suggestions rated accurate falls from 52 % to 39 % and the share rated not accurate rises from 20 % to 35 % in later rounds) argues for *short* judgment loops. **Resolution:** per finding ≤3 attempts, then revert + defer/escalate; per run ≤2 judgment rounds unattended (a third only if deterministic gates still fail), immediate stop on a zero-progress round, risk check every 5 fixes, hard cap 30 fixes; taste-only rules get exactly one pass. User-attended sessions may extend, but the user decides explicitly.
7. **Score thresholds vs finding-level exit.** visual-verdict exits at a VLM score ≥ 90 and uimax reports grade transitions; impeccable and impaccable-agent exit on finding-level verdicts and deterministic gates. **Resolution:** never use an LLM/VLM score as the sole exit criterion (scores drift and degrade across rounds); exit on (a) all P0/P1 findings verified-resolved or explicitly ruled on, (b) zero introduced deterministic regressions, (c) fresh-reviewer disposition. Report scores as context, like-for-like only, with a tolerance band for noisy metrics (Lighthouse median of ≥5 runs).
8. **Fix eligibility: autonomy vs approval.** impaccable-agent runs with zero prompts and lets fix agents infer intent; gstack plan review asks per issue and auto-fixes only a tiny mechanical set; impeccable asks targeted questions before fixing; designpowers defaults to Direct mode. **Resolution:** offer Direct and Auto modes; in Auto, only AUTO-FIX-tier findings and P0/P1 findings with unambiguous fixes run unattended, all taste/ASK-tier items are batched into one question set, and designpowers-style pause conditions are mandatory.
9. **Persona simulation as evidence.** designpowers runs synthetic persona walkthroughs after the fix round and feeds them into verification as evidence; impeccable lists persona red flags; gstack keeps a goodwill meter. The research (UXAgent; MLLM-as-judge; Duan et al.) shows simulated judgments diverge from humans on some dimensions. **Resolution:** keep persona walkthroughs (they catch predictable barriers cheaply) but label them *simulated*, never count them as user evidence, and route any claim about real users to empirical methods.
10. **Cross-project memory.** gstack's taste profile (with decay) biases future generations; designpowers deliberately never feeds its design memory back into a project to avoid cross-client contamination. **Resolution:** project-scoped decisions (DESIGN.md Decisions Log, accepted-with-reason waivers, debt register) steer the loop; cross-project memory is opt-in and advisory only.

|---|---|---|

### 3.4 Gaps no source fills (where UI-Evaluator can add value)

1. **Lecture-grade heuristic-evaluation records.** No source computes severity from frequency × impact × persistence, collects severity independently from ≥3 evaluators and averages it, or records ease-of-fix per finding. designpowers and impeccable tag heuristics; gstack does not.
2. **Measured evaluator reliability.** No source checks inter-run or inter-evaluator agreement of its LLM judges (e.g. the same page evaluated twice, or three evaluators' overlap). Duan et al. and NN/g show this matters; we can measure it cheaply (overlap of finding identities, agreement on severity).
3. **Real user data in the loop.** Only designpowers plans usability tests; nobody ingests analytics, session recordings, support tickets or A/B results as findings with provenance, and none distinguishes correlation from causation when using such data.
4. **Cognitive walkthrough as a first-class pass** exists only in designpowers' heuristic evaluator; gstack's mindless-choice audit and trunk test are partial substitutes.
5. **Unified evidence pointers.** Each source uses a different mix of screenshot paths, refs, selectors and file:line. A single evidence schema (page URL + viewport + state + selector/ref + screenshot crop + optional file:line) would make findings machine-checkable across runs.
6. **Taste-rule calibration against humans.** No source validates its AI-slop/taste rules against human judgments; impeccable's own issues show even mechanical rules misfire. Taste findings should carry lower default confidence until calibrated (Duan et al.: "Aesthetic and Minimalist Design" had the worst accuracy).

## 5. Open questions / things to verify later

1. **How many LLM evaluators buy real independence?** NN/g's 35 % single-evaluator figure and its 3–5 recommendation come from human evaluators in Nielsen's own projects. We do not know whether 3 runs of one model, 3 lenses on one model, or 3 different models approach human-panel coverage. Plan: on a benchmark set (e.g. UICrit UIs, https://arxiv.org/abs/2407.08850), measure finding overlap and severity agreement across those three set-ups before fixing LOOP-015's default.
2. **Calibrating LLM severity against humans.** LOOP-025 averages ≥3 ratings, but LLM ratings may be correlated in ways human ratings are not. Measure the correlation of LLM severity with expert severity (UICrit has quality ratings) and decide whether averaging is valid or whether a calibration offset is needed.
3. **Evaluator noise across rounds.** Duan et al. report accuracy falling in later rounds; is that the model, or the remaining problems getting subtler? Run a controlled test: re-evaluate an unchanged UI twice and an improved UI once, and compare precision, to set the round budget (LOOP-049) empirically.
4. **Thresholds for "no visual change".** LOOP-062 needs per-viewport pixel-diff thresholds (agent-browser default colour threshold 0.1; Playwright 0.2 YIQ) and a policy for anti-aliasing and font-rendering noise. Determine on our own fixture pages.
5. **Commit policy UX.** Some users will refuse per-fix commits (impaccable-agent's stance). Verify that per-finding patch files or Claude Code checkpoints give equivalent revert/bisect ability; checkpoints do not track changes made through Bash (Anthropic docs warning).
6. **Using impeccable's detector.** gstack downloads impeccable's engine binary only after consent and checksum-pins it; impeccable is Apache-2.0. Decide whether UI-Evaluator shells out to a user-installed detector (gstack model), vendors rules (needs NOTICE + change statement), or writes its own DOM checks. Given impeccable issues #881/#882/#867/#883, any detector must be wrapped by LOOP-023's confirmation step.
7. **5-evaluator coverage number.** The NN/g theory page states the 35 % single-evaluator figure in text; the commonly quoted ~75 % (or ~85 %) for five evaluators comes from its chart — [unverified exact value]; cite only the textual claims until checked against Nielsen & Molich (1990) / Nielsen (1992) originals.
8. **"2–3 screenshot iterations" claim.** Older copies of Anthropic's best-practices guide said outputs look much better after 2–3 iterations; the current page (2026-10-01) has no number. Treat as historical unless a dated Anthropic source is found.
9. **designpowers maintenance.** Issue #35 asks why updates stopped; last push 2026-06-23. Before depending on any of its files, re-check activity.
10. **impaccable-agent licensing.** No license file. If we want to reuse its scripts (`detect.mjs` comparison, QA protocol), ask the author for a license; until then only re-implement ideas.
11. **Real user feedback ingestion.** None of the surveyed loops ingests analytics, session replays, support tickets or A/B results. Our design must define provenance, sampling and causal caveats (correlation ≠ causation) for such inputs — likely in another research note (empirical methods), then wired in at synthesis (step 4) with `detection method = empirical`.
12. **URL-target fingerprints.** impeccable's fingerprint only covers local files; URL targets stay "current" until closed. We need a URL fingerprint (commit SHA + build id + DOM hash of key regions?) for LOOP-059 — design and test.
13. **gstack's goodwill meter and design-fix risk weights** are presented by the skill itself as heuristics (the goodwill scores are described as heuristic rather than measured; Rule 15 calls the risk formula a heuristic). Before relying on their numbers beyond LOOP-047, check in our own runs whether they predict anything (e.g. reverts, user complaints).
14. **Detector-free environments (native apps).** impeccable notes its detector reads HTML/CSS only; for iOS/Android the reviewer's floor check is the only mechanical gate. If UI-Evaluator targets native, LOOP-023/045 need native evidence sources (accessibility tree from the simulator, gstack ios-qa state snapshots).
