### 2.1 nextlevelbuilder/ui-ux-pro-max-skill ("UI/UX Pro Max")

- **What it is:** the most-starred design skill on GitHub (132,330★ on 2026-10-01, `gh api repos/nextlevelbuilder/ui-ux-pro-max-skill`). A retrieval-backed design-intelligence skill: a SKILL.md that tells the agent to call a local, stdlib-only Python BM25 search CLI over ~15 CSV datasets, plus a `--design-system` mode that stitches the top hits (product → style → palette → font pairing → landing pattern → reasoning rule) into one recommended design system. Six sibling skills ship in the same repo (`ui-styling`, `design-system`, `design`, `brand`, `banner-design`, `slides`).
- **URL:** https://github.com/nextlevelbuilder/ui-ux-pro-max-skill (HEAD `09170ee`, 2026-09-27)
- **License:** MIT (`LICENSE`, © 2024 Next Level Builder). Caveat: `.claude/skills/ui-styling/LICENSE.txt` is Apache-2.0 while its SKILL.md frontmatter says MIT/author "claudekit"; bundled `canvas-fonts/*.ttf` are SIL OFL. Data and ideas can be adapted with attribution (MIT notice must be retained for copied text/data).
- **Files read:** `.claude/skills/ui-ux-pro-max/SKILL.md` (full), `references/quick-reference.md` (full, all 10 categories), `references/pro-rules.md` (full, incl. the pre-delivery checklist it calls canonical), every CSV schema + sampled rows (`styles.csv`, `colors.csv`, `typography.csv`, `products.csv`, `ui-reasoning.csv`, `ux-guidelines.csv`, `charts.csv`, `motion.csv`, `landing.csv`, `app-interface.csv`), `data/catalog-summary.json`, `data/data-provenance.json`, `scripts/core.py` (BM25 class), `scripts/reasoning_contract.py`, `scripts/tests/fixtures/relevance-thresholds.json` + `relevance-cases.json`, `docs/journals/260812-1844-search-data-quality-planning.md`, `docs/journals/260813-1800-search-data-overhaul-completion.md`, `.claude/skills/design-system/scripts/validate-tokens.cjs` + `html-token-validator.py` + `references/token-architecture.md`, `.claude/skills/ui-styling/SKILL.md` (head). I also **ran** `scripts/search.py "developer tool CLI documentation" --design-system -f markdown` to see real output.

**Key content (my words).**
1. *Priority-ordered rule categories* (SKILL.md table): 1 Accessibility (CRITICAL) → 2 Touch & Interaction (CRITICAL) → 3 Performance → 4 Style Selection → 5 Layout & Responsive → 6 Typography & Color → 7 Animation → 8 Forms & Feedback → 9 Navigation → 10 Charts & Data (LOW). Each category lists "must-have" checks and anti-patterns.
2. *Query contract*: choose the smallest search mode (design-system for new pages; one `--domain` for a targeted bug; `--stack` for implementation); 2–5 meaningful terms; verify the returned domain/top hit; retry once; if still empty, say so and label fallback guidance as such, and never persist unverified output. Stack must be detected from the project (package.json, pubspec.yaml, etc.), never assumed.
3. *Persisted design system*: `--persist` writes `design-system/<slug>/MASTER.md` + `pages/<page>.md` overrides; page file overrides master; never `--force` overwrite without explicit user authorization. (A master-plus-overrides memory pattern comparable to interface-design's `system.md`.)
4. *Design dials*: `--variance`, `--motion`, `--density` (1–10). Density maps to spacing scales: low = 24–96px, mid = 16–64px, high (dashboard) = 8–32px.
5. *quick-reference.md* (221 one-line rules, each tagged with its claimed origin: Apple HIG / Material / WCAG 2.2). Concrete numbers I would keep (after re-verifying against the primary sources in sibling notes): text contrast 4.5:1 (3:1 large); focus ring 2–4px; touch target 44×44pt iOS / 48×48dp Android, ≥8px gap; web pointer target 24×24 CSS px (WCAG 2.2 AA 2.5.8); CLS < 0.1; per-frame work < ~16ms; feedback within 100ms of a tap; body ≥16px on mobile; line-height 1.5–1.75; measure 65–75 chars (desktop 60–75, mobile 35–60); breakpoints 375/768/1024/1440; 4/8-pt spacing; z-index scale 0/10/20/40/100/1000; `min-h-dvh` over `100vh`; exit animation ≈60–70% of enter duration; stagger 30–50ms per item; press scale 0.95–1.05; don't linger below opacity 0.2; animate 1–2 key elements per view; disabled opacity 0.38–0.5; toasts auto-dismiss 3–5s; validate on blur not keystroke; error summary focused after failed multi-error submit; virtualize lists ≥50 items; no pie/donut beyond 5 categories; chart data marks ≥3:1, chart text ≥4.5:1; aggregate >1000 points.
6. *pro-rules.md* (native/mobile-scoped): icon discipline (no emoji as structural icons, one icon family, consistent stroke 1.5 or 2px, filled vs outline by hierarchy level, icon sizes as tokens, meaningful icons ≥3:1 non-text contrast); press feedback within 80–150ms without changing layout bounds; dark-mode contrast tested separately; scrims checked against the actual background behind them; safe areas; and the **canonical Pre-Delivery Checklist** (Process / Visual Quality / Interaction / Light-Dark / Layout / Accessibility; 39 checkboxes, e.g. test at 375px and landscape, reduced-motion + largest Dynamic Type, both themes tested, sticky UI never obscures focus, drag has a button alternative, auth allows paste/password managers).
7. *Datasets*: 88 styles (50 active / 29 supplemental / 9 deprecated), 192 product types × (palette, reasoning row), 74 font pairings, 1,934 Google Fonts (license-checked), 105 curated icons (Phosphor upstream), 17 GSAP motion presets, 25 chart types, 22 stack files (1,271 stack rules), 119 UX guidelines, 32 app-interface rules, 44 React performance rules (`data/catalog-summary.json`).
8. *Validator*: `design-system/scripts/validate-tokens.cjs` greps source for hard-coded hex colors and px/rem values that should be tokens — a cheap static "token discipline" check.
9. *Self-evaluation*: unusually, the maintainers built a human-judged retrieval relevance corpus (90 cases) with regression floors (P@1 ≥ 0.763, MRR@3 ≥ 0.836, nDCG@3 ≥ 0.837, negative abstention ≥ 0.912, design-system coherence ≥ 0.719 — `scripts/tests/fixtures/relevance-thresholds.json`). Their own journal concedes that before this work the tests "mostly prove that output is non-empty—not relevant", and that 37 of 122 non-product keywords returned zero hits in their own domain (`docs/journals/260812-1844-search-data-quality-planning.md`). Note this measures *retrieval* relevance, not the visual quality of generated UI.

**Data-quality audit (my own sampling, reproducible).**
- *Palettes are mostly Tailwind defaults.* I compared every hex in `colors.csv` against Tailwind CSS v3.4.17's default palette (`src/public/colors.js`): **1,748 of 2,093 hex values (83.5%) are exact Tailwind defaults, and 178 of 192 "Primary" colors are.** Only 50 distinct primaries exist across 192 product types; the most common are `#2563EB` (blue-600, 17×), `#7C3AED` (violet-600, 16×), `#0F172A` (slate-900, 12×), `#6366F1` (indigo-500, 5×). 31 of 192 primaries fall in the indigo/violet/purple hue band (230–290°) and 78 in blue. This is precisely the Tailwind-indigo default look that anti-slop sources flag (see §2.6, §2.8, and Gesso's `indigo-accent` guard in §2.14). The palettes *are* contrast-checked: only 1 of 192 had a primary/foreground/muted pair below 4.5:1 in my check (`Spatial Computing OS / App`, muted-foreground 1.63:1).
- *Style rows* are rich in fields (keywords, do-not-use-for, CSS hints, a11y requirements, checklist, variables) but several fields are unsupported or wrong: e.g. Glassmorphism is tagged `Performance: cost:low|drivers:none` although `backdrop-filter` is a well-known paint cost; `Conversion-Focused: ✓ High` appears on aesthetic styles with no evidence; the "AI-Native UI" style hard-codes `#6366F1 (AI Purple)` as its accent, i.e. it *prescribes* the most-cited AI-slop color.
- *Typography*: 74 pairings; Inter appears in 8 of them, Space Grotesk in 5, Plus Jakarta Sans in 3 — reasonable variety, but many pairings are the most popular Google Fonts (Poppins + Open Sans, Playfair + Inter).
- *Reasoning rows*: 161 of 192 have empty `Reasoning` and `Confidence`; `Key_Effects` sometimes contains features rather than effects (e.g. Veterinary Clinic → `Pet profile management`). Decision rules are a closed keyword grammar (`reasoning_contract.py`: ~35 `if_*` signals such as `if_luxury` → keyword list).
- *Provenance*: `data-provenance.json` holds only 51 records (52 "official" URLs, e.g. WCAG Understanding docs, GOV.UK error summary, Fluent 2) for >1,000 data rows; most product/palette/style rows are unsourced.
- *What is genuinely useful*: `charts.csv` (each chart type has when-to-use, when-NOT-to-use, data-volume thresholds such as SVG below 1,000 points and Canvas with downsampling above that, and an a11y fallback of a visible data table plus a short trend summary), the WCAG 2.2 additions (focus-not-obscured, dragging alternative, accessible authentication, consistent help, redundant entry), the forms/error rules (GOV.UK-derived error summary), text-layout resilience rules (`overflow-wrap:anywhere`, `min-inline-size:0`, never `word-break:break-all` on prose, `text-wrap: balance` as progressive enhancement), and the motion presets with reduced-motion handling.
- *What is generic*: industry → style/palette mapping (`Trust blue + accent contrast` for SaaS) — this is the mechanism that converges every SaaS onto blue-600 + glass/flat; the output for my dev-tool query was dark slate `#0F172A` + green `#22C55E` + JetBrains Mono headings + `minimal glow` — a stereotypical dev-tool look.

**Strengths.** Broadest rule coverage of any skill reviewed; explicit priority ordering; honest abstention policy (never fabricate output); persistent master/override design memory; a canonical pre-delivery checklist; one of very few repos with a measured (retrieval) evaluation and provenance file; stack-specific rules for 22 stacks.
**Weaknesses.** Taste is retrieved, not reasoned: categorical industry→style/palette lookup produces stereotypes and Tailwind-default colors; most rows lack sources; several numeric "rules" are presented as platform-mandated when they are folk heuristics (e.g. `Smooth Scroll` rated High severity, conflicting with reduced-motion); no visual verification step (no screenshot/DOM check) — the checklist is self-attested; no brand-context elicitation beyond keyword extraction.
**Adopt.** (a) the priority ordering of categories for audits; (b) the abstention rule (label any fallback guidance as such); (c) the master + page-override persistence pattern; (d) selected numeric rules after primary-source verification; (e) charts when/when-not table; (f) WCAG 2.2-era checks; (g) the token-hardcode static check; (h) the idea of a human-judged regression corpus for our own retrieval/rules. **Do not adopt** its palettes or industry→style mapping as defaults.

### 2.2 vercel-labs/web-interface-guidelines (+ `AGENTS.md` and `command.md`)

- **What it is:** Vercel's public, opinionated checklist of web-UI implementation details, framed as the many small decisions that make interfaces succeed, maintained by Vercel (recent PRs come from `johnphamous/*` branches, merged 2026-08-18). Three renderings of the same rules: `README.md` (human prose: 115 bullets across Interactions 28, Animations 10, Layout 7, Content 24, Forms 19, Performance 16, Design 11, plus 14 Vercel-specific Copywriting rules — 129 in total); `AGENTS.md` (107 imperative rules: 72 MUST / 29 SHOULD / 6 NEVER, meant to be dropped into a project so agents follow them while generating); `command.md` (an audit slash-command: ~100 code-level checks + an anti-patterns-to-flag list + a strict output format). `install.sh` copies `command.md` into Claude Code / Cursor / OpenCode / Windsurf / Gemini / Amp command folders.
- **URLs:** https://github.com/vercel-labs/web-interface-guidelines (HEAD `e3d624b`, 2026-08-17; 918★), mirrored at https://vercel.com/design/guidelines (per `install.sh` header).
- **License:** MIT (© 2025 Vercel Labs). Rules can be adapted with attribution.
- **Files read:** `README.md`, `AGENTS.md`, `command.md` (all in full), `install.sh` (first 80 lines), commit log.

**Key content (my words; every rule verified in the files above).**
- *Interactions:* full keyboard operability per WAI-ARIA APG; visible, unobscured focus using `:focus-visible` (group with `:focus-within`), sticky/fixed UI must never cover the focused element; focus trap/move/return per APG; **hit target ≥24px, ≥44px on mobile, expand hit area when the visual is smaller**; mobile `<input>` font-size ≥16px (prevents iOS zoom); never disable zoom; hydration-safe inputs; never block paste; loading buttons keep their label and add a spinner; **spinner/skeleton show-delay ~150–300ms and minimum visible time ~300–500ms** to avoid flicker; URL as state (deep-link filters/tabs/pagination/expanded panels — effectively any UI state kept in component state); optimistic updates with rollback/Undo; ellipsis for follow-up menu items (`Rename…`) and progress states (`Saving…`); confirm destructive actions or give an Undo window; `touch-action: manipulation`; deliberate `-webkit-tap-highlight-color`; tooltips: delay the first in a group, subsequent peers open instantly; `overscroll-behavior: contain` in modals/drawers; Back/Forward restores scroll; autofocus only on desktop single-input screens; no dead zones (if it looks interactive it is); drag: disable text selection + `inert` on the dragged element; every gesture has a click + keyboard alternative (WCAG 2.5.7); links are `<a>`/`<Link>`, never `<div onClick>`; polite `aria-live` for toasts/validation; locale-aware keyboard shortcuts.
- *Animations:* honor `prefers-reduced-motion`; implementation preference CSS > Web Animations API > JS libraries; animate only `transform`/`opacity`; **never `transition: all`**; animate only to clarify cause/effect or for intentional delight; easing chosen by what changes; interruptible; autoplay only for muted non-essential loops, and motion >5s next to other content needs pause/stop/hide (WCAG 2.2.2); correct `transform-origin`; SVG transforms on a `<g>` with `transform-box: fill-box`.
- *Layout:* optical alignment (±1px nudges where perception should override geometry); everything aligns to something deliberately; balance icon/text lockups (stroke weight vs text weight); verify mobile, laptop, ultra-wide (simulate ultra-wide by zooming to 50%); safe-area insets; no unwanted scrollbars (test with macOS set to always show scroll bars); let CSS layout, don't measure in JS.
- *Content:* inline help before tooltips; skeletons mirror final content; accurate `<title>`; no dead ends; **design empty, sparse, dense and error states**; curly quotes and the `…` character; avoid widows/orphans (`text-wrap: balance`); `tabular-nums` for compared numbers; redundant (non-color) status cues; accessible names even when visible labels are omitted; `scroll-margin-top` on anchored headings; skip link; layouts resilient to short/average/very long user content; `Intl.*` locale formatting; language from `Accept-Language`/`navigator.languages`, never IP; `translate="no"` on brand names/code; non-breaking spaces in `10&nbsp;MB`, `⌘&nbsp;K`; flex children need `min-w-0` to truncate.
- *Forms:* Enter submits single-input forms; ⌘/Ctrl+Enter in textarea; every control labelled and label click focuses it; **keep submit enabled until submission starts, then disable + spinner + idempotency key; don't pre-disable submit**; don't block typing — accept then validate; errors next to fields, focus first error on submit; `autocomplete` + meaningful `name`; correct `type`/`inputmode`; spellcheck off for emails/codes; placeholders are example values ending with `…`; warn on unsaved changes; allow pasting 2FA codes; trim trailing whitespace from text expansion; explicit colors on native `<select>` (Windows dark-mode bug).
- *Performance:* test iOS Low Power Mode + macOS Safari; profile with CPU/network throttling and without extensions; minimize re-renders (React Scan); **mutations (`POST/PATCH/DELETE`) complete in <500ms**; virtualize lists >50 items (`virtua`, `content-visibility:auto`); preload only above-the-fold images; explicit image dimensions (no CLS); preconnect CDN origins; preload + subset critical fonts; move long tasks to Web Workers; video instead of GIF.
- *Design:* **layered shadows (ambient + direct, ≥2 layers)**; semi-transparent borders + shadows for crisp edges; **nested radii: child ≤ parent, concentric**; on tinted backgrounds tint borders/shadows/text toward the same hue; color-blind-safe chart palettes; **"prefer APCA over WCAG 2"** for contrast; hover/active/focus states have *more* contrast than rest; `theme-color` meta matches background; `color-scheme: dark` on `<html>` in dark themes; avoid gradient banding on dark fades.
- *Vercel-specific copy (which the README itself marks as brand preference, not universal guidance)*: active voice; Title Case headings/buttons (sentence case on marketing pages); `&` over "and"; second person; numerals for counts; consistent currency decimals; space between number and unit; positive framing; **error messages say how to fix**; specific button labels (`Save API Key`, not `Continue`).
- *Audit output contract (`command.md`)*: findings grouped by file, `file:line - issue` terse lines, `✓ pass` for clean files, and no preamble.

**Strengths.** Highest density of concrete, *checkable* web-implementation details of any source; many rules map directly to static code checks (grep for `transition: all`, `outline-none`, `user-scalable=no`, `onPaste`+`preventDefault`, `<div onClick>`, `<img>` without width/height, `...`, missing `aria-label` on icon buttons). Clear MUST/SHOULD/NEVER modality. Tasteful polish rules that most a11y checklists lack (layered shadows, concentric radii, hue-tinted neutrals, tooltip grouping, loading-state anti-flicker timing).
**Weaknesses / conflicts.** (1) Internal inconsistency: README's mobile-input-size rule offers `maximum-scale=1` as an alternative, while its respect-zoom rule and `command.md`'s anti-pattern list forbid `maximum-scale=1`. (2) The APCA preference conflicts with WCAG 2.x conformance, which is what laws/procurement reference; APCA is not normative — the W3C WCAG 3.0 Working Draft of 10 September 2026 still says "The contrast algorithm used in WCAG 3 is yet to be determined" and does not name APCA (https://www.w3.org/TR/wcag-3.0/, fetched 2026-10-01). (3) Almost nothing about *aesthetic direction* — no guidance on typography choice, palette, layout composition or avoiding generic looks; it is a craft/quality floor, not a taste ceiling. (4) Some numbers are Vercel-internal heuristics without cited evidence (500ms mutation budget, 150–300ms show-delay). (5) The audit is static-code only — no rendered/DOM check.
**Adopt.** Most of the rule set as the web craft floor in our checker, with modality preserved; the anti-pattern grep list as static checks; the `file:line` terse finding format as one output mode; resolve the zoom conflict by *never* allowing `maximum-scale=1`/`user-scalable=no`; treat APCA as advisory alongside a WCAG 2.2 AA gate.

### 2.3 vercel-labs/agent-skills → `web-design-guidelines` (and other UI-adjacent skills)

- **What it is:** Vercel's official skill collection (31,811★). `skills/web-design-guidelines/SKILL.md` (39 lines) is a *thin fetch-and-apply wrapper*: (1) fetch `https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md` with WebFetch **before every review**, (2) read the user-specified files (ask if none), (3) check against all fetched rules, (4) output terse `file:line` findings. Same pattern for `writing-guidelines` (fetches `vercel-labs/writing-guidelines/main/command.md`).
- **URL:** https://github.com/vercel-labs/agent-skills/tree/main/skills/web-design-guidelines (HEAD `063bee9`, 2026-08-28).
- **License:** README states MIT; no root LICENSE file (GitHub API reports `license: null`); several SKILL.md files declare `license: MIT` in frontmatter, `web-design-guidelines` does not.
- **Files read:** `skills/web-design-guidelines/SKILL.md`, `skills/writing-guidelines/SKILL.md`, `skills/react-view-transitions/SKILL.md` (first 120 lines) + grep of `references/css-recipes.md`, heads of `skills/vercel-optimize/SKILL.md` and `skills/react-best-practices/SKILL.md`, README license section.
- **How it audits:** purely LLM reading of source files against a remote rule list — no parsing, no rendering, no DOM/computed-style inspection, no severity levels, no de-duplication across runs. Fetching rules at run time means results are not reproducible (rules change; e.g. curly-quote guidance was rewritten on 2026-08-18) and introduces a remote-content trust dependency.
- **Other UI-relevant skills in the repo:** `react-view-transitions` — a principle worth adopting: *each view transition should express a spatial relationship or continuity, and one whose meaning cannot be stated should be dropped*; reserve directional slides for hierarchical (list→detail) or ordered (prev/next) navigation, never for lateral tab switches; its CSS recipes use exit 150ms / enter 210ms (enter delayed by the exit) / move 400ms and zero durations under reduced motion (`references/css-recipes.md` lines 13–15, 301–308). `react-best-practices` (70 perf rules in 8 categories) and `composition-patterns` are code-architecture, not visual design. `vercel-optimize` is metrics-first (it refuses to open source files until a metrics `signals.json` exists) — a useful *process* analogue: evidence before inspection.
- **Adopt.** The two-file separation (rules file vs. thin auditor) and the terse output format; **but pin rule versions** (vendor a dated copy with a hash) instead of fetching live; add severity, evidence and recommendation fields (our HE report format) rather than one-line findings; borrow the view-transition test (if you cannot say what a transition communicates, drop it) as a motion rule.

### 2.4 Dammyjay93/interface-design

- **URL:** https://github.com/Dammyjay93/interface-design (HEAD `2f9be32`, 2026-06-20); site https://interface-design.dev
- **License:** MIT (© 2026 Damola Akinleye). Text can be adapted with attribution.

**Key content (my words).**
- *Diagnosis of the failure mode.* The skill tells the model plainly that it *will* produce generic output because code generation pulls from training patterns even when the prose intent is good; "intent lives in prose, but code generation pulls from patterns." **The bar:** output that another model would reproduce almost identically from a similar prompt counts as a failure.
- *Where defaults hide*: typography treated as a container, navigation as scaffolding, data as presentation, token names as implementation detail (`--ink`/`--parchment` evoke a world; `--gray-700`/`--surface-2` evoke a template).
- *Intent first (brand-context elicitation)*: three questions — who exactly is the human (where are they, what did they do 5 minutes ago), what is the verb they must accomplish, what it should feel like, described in concrete terms (generic labels such as clean-and-modern are rejected as empty). If too vague, ask **one** concise question; otherwise state an assumption and proceed. Intent must be *systemic* — every token checked against it, and every choice must have a why (citing commonness means the choice was defaulted).
- *Product-domain exploration — four mandatory outputs before any direction*: **Domain** (≥5 concepts/metaphors from the product's world), **Color world** (≥5 colors that exist naturally in the physical version of that world), **Signature** (one element that could only exist for this product), **Defaults** (3 obvious choices for this interface type, named so they can be rejected). Test: remove the product name — can someone still tell what it's for?
- *Suggest + Ask block*: Domain / Color world / Signature / Rejecting: default→alternative ×3 / Direction, then a request for the user to confirm the direction. Render a live specimen (swatches, type scale, elevation steps, signature component) when an inline render tool exists.
- *Mandatory per-component checkpoint* before writing any UI code: Intent, Hierarchy (focal element and how it wins), Palette (+why), Depth (+why), Surfaces, Typography (+why), Spacing.
- *Visual hierarchy rules with numbers*: one focal point per view; **type scale as a ratio — ~1.2 dense/calm, ~1.25 most product UI, ~1.333 expressive** (example from 14px base at 1.25: 11/14/16/18/22/28/44+); weight and color do more hierarchy work than size (one 14px size can carry three tiers: 600/primary, 500/secondary, 400/muted); **four text levels** (primary/secondary/tertiary/muted); density chosen in px (12–16px padding = workbench-tight, 24px = brochure) and held; uneven spatial rhythm; proportions that state relationships (280px sidebar = navigation serves content; 360px = peers); **~60/30/10 color distribution, accent ≤ ~10%, one accent**; hierarchy through space and weight before lines; tighten tracking on large headings, body line-height ~1.5.
- *Craft foundations*: surface elevation as tiny lightness steps (dark: base → +7% → +9% → +12%; light: add shadow instead); sidebar same color as canvas + subtle border; dropdowns one level above parent; **inputs slightly darker than surroundings (inset)**; borders as low-opacity rgba (dark `rgba(255,255,255,0.06–0.12)`); **squint test**; infinite expression (their term) — the default trio of identical sidebar width, card grid and icon-left big-number metric boxes is said to mark output as AI-generated at a glance.
- *Use what exists*: native HTML → battle-tested headless primitive (Radix, React Aria, Ark, Headless UI, Vaul, cmdk) → hand-roll only as last resort with the full keyboard/focus/ARIA contract; styling order: project design system → extracted component (on the second real reuse) → semantic tokens (`bg-card`, not `bg-white`) → one-off utilities; the same long utility-class string repeated everywhere is called out as the tell of slop.
- *Design-system essentials*: tokens trace to primitives (foreground/background/border/brand/semantic); 4 or 8px base and multiples only; symmetrical padding by default; **choose ONE depth strategy** (borders-only / subtle shadows / layered shadows / surface shifts) and don't mix; a radius scale; dedicated control tokens; dark mode: lean on borders, desaturate semantic colors, keep one hue and shift lightness.
- *Polish & motion (numbers)*: concentric radius **outer = inner + padding**; `tabular-nums` on dynamic numbers; optical alignment (icon-side padding ≈ text-side − 2px; play triangles ~2px right); every interactive element has default/hover/active/focus/disabled and data has loading/empty/error; **hit areas 44×44 (attributed to WCAG), 40 minimum**, extend via pseudo-element, never overlapping; light-mode lift = 1px ring + two soft shadows (e.g. `0 0 0 1px rgba(0,0,0,.06), 0 1px 2px -1px rgba(0,0,0,.06), 0 2px 4px rgba(0,0,0,.04)`), dark = single ring `0 0 0 1px rgba(255,255,255,.08)`; `text-wrap: balance` headings / `pretty` body; `-webkit-font-smoothing: antialiased`; image outline 1px inset `rgba(0,0,0,.1)`/`rgba(255,255,255,.1)`. Motion: **no animation on actions repeated 100+×/day**; UI durations **<300ms** (press 100–160ms, tooltip/popover 125–200ms, dropdown 150–250ms, modal/drawer 200–500ms); custom ease-out `cubic-bezier(0.23, 1, 0.32, 1)`, on-screen movement `cubic-bezier(0.77, 0, 0.175, 1)`, **never ease-in**; press `scale(0.97)` (never below 0.95); **never animate from `scale(0)`** (start at 0.95 + opacity 0); popovers scale from their trigger, modals stay centered; stagger 30–80ms; exits faster than enters; reduced motion keeps opacity/color, drops movement. (These motion rules match Emil Kowalski's published guidance — see §2.9.)
- *"Avoid" list (anti-patterns)*: harsh borders, dramatic surface jumps, flat hierarchy, monotone layout, inconsistent spacing, mixed depth strategies, missing states, dramatic drop shadows, large radius on small elements, thick decorative borders, decorative gradients/color, multiple accents, different hues per surface, **default typography — system/Inter fonts and size-only hierarchy**, structural hacks (negative margins undoing parent padding, escape-hatch `calc()`, absolute positioning to dodge flow).
- *Verification step*: visual verification for any non-trivial UI via inline render, local browser or screenshots at desktop and mobile widths; plus four **pre-show checks**: **Swap test** (swap your typeface/layout for the usual one — where nothing changes, you defaulted), **Squint test**, **Signature test** (point to five concrete places the signature appears), **Token test** (do the CSS variable names belong to this product's world?).
- *Design-review command*: 5 steps — (1) scope + intent (review against the design's *own* intent, from `system.md`), (2) see the whole first (render/screenshot; compositional slop is invisible line-by-line), (3) six lenses run **independently** (A Hierarchy, B Type & color, C Surfaces & depth, D Composition & rhythm, E States/polish/motion, F Structure/reuse/content), (4) **severity Blocker / Should-fix / Note + explicit false-positive filter** (taste-not-defect; bold choice working as intended; out of scope; ratified by system.md; lint concerns; a finding whose cost to the user, or contribution to a generated look, cannot be explained is treated as taste and dropped), (5) report each finding as *what defaulted / why it costs / the crafted fix* + verdict against an **approval bar** with presumptive blockers. Review and mutation are kept separate (judge by default; fix only on request).
- *Deslop command*: Pass 1 (squint) on the rendered output, ranked tells (no focal point → flat hierarchy → monotone layout → timid color → borders doing the work of space); Pass 2 (scan) over the diff by category (tokens & color, typography, surfaces & depth, states & motion, spacing & structure, reinvention); an explicit list of what is not slop (motivated bold choices, reasoned deviations, out-of-diff code, linter-owned issues, system.md-ratified choices; ambiguous cases are treated as decisions); output as a Before/After table.
- *Memory*: after a task, offer to save direction, depth strategy, spacing base, type-scale ratio, density, focal pattern and measured component patterns (e.g. a primary button's height, padding, radius and type size) to `.interface-design/system.md`, with a Decisions table (decision, rationale, date). Subsequent sessions treat it as ratified.

**Strengths.** The best articulation I found of *why* agents produce slop and of concrete counter-moves; strong elicitation (human/verb/feel + 4 exploration outputs + named defaults); explicit, falsifiable self-tests (swap, squint, signature, token); a review procedure with independent lenses, severity, a false-positive filter and an approval bar — very close to heuristic-evaluation practice; separation of judging from fixing; memory of decisions with rationale.
**Weaknesses.** (1) Accessibility attribution errors: the skill attributes 44×44px to WCAG and allows 40px as a floor — checked against W3C: SC 2.5.8 Target Size (Minimum) is Level **AA at 24×24 CSS px** (with spacing/equivalent/inline/user-agent/essential exceptions; https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) and SC 2.5.5 Target Size (Enhanced) is Level **AAA at 44×44 CSS px** (https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html); "40" has no WCAG basis. (2) Its own `reference/system-template.md` and `system-precision.md` default to slate + `blue-600` + system/Inter/Geist — exactly what the SKILL.md tells the model to avoid; the templates re-inject defaults. (3) Severity is a 3-level label, not derived from frequency/impact/persistence. (4) Visual verification is recommended but not scripted (no screenshot harness, no computed-style checks). (5) Scope excludes marketing pages.
**Adopt.** Intent triad + 4 exploration outputs + named-defaults list as our direction-elicitation template; swap/squint/signature/token tests as pre-delivery checks; the six review lenses and false-positive filter; review judges and fixes happen only on request; `system.md`-style decision memory with rationale and dates; numeric polish rules (concentric radius, single depth strategy, 60/30/10, type-scale ratios, sub-300ms UI motion, never scale(0), no animation for 100×/day actions). Fix the hit-area numbers against WCAG.

- *Top-12 rules*: ask before assuming; **sentence case** (uppercase only for 11–13px tracked labels); **≥90% neutral + one accent, 3–5 accent placements per above-the-fold viewport**; vary radius by role (e.g. 6px inputs / 10px cards / 14px modals); real SVG icon set, never mix two; tracking −0.02em+ above 24px; one body font (+ optional display); layered shadows; exits ≈75% of entrance duration; plain secondary text for comparisons (no colored trend pills); every section earns its space; one signature detail per UI.
- *Anti-slop test (graded)*: would a viewer instantly believe an AI made this? **Critical**: identical card grids (icon+heading+text ×3–6), ALL CAPS headings/nav/buttons, purple/cyan gradients, emoji feature icons, bounce/elastic easing, glassmorphism on dark + neon. **Major**: colored pills on trend %, thick colored left/top card borders, uniform radius, gradient text on hero metrics, vertical bars for time series, `transition: all`, decorative glow as affordance, blurry gradient blobs/orbs, generic CTAs, walls of text (>2–3 sentences per landing section), caps "OR" dividers, saturated brand panel beside sign-in, uppercase eyebrow above every heading (≤1 per 3 sections), numbered section eyebrows, scroll cues, two CTA labels for one intent, fake product screenshots from styled `<div>`s, text-only logo walls, purposeless carousels, app UI built from stacked cards, **em-dash flood (≥3 in UI copy)**. **Minor**: no `tabular-nums`, no `text-wrap: balance`, straight quotes, no `&nbsp;` in brand names, star ratings in testimonials, hero metric without context.
- *When rules break* — explicit inversions (small tracked caps labels; multi-tenant accents; two-segment donut OK; emoji as user content; gradient on a single brand hero metric on marketing pages; deliberate 3-family type systems). Principle: each rule guards against the most common failure, so when context inverts that failure the rule may invert as well.
- *Surface recipes with numbers*: landing hero ≤4 text elements, **subtext ≤20 words**, headline ≤2 lines, logo wall below the hero; **a layout family at most once per page, ≥4 families for 8 sections, ≤2 consecutive image+text splits**; **eyebrows ≤ ceil(sections/3)**; headline top at 18–30% of the fold; 4–6 distinct font sizes with a ≥2.5× jump to display; section gaps 80–160px; entrances ≤400ms; no scroll-jacking. Dashboard: ≥3 content types above the fold, no equal-weight card grid, one accent ≤5 placements, sidebar tinted not full-dark, padding 24px (32px sparse / 16px dense), 12-col grid gap 16px.
- *Motion*: decision ladder (high-frequency → no animation; hover/list nav < 150ms; modals/page transitions 200–300ms; one-time onboarding may be expressive); budgets color/opacity 100–150ms, small UI 150–200ms, medium 200–300ms, large 300–400ms; reduced-motion collapses to ≤80ms or removes entrances.
- *Finish bar* (`finish-bar.md`) — 10 ordered passes with **measurable criteria**: (1) Hierarchy — squint/`filter: blur(8px)` test, adjacent hierarchy levels differ by **≥1.5× in at least one signal**, one focal point per viewport; (2) Type system — **≤3 font weights per viewport**, `tabular-nums` on all numeric data, prose 50–75 chars, ≤1 body + 1 display + 1 mono face; (3) Surface stack — canvas/raised/overlay differ by **≥2% luminance in light, ≥4% in dark**, dark canvas not `#000`, `color-scheme` set; (4) Spacing rhythm — within < between < section at every level, **section breaks ≥2× inter-block spacing**, all values from the scale; (5) Iconography — one family, stroke matched to text weight (1.5px ↔ 400, 2px ↔ 500), constant icon:label size ratio; (6) **State coverage — idle, loading (skeleton after ~200ms), empty (one line + one action), error (inline, actionable), success (beyond color), partial (em-dash for unknown, never `null`/`N/A`/false 0), conflict, offline**; (7) Motion — UI 100–400ms, no linear for spatial motion, motion-gap audit; (8) Microcopy — consistent verbs, no placeholder copy, specific CTAs, actionable errors, one action per empty state, voice axes from the brief; (9) Pixel honesty — hairline borders via `color-mix`, 2–3-layer shadows, radius varies by role (uniform radius is called the most recognisable sign of generated UI), overflow handled; (10) Data formatting — abbreviation vs exact, relative vs absolute time, locale currency, negatives with two signals, precision matched to the decision. Severity mapping: **Critical blocks ship** (flat hierarchy, missing loading/empty/error states, placeholder copy); **Major** fix or document; **Minor** must be written down to be accepted; a deferral without a written reason counts as a skip.

**Key content (my words).**
- *Philosophy*: taste is trained, not innate; unseen details compound; beauty is leverage. **Review output is a Before / After / Why table** (no prose lists).
- *Animation decision framework*: (1) **should it animate at all — by frequency**: 100+/day (keyboard shortcuts, command palette) → never; tens/day (hover, list nav) → remove or drastically reduce; occasional (modals, drawers, toasts) → standard; rare/first-time → may delight. "Never animate keyboard-initiated actions." (2) **purpose** must be one of spatial consistency, state indication, explanation, feedback, preventing jarring change. (3) **easing decision tree**: entering/exiting → ease-out; moving on screen → ease-in-out; hover/color → ease; constant motion → linear; default ease-out; **never ease-in for UI**; built-in curves too weak → custom tokens `--ease-out: cubic-bezier(0.23, 1, 0.32, 1)`, `--ease-in-out: cubic-bezier(0.77, 0, 0.175, 1)`, `--ease-drawer: cubic-bezier(0.32, 0.72, 0, 1)`. (4) **durations**: press 100–160ms, tooltips/small popovers 125–200ms, dropdowns/selects 150–250ms, modals/drawers 200–500ms; **UI animations under 300ms** (the essay gives 200–300ms for modals/drawers — a small inconsistency).
- *Component rules*: `:active` scale 0.97 (range 0.95–0.98); **never animate from `scale(0)`** (start ≥0.9–0.95 + opacity 0); popovers/dropdowns/tooltips scale from their trigger (`transform-origin: var(--transform-origin)`), **modals stay centered**; tooltips: delay the first, then instant with no animation for neighbours; **CSS transitions (retargetable) over keyframes** for rapidly triggered UI; blur (≤20px, ~2px typical) to mask awkward crossfades; `@starting-style` for entry; springs (`{type:"spring", duration:0.5, bounce:0.2}`; bounce 0.1–0.3 only for drag/playful) for interruptible/gesture motion; momentum dismissal (velocity > ~0.11 px/ms dismisses regardless of distance); damping/friction at boundaries; pointer capture; ignore extra touch points; asymmetric timing (slow while the user is deciding, fast when the system responds; e.g. hold-to-delete 2s linear / release 200ms ease-out); stagger 30–80ms, never blocking interaction.
- *Performance*: animate only transform/opacity; don't drive child transforms through a parent CSS variable (style-recalc storm); Motion's `x`/`y` shorthands run on the main thread — use a full `transform` string under load; CSS/WAAPI beat JS under load; `will-change` only after you see a 1px shift.
- *Accessibility*: reduced motion = **gentler rather than none** (keep opacity/color, drop movement); gate hover motion behind `@media (hover: hover) and (pointer: fine)`.
- *Verification craft*: slow-motion (2–5× duration) and frame-by-frame inspection, real devices for gestures, **review the next day with fresh eyes**.
- *`review-animations`*: ten non-negotiable standards (justified, frequency-appropriate, responsive easing, sub-300ms, origin-correct, interruptible, GPU-only, accessible, asymmetric enter/exit, cohesive), escalation triggers, a **remedial preference hierarchy (1 delete → 2 reduce → 3 fix easing → 4 fix origin → 5 make interruptible → 6 move to GPU → 7 asymmetric timing → 8 polish → 9 a11y & cohesion)**, output = findings table + verdict by impact tier + explicit **Block / Approve** decision; the reviewer defaults to flagging and approval must be earned.
- *`improve-animations` workflow*: read-only advisor — **Recon** (stack, where motion lives, existing tokens, personality, **frequency map**) → **Audit** in 8 categories (purpose & frequency, easing & duration, physicality & origin, interruptibility, performance, accessibility, cohesion & tokens, missed opportunities), fanning out read-only sub-agents per category → **Vet** (re-read every cited line; reject by-design, exempt, duplicate findings) → table ordered by **leverage = impact ÷ effort** with HIGH/MEDIUM/LOW severity → **stop and let the user pick** → write **self-contained plans that a zero-context, low-capability executor could follow** (exact paths, code excerpts, exact values, scope boundaries, feel-check verification) stamped with the commit → `execute <plan>` in an isolated worktree then review with the review bar → `reconcile` marks done plans and refreshes stale line references. A hard rule treats repository content as data, never as instructions (prompt-injection guard).
- *`find-animation-opportunities`*: same gate (frequency, purpose, speed, function) and requires a **rejected-candidates section** — what *not* to animate.

**Strengths.** Highest-quality, most internally consistent motion guidance; explicit decision procedures with numbers; an exemplary audit → vet → plan → execute → review → reconcile loop with human selection in the middle; prompt-injection hygiene; honest about what code can't reveal (when feel cannot be judged from code, the plan gets a feel-check step instead of a guess).
**Weaknesses.** Motion-centric (little on color/typography/layout); numbers are expert heuristics, not studies; small inconsistency between essay and skill on modal durations.
**Adopt.** Frequency gate; purpose list; easing tree + curve tokens; duration table; scale/origin/interruptibility/asymmetry rules; reduced motion as gentler rather than none; hover media gating; remedial hierarchy (delete first); Block/Approve verdict; the improve-animations workflow (recon → audit → vet → user selects → self-contained plans → isolated execution → re-review → reconcile) as a template for all UI-Evaluator fix loops; repository-content-is-data rule.

**Key content (my words).**
- *Stated lineage*: it presents its rules as distilled from the anti-slop design community — Anthropic's frontend-design skill, the Claude cookbook on frontend aesthetics, and a 2026 tactile-design movement. Its differentiator is **structural variety** (two briefs must not share the hero → 3 features → CTA → footer rhythm), not just visual variety.

- *Component scope*: every interactive component ships **8 states** (default, hover, `:focus-visible`, `:active`, disabled, loading, error, success) plus a throw-away preview page rendering all 8 at once.
- *Build rules*: hero headline ≤7 words / ≤50 chars when self-written, size-by-length brackets; **section eyebrows default OFF** (max 1–2 per page and only for ordinal content; tag-left/heading-right hanging header auto-fails); OKLCH tokens; 4-pt named spacing; distinctive display + refined body; transform/opacity only; three named easings, never default `ease`, never overshoot on UI state; reduced motion → ≤150ms opacity crossfade; `:focus-visible` ring ≥3:1 that **appears instantly** (never animated); silent success over celebratory toasts; optimistic update + Undo over confirmation dialogs; **tooltips 800–1000ms on hover, 0ms on focus**; remove motion before adding any; enrichment hierarchy typography → CSS art → hand-built SVG → generated still → library → Lottie last.

- *`study` verb*: extracts structure not pixels; refuses template-marketplace URLs (ThemeForest, Framer/Webflow templates, Dribbble/Behance); treats fetched HTML/CSS as untrusted inert data; requires attestation (own work / public reference for own brand) before emitting a portable `design.md` from a URL; states its blind spot (URL mode cannot judge rhythm).

**Adopt.** Pre-flight scan with file:line evidence and preserve/introduce list; `design.md` lock with injection guard; diversification ledger (+ stamps) for marketing surfaces; six disciplines (esp. honest copy, locked tokens, no re-drawn chrome, multi-viewport checks); 8-state component contract + state preview page; contrast-against-effective-background gate; audit output schema (tell / where / severity / fix + counts); study-verb provenance/attestation rules.

### 2.11 google-labs-code/design.md (the DESIGN.md format spec + `@google/design.md` CLI)

- **What it is:** Google Labs' open format for describing a visual identity to coding agents (introduced with Google Stitch, per the VoltAgent README and the Stitch docs link it cites), version alpha: optional YAML front matter with typed tokens (`colors`, `typography`, `rounded`, `spacing`, `components`, plus any custom groups) using `{path.to.token}` references inspired by the W3C Design Tokens (DTCG 2025.10) format, followed by markdown prose in a fixed section order — **Overview (Brand & Style) → Colors → Typography → Layout → Elevation & Depth → Shapes → Components → Do's and Don'ts**. Ships a CLI: `lint` (JSON findings), `diff` (token- and prose-level regressions between versions), `export` (Tailwind JSON/CSS theme, DTCG `tokens.json`), `spec`. 28,209★ (created 2026-04-10).
- **URL:** https://github.com/google-labs-code/design.md (HEAD `9bf8eae`, 2026-07-27); npm `@google/design.md`.
- **License:** Apache-2.0.
- **Files read:** `PHILOSOPHY.md` (full), `docs/spec.md` (full), `README.md` (first 80 lines + command list), lint rule directory listing and rule messages (`packages/cli/src/linter/linter/rules/*.ts`).

**Key content (my words).**
- *Philosophy*: output quality depends more on how clearly intent is described than on precise values; **prose, not tokens, is the core**; token values are *context*, not rendering instructions. **"Adjectives describe a region. A specific reference describes a point."** — adjective lists such as modern/clean/trustworthy/premium land a model in the middle of that region (generic), whereas a concrete referent (their example is a 1970s graduate lecture handout) carries its own palette, type, margins and *negative constraints* for free. An intentional, short Do's/Don'ts list complements a strong reference; a long rambling list signals a vague reference. Its example rules trust modest size steps (section titles about 1.9× body), cap UI animation at 300ms, and collapse all durations to 0ms under reduced motion (contrast Emil's gentler-rather-than-none stance).
- *Spec details*: at least a `primary` color; 9–15 typography levels is typical; recommended (non-normative) names `primary/secondary/tertiary/neutral/surface/on-surface/error`, `headline-*/body-*/label-*`, `rounded none…full`; components map to property tokens (backgroundColor, textColor, typography, rounded, padding, size, height, width) with state variants as sibling keys (`button-primary-hover`); `omitted:` documents intentionally absent sections; unknown sections/tokens are preserved, duplicate sections are an error.
- *Linter rules*: `broken-ref`, **`contrast-ratio` (component text/background pairs below WCAG AA 4.5:1)**, `missing-primary`, `missing-typography`, `missing-sections` (each warns that the agent will fall back to its own default colors, fonts, spacing or rounding), `section-order`, `orphaned-tokens`, `token-like-ignored`, `unknown-key`, `omitted`, `token-summary`.

**Strengths.** A vendor-neutral, tool-backed, diffable format for persistent design context — the de facto interchange format that hallmark, ibelick and the DESIGN.md collections now target; the reference-over-adjectives principle is the clearest statement of *why* briefs produce generic output.
**Weaknesses.** Alpha; components section still evolving; no motion/elevation schema; linter checks only structure + contrast, not quality.
**Adopt.** Use DESIGN.md (this spec) as UI-Evaluator's persistent design-context file instead of inventing a format; require a **specific referent + short Do/Don't list** in the Overview; run `lint` + `diff` as checks (contrast, broken refs, missing sections) and treat missing typography/primary as default-fallback warnings.

### 2.13 ibelick/ui-skills (Julien Thibeaut)

- **What it is:** a small, rigorous set (9,308★, created 2026-01-07) — `baseline-ui` (85 lines), `improve-ui` (+ `references/plan-template.md`), `create-design-md`, `fixing-accessibility`, `fixing-metadata`, `fixing-motion-performance`, `ui-skills-root` — plus a registry website (https://www.ui-skills.com/, per README) whose source also carries 18 company DESIGN.md files.
- **URL:** https://github.com/ibelick/ui-skills (HEAD `ebf5f26`, 2026-09-30)
- **License:** MIT (© 2026 Julien Thibeaut).
- **Files read:** `skills/baseline-ui/SKILL.md` (full), `skills/improve-ui/SKILL.md` (full), `skills/improve-ui/references/plan-template.md` (full), `skills/create-design-md/SKILL.md` (first 80 lines), `skills/fixing-accessibility/SKILL.md` (first 60 lines).

**Key content (my words).**
- *`baseline-ui` — a don't-improvise floor*: MUST use Tailwind defaults unless custom values exist; `motion/react` for JS animation; `cn` for class logic; accessible primitives (Base UI, React Aria, Radix) for anything with keyboard/focus behaviour and never mix primitive systems; `aria-label` on icon-only buttons; AlertDialog for destructive actions; structural skeletons; `h-dvh` not `h-screen`; safe-area insets; errors next to the action; never block paste. Animation: **never add animation unless requested**; compositor props only; ease-out on entrance; **interaction feedback ≤200ms**; pause off-screen loops; **no custom easing curves unless explicitly requested**. Typography: `text-balance` headings, `text-pretty` body, `tabular-nums` data, **no letter-spacing changes unless explicitly requested**. Layout: fixed z-index scale; `size-*`. Performance: never animate large blur/backdrop-filter, `will-change` only during animation, no `useEffect` for render logic. Design: **no gradients unless requested, never purple or multicolor gradients**, no glow as primary affordance, Tailwind default shadows, one accent per view, empty states with one next action. Review mode: quote the violating line, one-sentence why, code-level fix.
- *`improve-ui` — the strictest evidence standard in the survey*: read-only on product source (plans only, under `design-plans/`); select **one coherent surface** and trace its real render path (routes → layouts → components → variants → resolved tokens); a connection counts only when proven through rendering, imports, props, resolved configuration, CSS inheritance or a generated artifact; reconstruct the governing local system (DESIGN.md only if proven current). A candidate becomes a finding only with **three proofs: Contract** (a binding design decision or a direct contradiction in user-facing presentation; soft wording such as prefer, repetition and omissions do not count), **Runtime** (the value actually reaches the surface), **Correction** (exactly one change follows from the evidence; if it requires inventing product intent, reject). **"Hierarchy, prominence, density, clarity, discoverability, usability, and perceived coherence require rendered or user evidence"** — source code alone cannot prove them. Then a falsification pass, report **at most three** findings (`Problem | Evidence | Proposed change | Scope | Confidence`) + one improve-first pick; an explicit no-findings result is valid; stop and let the user choose; write self-contained plans (evidence chain, design decision, reuse/exemplar, changes with preserve/verify, inherit/verify/exclude scope, product/interface/system/repository validation, **stop conditions**, documentation update) for another agent; `reconcile` re-checks plans against current source.
- *`create-design-md`*: repository mode (normative values from source) vs URL mode (requires **rendered** inspection of DOM + computed styles at desktop and mobile; screenshots alone cannot establish exact values; URL evidence can't establish internal token names or rationale); evidence pipeline `role → value → source → scope → recurrence → confidence`; omit uncertain or local-only candidates; the draft stays private until lint + export pass.

**Strengths.** A principled epistemology for UI audits (what source can and cannot prove; three-proof gate; falsify before reporting; cap at three; allow a no-findings result); identity-preserving improvement; a conservative baseline that removes the agent's room to improvise.
**Weaknesses / conflicts.** The baseline's bans on custom easing and tracking directly contradict Emil Kowalski, interface-design, ui-craft and top-design (all of which require custom curves and negative tracking on large type); its no-animation-unless-requested rule contradicts taste-skill's requirement that declared motion actually ship; it relies on Tailwind defaults — which (see §2.1) are the visual signature of generic AI output. It is a *correctness floor*, not a taste engine.
**Adopt.** The three-proof finding gate, the source-vs-rendered-vs-user evidence boundary, the falsification vet, stopping at three findings with one improve-first pick, no-findings as a valid outcome, the plan template with stop conditions, and the DESIGN.md evidence pipeline. Resolve the easing/tracking conflict as described in §3.

### 3.2 Conflicts and proposed resolutions

| # | Conflict | Positions (sources) | Proposed resolution for UI-Evaluator |
|---|---|---|---|

If a DESIGN.md/brief exists → no question. ### 3.3 Gaps (what no source covers well)

1. **No outcome evidence.** Almost every rule is expert heuristic; none of the sources report user-level outcomes (task success, time, errors, SUS/SEQ) for interfaces built with vs without the skill. The only measurements are retrieval relevance (ui-ux-pro-max), rule-compliance in agent builds with a control arm (ui-craft), and detector FP/FN on 17 cases (tastecheck). UI-Evaluator should add empirical evaluation (lecture: objectives → tasks → data → analysis; A/B with power analysis).
2. **No evidence on which "tells" humans actually perceive as AI-made.** Lists are authors' observations (unpublished production tests, observation samples of unstated size). A rater study (screenshots of generated vs designer UIs, rating "AI-made?" and quality) would ground the tell list and its weights.
3. **Multi-evaluator heuristic evaluation is missing.** Several tools fan out by *lens* (interface-design, designer-skills, Emil, ui-craft agents) but none runs 3–5 *independent evaluators* on the same lens and merges with consensus severity (the lecture's HE protocol). Nor does any source run ≥2 passes per evaluator explicitly.
4. **Cognitive walkthrough is only gestured at** (Norman's seven stages, Jobs' cold walkthrough, persona walkthroughs). No source implements the 4-question per-action CW protocol with task + action sequences.
5. **Real user feedback ingestion** is limited to wondelai journeys (evidence before change) and designer-skills (triangulation, test plans). No skill parses tickets/reviews/session recordings into findings mapped to heuristics and screens.
6. **Rendered verification is rare.** Most skills audit source text; only plugin87, ui-craft (fold), hallmark (multi-width), auteur (frame QA), ibelick (create-design-md URL mode) require rendering. ibelick's rule that hierarchy/clarity claims need rendered or user evidence should become a framework-wide epistemic rule.
7. **The "whack-a-mole" drift.** Each anti-slop list's recommended alternatives become the next generation of tells (Geist/Space Grotesk, bento, split hero, editorial serif + italic, beige-brass "premium", eyebrow labels). Only ledger-based rotation (ui-craft, hallmark) and referent-based derivation (DESIGN.md philosophy) address the mechanism; nobody monitors the distribution of outputs over time.
8. **Thin coverage** of i18n/RTL/CJK typography (Vercel locale rules, plugin87 RTL verifier, awesome-design-md-jp only), native desktop/mobile apps (mostly ui-ux-pro-max), data-dense enterprise UI (taste-skill/hallmark exclude it), and dark-mode verification beyond testing both themes.
9. **License and provenance hygiene** is weak in the ecosystem: book-derived summaries (wondelai), "reverse-engineered" vendor prompts (Trystan-SA, possibly baoyu-design), brand-identity clones (DESIGN.md collections), unlicensed repos (senlindesign). UI-Evaluator should adopt ideas with attribution and avoid redistributing such text.

## 5. Open questions / things to verify later

1. **Do humans actually read these tells as "AI-made"?** Run a rater study (generated vs designer-made screens, randomised, blind) to weight the tell list (DSL-011, -019–-021, -031) and to test thresholds such as accent ≤5–10% of viewport, eyebrows ≤ ceil(sections/3), hero subtext ≤20 words, display:body ≥2.5×. All of these are currently [heuristic].
2. **Replicate ui-craft's fold experiment** (10/10 identical folds under prose instructions; 0/4 splits after a mechanical draw) with more models, more briefs and larger n before treating the claim that variety cannot be requested in prose as settled; also test whether ledger rotation makes outputs recognisably "catalogue-made" over time (hallmark's 21 themes, ui-craft's 4 presets).
3. **LLM-as-evaluator reliability**: how many independent agent evaluators (different prompts/models/temperatures) are needed to approach the 3–5-evaluator yield of human heuristic evaluation, and how do their severity ratings agree with each other and with humans (inter-rater agreement)? No source measures this (tastecheck states it explicitly).
4. **Tooltip hover delay** (hallmark's 800–1000ms; no source given) and the **300–600ms post-error pause** (designer-skills) — no source cited; verify against platform guidance or research before adopting numbers.
5. **Platform numbers to confirm in sibling notes**: Apple HIG 44×44pt minimum hit target and Material 48×48dp (verified here only via secondary summaries; primary pages: https://developer.apple.com/design/human-interface-guidelines/accessibility, https://m3.material.io/foundations/designing/structure); wondelai `ios-hig-design` lists Title as 17pt Medium and clarity/deference/depth as the current principles — both look outdated or wrong [unverified]; check against the current HIG.
6. **APCA timing**: WCAG 3.0 WD (2026-09-10) leaves the contrast algorithm undetermined; re-check before any release that mentions APCA thresholds (hallmark uses Lc ≥60 body / ≥45 large as advisory).
7. **Licensing**: wondelai summaries of copyrighted books (adopt ideas only, cite the books); Trystan-SA and possibly baoyu-design ("reverse-engineered" vendor prompts) — no text reuse; senlindesign has no licence; transitions.dev forbids redistribution; DESIGN.md collections describe third-party trade dress. 8. **Google DESIGN.md spec is "alpha"**: track changes (components, motion, elevation schemas) and the CLI's lint rules; decide whether UI-Evaluator writes extra sections (Motion, States, Iconography, Known Gaps, Provenance) as allowed custom sections.
