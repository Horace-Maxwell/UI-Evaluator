# UI-Evaluator 总览

> 一个面向 AI 编程助手的 Agent Skill。它让助手能做出、评估并修好网页前端界面，标准是可用、无障碍（WCAG 2.2 AA）、做工到位、没有"AI 味"，而且每一条结论都要有证据、可以复查。

本文是给项目负责人和中文读者的总览。规范原文是英文，见 [framework/](framework/)。供 AI 助手执行的说明在 [skills/ui-evaluator/](../skills/ui-evaluator/SKILL.md)。

## 1. 要解决的问题

调研发现，AI 做界面或评界面时有四个反复出现的毛病：

1. **默认值扎堆。** AI 生成的界面会落到训练数据里最常见的选择上：靛蓝到紫色的渐变、那几款"有品位"的字体、三张一模一样的图标卡片、每个区块上方一行字距拉开的大写小标签、每一屏都淡入上浮、凭空编出来的数据和客户 logo。人们一眼看出"AI 做的"，原因是里面没有一处是为这个产品专门决定的。光靠文字提示改不了这个毛病。有个对照实验里，只靠文字规则生成 10 次，首屏结构 10 次完全一样；改成机械抽签加记录台账之后，4 次里 0 次重复。
2. **单次评估不可靠。** 一位专家做启发式评估，大约只能找到三分之一的问题；任意两位评估员找到的问题，重合度只有 5%–65%；单人给出的严重度在评估员之间相关性只有约 0.2–0.3。大模型单次评估大约能找回专家问题集的 35%–45%，准确率 60%–83%，而且多轮迭代后反馈会越来越不准。
3. **评估和用户反馈各管各的。** 审查工具不读真实用户的反馈，反馈工具也不会把反馈对应到启发式原则、任务步骤或已有问题上。
4. **修复没人验证。** 改完由改的人自己宣布"好了"；用"问题数变少"来证明有进步，会把新引入的问题藏起来；修复循环没有上限，越改越乱。

市面上没有哪个现成项目把这四件事一起解决（调研见 [research/00](research/00-landscape-survey.md)）。

## 2. 承诺：把"100% 美观、不 AI 味"变成可验收的标准

"美"没法被证明，审美打分本身就很不稳定。专业设计师之间对同一组界面的一致性系数只有 0.37 左右。如果许诺"100% 美观"却无法验证，就违背了这个框架自己"有证据才能下结论"的原则。所以我们把它改写成**能被检验的最强承诺**：只要没达到目标等级，技能就不会说"做完了"，并且会如实报告实际达到了哪一级。

| 保证等级 | 含义 |
|---|---|
| **L1 机器验证** | 所有确定性检查通过：证据完整、功能完整、可自动检测的 WCAG 2.2 AA 项、可量化的做工底线，以及零个未被认可的 AI 味特征 |
| **L2 评审团通过** | L1 之外，多位相互隔离的评估员和设计评审团没有发现悬而未决的严重问题，并认为设计确实是为这个产品做的、对它的受众有吸引力。所有问题都经过验证员复现和盲评严重度 |
| **L3 人工确认** | L2 之外，负责人或专家确认（或否决）了所有严重问题和设计结论，并完成了机器测不了的无障碍检查项 |
| **L4 用户验证** | L3 之外，真实用户完成了关键任务，观察到的问题已经修复并复测 |

默认目标：一次性原型做到 L1，给用户用的产品做到 L3，高风险领域（医疗、金融、政务、安全）做到 L4。

**通过意味着什么：** 在 L2 及以上，已知的做工缺陷、AI 味特征、可自动检测的无障碍问题和严重可用性问题，都已经修好或者有明确记录的决定；独立评审认为设计是为这个产品量身定制的。
**通过不意味着什么：** 不保证人人都觉得美，不保证没有遗漏，不保证商业成功，也不代表"不是 AI 做的"。框架检测的是"有没有做决定"，从不判断作者是谁。

## 3. 整体流程

```
 需求 ─▶ 准备 ─▶ 定方向 ─▶ 构建 ─▶ 审查 ─▶ 修复 ─▶ 验证 ─▶ 报告
        setup   direct   build   audit   fix    verify   report
                                   │                ▲
                                   ▼                │
                               研究计划 ─ 真人 ─▶ 反馈导入
                               study            ingest
```

| 工作流 | 做什么 |
|---|---|
| **setup 准备** | 弄清用户、关键任务、使用场景和产品事实，写 `PRODUCT.md`、关键用户旅程和配置，检查工具链 |
| **direct 定方向** | 先找参考，列出 5–7 个来自用户世界的候选方向，用带种子的抽签发出三个（一个避开模型最想选的前两名，一个模型自己的首选，一个常规方案），分头独立深化，做"可替换 / 可猜 / 同题"三项趋同测试，选定后锁进 `DESIGN.md` 并记入台账 |
| **build 构建** | 先落设计令牌，结构保持常规，组件状态做全，文案按规范写，响应式，守住无障碍底线，动效放到最后，收尾时做一道完成度检查，避免页面干净但寡淡。编辑时持续做静态检查，最多两轮机械自检 |
| **audit 审查** | 确定性检查，加上多位隔离的评估员（启发式评估、认知走查、设计评审、无障碍、代码），再经过合并、验证员复现、三人盲评严重度、汇总讨论，最后算关卡、出报告 |
| **study 研究计划** | 按课件的"目标 → 任务 → 数据 → 分析"设计可用性测试、问卷、情感测试或 A/B 实验 |
| **ingest 反馈导入** | 把测试记录、问卷、工单、评论、数据导入，归纳主题，挂到已有问题上，按观察到的频率重新评定严重度 |
| **fix 修复** | 按优先级一次修一个，在最合适的层级动手，用当初发现问题的那条标准复测，有回归就回滚，每个修复单独提交，有风险上限，最后交给独立复核 |
| **verify 验证** | 和基线比较"已消失 / 新引入 / 仍存在"，重算关卡 |
| **report 报告** | 用和证据等级相符的措辞写报告，生成"同意 / 不同意"反馈表 |

## 4. 八道关卡

| 关卡 | 名称 | 举例 |
|---|---|---|
| G0 | 证据完整性 | 运行清单齐全；工具冒烟测试通过；截图有效；每个问题都能定位；措辞不超过证据；评估员的隔离情况有记录 |
| G1 | 功能完整性 | 页面能加载；控制台无报错；关键旅程走得通；320–1440 宽度下没有横向溢出和文字被截断；CLS ≤ 0.1 |
| G2 | 无障碍（WCAG 2.2 AA） | axe 0 违规；键盘全可达；焦点可见且不被遮挡；对话框焦点行为正确；320 px 下可重排；目标尺寸 ≥ 24 px；对比度；表单；`lang`；不能只靠颜色传达信息 |
| G3 | 做工底线 | 字号下限、行高、行长、字体数量、层级比例、字距；颜色令牌化；间距刻度；圆角嵌套；阴影层级；动效属性、时长、缓动和减少动态；组件状态；触控目标；文案规范；中文字体栈 |
| G4 | 刻意性与反 AI 味 | `PRODUCT.md` / `DESIGN.md` 完整，方向决策有记录，本项目台账显示和前几次不重复；硬性 AI 味特征为 0（除非简报明确要求）；每个软性特征都有处置（已修复、已接受、有争议或已延期），每页最多 1 个已延期 |
| G5 | 分析式可用性 | 多位隔离评估员各做两遍；合并、验证、三人盲评；没有未处理的 P0，每个 P1 都有决定；关键旅程走查完；任务可完成性检查；覆盖率达标 |
| G6 | 设计质量评审 | 至少 3 位隔离评审；多数认为设计有针对性；多数判定有吸引力；没有多人一致认定的严重设计问题；体现品牌属性；不比旧版差。评分只作参考，**从不作为通过依据** |
| G7 | 实证验证 | 研究计划完整；每组至少 5 名用户；观察到的问题已并入；关键任务无协助完成率 ≥ 80%；修复后复测；指标带置信区间 |

每一条都有编号、阈值、验证方式和来源，详见 [QUALITY-BAR.md](framework/QUALITY-BAR.md)。

## 5. 怎么做到"不 AI 味"

靠的是一整套贯穿各阶段的**机制**，一份禁用清单解决不了问题：

| 阶段 | 机制 |
|---|---|
| 准备 | 简报写清：题材、受众、每个页面唯一要完成的事、界面模式（说服 / 操作 / 阅读 / 体验）、使用场景（决定用浅色还是深色）、3–5 个"是 X，不是 Y"的品牌属性、语气定位、真实内容和事实清单 |
| 定方向 | 先找参考：至少 3 个品类外、1–2 个品类内，只提取"基因"，不搬素材。从用户的世界出发生成候选方向，并明确排除"这个品类的标配"和"它的套路化反面" |
| 定方向 | **带种子的抽签**会发出一个避开模型前两名首选的方向，加上模型自己的首选和常规方案；结构参数从台账里最近没用过的选项中抽取 |
| 定方向 | 三项趋同测试：同样的需求会不会落到这里？只看品类能不能猜出长相？换成无关的产品还能不能原样用？ |
| 构建 | 只用令牌、不写死数值；每次编辑后自动检查硬性特征和做工底线 |
| 审查 | 确定性检测只报告"特征密度"（0–1 低，2–3 中，4+ 高），从不下"这是 AI 做的"这种结论；设计评审先独立判断，再看检测结果 |
| 长期 | 本项目的方向台账保证新作品和最近 3 次在字体和页面结构上都不同（项目里的第一个方向没有可比对象，靠带种子的抽签保证多样；跨项目台账只作提示）；AI 味特征目录带版本和状态，每次模型大版本更新都重新校准 |

另外有四条原则，防止"反 AI 味"本身变成新的套路，或者把页面删得光秃秃：
- **不提供推荐字体或配色清单。** 某一代的推荐，就是下一代的 AI 味。
- **示例总是同时给出风格对立的两种以上方向。**
- **简报明确要求的样式就是合理的。** 惯例本身不算 AI 味：操作类页面的导航和控件保持常规，是对用户负责。
- **题材自己的材质不算痕迹。** 书法班的宣纸和印章、修表铺的表盘，是要结合产品具体内容来用的参照。构建收尾的完成度检查和评审的吸引力裁定，会让"干净但寡淡"的页面不通过（[ADR-035](framework/DECISIONS.md#adr-035--appeal-is-judged-and-gates-g6)）。

## 6. 为什么评估结果可信

- **多人独立再合并**：标准深度会派出 3 位启发式评估员，每人做两遍（第一遍熟悉流程，第二遍逐个元素检查），彼此看不到对方的结果。
- **黑盒和白盒分开**：黑盒评估员看不到源码和开发过程，所以不会被实现意图带偏；白盒的代码审查员负责给出文件和行号，并估计修复难度。每个角色能看到什么，由脚本生成的"材料包"决定，而不是靠主助手自觉。
- **验证员把关**：每个候选问题都要过一条链：证据能否定位 → 是否截图或测试工具造成的假象 → 是否在范围内 → 能否亲手复现 → 说"缺少某样东西"时是否有证据 → 是否已被人否决过 → 从第 2 轮起，只被一次检查发现的问题先打上可信度上限标记（评分后平均分低于 2.5 的暂不报告，等第二次独立检查或人工确认）。
- **盲评严重度**：至少 3 人各自先评频率、影响、持续性，再给 0–4 级，取平均并保留分歧；判为"不是问题"的票不计入平均。分歧 ≥ 2，或有人判"不是问题"而平均分 ≥ 2.5 的问题，交给真实用户去判断，**不投票**。
- **证据等级决定措辞**：E0 预测，E1 已复现或已测量，E2 专家确认，E3 用户观察到（k/n），E4 带置信区间的量化结果，E5 随机实验证明的因果。只有 E3 及以上才能写"用户会……"，只有 E5 才能用因果动词。
- **没跑过的检查不算通过**；无法隔离时，结果顶部必须标注 `DEGRADED`。

## 7. 用户反馈怎么闭环

1. **study**：确定要回答的决策问题，选方法，计算样本量，写出不含界面字眼的任务，设计招募和**固定报酬**（课件讲过：按表现给报酬会让人视野变窄、行为失真），准备主持人脚本、知情同意书、观察表，先定好分析计划，然后试测。
2. 由真人去执行测试。AI 助手**不会**编造参与者数据。
3. **ingest**：导入数据并去除个人信息 → 给每条反馈分类 → 用主题分析或亲和图归纳主题，每个主题都要有比例（k/N）和至少两条原话 → 挂到已有问题上，频率和证据等级随之升级；或者新建候选问题，先复现再说 → 按观察到的频率重新评定严重度 → 计算 SUS / SEQ / 完成率并给出置信区间。
4. 用户报告的问题，只有人（或原报告者）可以关闭。

## 8. 怎么修

- 修复顺序：先按优先级，再按依赖层级（令牌 → 布局间距 → 字体 → 颜色 → 组件状态 → 动效 → 文案），然后看修复难度和出现频率。
- 每个问题先写"验收条件"，也就是当初发现它的那条标准，然后在最合适的层级修改：令牌、共享组件，还是局部。
- 改完立刻复测：原来那条检查、相邻的正常流程、截图像素对比、无障碍树对比、控制台；有回归就回滚。
- 每个问题单独一次提交；同一个问题最多试 3 次；每修 5 个算一次风险分，超过 20% 就停下来问人；单次运行最多修 30 个。
- 最后由一位全新的复核员根据前后证据逐项判定"确认修好 / 部分修好 / 未修好"，最多指出 3 个回归。"部分修好"或"未修好"的，一律不能发布。
- 修复者自己的复测只能把问题标为"已修复"；要标为"已验证"，必须有修复者以外的证据：复核员判定"确认修好"、同一项自动检查在修好的版本上复跑后不再报出，或由人确认。

## 9. 课件知识点的落地对照

| 课件内容 | 框架里的落点 |
|---|---|
| 分析式评估 vs 实证评估，二者交替进行 | audit 和 study + ingest 交替；原则 P9 |
| 启发式评估、Nielsen 十条 | 启发式评估员；`knowledge/heuristics.md` |
| 每位评估员至少两遍 | 第一遍熟悉流程，第二遍逐个元素检查 |
| 一个违规记一条 | 一条记录只写一个问题 |
| 3–5 位独立评估员，再达成共识 | 标准深度 3 位，严格深度 5 位；确定性合并 |
| 汇总讨论（debrief） | audit 第 12 步的 `debrief.md` |
| 严重度 0–4，看频率、影响、持续性 | 盲评三个因子，取平均，保留分歧 |
| 修复难度由开发团队评 | 白盒代码审查员给出修复难度（1–4） |
| 报告字段（问题、原则、描述、证据、严重度、建议） | 问题记录的数据结构 |
| 问题类型（单处、多处对比、整体结构、缺失） | `problem_type` 字段；说"缺失"必须给出查找过的证据 |
| 启发式评估会产生"假问题" | 验证员复现，有分歧的问题交给用户 |
| 认知走查的四个问题 | 走查评估员，逐步回答 CW-Q1…Q4 |
| 目标 → 任务 → 数据 → 分析 | study 工作流和研究计划模板 |
| A/B 测试（只改一个变量、测结果、重复） | `methods/experiments-analytics.md` |
| Mill 的因果条件、相关不等于因果、对照实验 | 只有 E5 才能用因果措辞；对照实验设计 |
| 定量和定性结合 | 每个数据异常都配一次定性探查 |
| 参与者动机与固定报酬 | study 的招募要求 |

完整对照见 [TRACEABILITY.md](framework/TRACEABILITY.md)。

## 11. 怎么用

- **Claude Code（推荐，可以真正隔离评估员）**：添加插件市场 `Horace-Maxwell/UI-Evaluator` 后安装 `ui-evaluator` 插件，两条命令见 [README 的快速上手](../README.zh-CN.md#快速上手)。之后可以直接说"帮我审查这个页面"，或使用 `/ui-evaluator:audit` 等命令。
- **其他助手（Codex、Cursor、Gemini CLI 等）**：`npx skills add Horace-Maxwell/UI-Evaluator`。没有子代理的环境会顺序执行各个角色，并标注 `DEGRADED`。
- 常见说法示例：
  - "给我们的宠物医院预约页做一个新设计。" → setup → direct → build → audit → fix → verify → report
  - "这个后台页面哪里有问题？" → audit（标准深度）→ report
  - "这是 5 场可用性测试的记录，帮我整理并修复。" → ingest → fix
  - "帮我设计一轮可用性测试。" → study
  - "这个能上线了吗？" → verify → report
- 检测器判错了、程序出错或缺少规则，请用 GitHub 上的 issue 表单提交；安全问题按 [SECURITY.md](../SECURITY.md) 私下报告。

## 12. 局限

- 它不能替代设计师和用户研究。它让 AI 助手成为更好的合作者和第一轮审查者，品味上的分歧和关于用户的结论都交给人。
- 评估一定会有遗漏。报告会写明预期覆盖率，并估计还有多少问题没被发现。
- 不少 AI 味阈值还是专家经验，标注为 [calibrating]，会用标注数据逐步校准。
- 目前只覆盖网页；原生 iOS、Android 和桌面应用不在范围内。
- 数据可视化和高密度企业界面方面的调研相对少，相关规则会如实说明。
- **实测结果。** 四轮基准测试里，技能稳定提升了能验证的质量：零硬性 AI 痕迹，守住无障碍底线，不编造内容，页面与回复的检查满足 83–100%（不用技能为 0–70%；评分脚本另有几条检查技能自己文件的断言，不用技能的版本不可能通过，所以不计入比较）。但在真人盲评中，它还不能稳定做出更美的页面：最近一轮 8 组里，不用技能的版本有 6 组被判为更美。代价约为 2.7 倍 token 和 2.3 倍时间。只有一位评委、样本量小，详见 [README 的实测结果](../README.zh-CN.md#实测结果) 和 [evals/README.md](../evals/README.md#results)。
- **发布门槛。** 对照[评估计划](framework/EVALUATION-PLAN.md) §6，2.0.0 达到了测试、检测器和脚本化无障碍检查的门槛；没有达到“构建结果”门槛（要求真人盲评中至少 70% 偏好技能版，实际 12 组中只有 3 组）；2026-10-06 的[智能体评测](../evals/results/agent-evals-2026-10-06/REPORT.md)补测了其中四项：标准深度审计单次运行达标（召回 10/11、判定类发现的精确率 0.82），但不加载技能的同一模型在同一网站上也找到 10/11，说明这个测试网站分不出两组；反馈导入达标（主题与问题的链接准确率 0.99，个人信息清除 62/62）；诚实一项的用语检查和等级声明达标；修复循环未达标（3 个预埋的严重缺陷中验证修复了 2 个）。多样性仍未测量。逐项情况见[门槛对照表](../evals/README.md#status-against-the-release-thresholds)。
